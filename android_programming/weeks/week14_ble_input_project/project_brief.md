# 14주차 2차 과제 안내 — Smart I/O Controller 2~3분 시연

이 문서는 학생과 평가자가 함께 보는 공개 안내다. 제출 위치·마감·팀 운영처럼 분반마다 다를 수 있는 것은 수업 공지(LMS)가 이 문서보다 **우선**한다.
점수 기준은 [채점표](rubric.md)에 있다.

## 한눈에 보기

| 항목 | 내용 |
|---|---|
| 때 | 14주차 2일차 발표(60분). 인원이 많으면 조교 평가자를 늘려 조를 나눠 동시에 듣는다([발표 정원 계산](#발표-정원-계산)) |
| 배점 | 20점 = 발표 12 + 레포트 8 (2차 과제 20%) |
| 형식 | 개인 과제를 기준으로 안내한다. 2인 팀을 허용할지와 팀 점수 적용은 수업 공지를 따르며, 팀이어도 **코드 설명은 한 사람씩** 한다 |
| 앱 | 4주차부터 만든 `SmartIO`(Smart I/O Controller). 14주차 1일차까지 만든 것을 이어서 쓴다. 없으면 13주차 완성본에서 14주차 따라하기를 한다 |
| 범위 | 2~14주차에 배운 것(View·ViewBinding·Intent·생명주기·코루틴·ViewModel·StateFlow·권한·ListView·SharedPreferences·제공 bleuno 라이브러리) |
| 기기 | 실기기 + 수업 보드, 또는 에뮬레이터 + 가짜 클라이언트(Fake). 채점표의 항목은 둘을 같은 기준으로 본다. 실보드 시연을 반드시 해야 하는지는 수업 공지를 따른다 |
| 연습 | 14주차 1일차 실습 [캡처 세트와 시연 리허설](lab.md#7-캡처-세트와-23분-시연-리허설) |

## 필수 기능 — 일곱 가지

| # | 필수 기능 | 시연에서 보여 줄 장면 | 만드는 코드(수업 예제 기준) |
|---|---|---|---|
| 1 | 권한 안내 | [권한 확인] → Toast `권한 OK`, 또는 거절 뒤 AlertDialog `권한이 필요합니다` → [설정으로] | 10주차 권한 요청 틀, `showPermissionDialog()` |
| 2 | 검색·연결·해제·상태 표시 | [검색] → `검색된 장치`에 `ESP32_BLE…` → 줄 탭 → `연결 중` → `서비스 확인 중` → `준비됨` → [해제]로 `연결 안 됨` | 12주차 `startScan`·`connect`·`disconnect`, 연결 상태 collect |
| 3 | 출력 1개 이상 제어 | 제어 화면 LED Switch 켜기·끄기 → 명령 로그 `on 3`과 `응답: {"result":"ok","ms":"led(s) on"}`(실보드면 LED가 켜진다) | 13주차 `send("on $index")`·`onMessage` |
| 4 | 입력 수신 | [온습도 받기 시작] → 입력 이력에 `시:분:초 [온도,습도]` 3줄 이상 → [중지]. Fake는 입력 이벤트 `시:분:초 입력=1` 3줄도 된다 | 14주차 `inputJob`·`addHistory()`·`BleunoMessage.value/event` |
| 5 | 끊김·시간 초과 안내와 재시도 | 끊김(실보드 전원 끄기 또는 Fake [끊김 시험]) → Toast + [재연결] → `준비됨`. 연결이 10초를 넘으면 Toast `연결 시간이 초과되었습니다`와 [다시 시도] | 14주차 `ConnState.LOST` 가지·`connect(lastAddress)`·`waitConnectTimeout()` |
| 6 | 명령 규약 준수 | 명령 이름 + 띄어쓰기 한 칸 + LED 번호 `0`~`3`(`-1`은 전체). 허용되지 않는 번호는 보내지 않는다 | 13주차 명령 글자, `isAllowedIndex()` |
| 7 | 재현 가능한 2~3분 시연 절차 | 레포트 1절에 적은 순서대로 누르면 누구든 같은 화면을 볼 수 있다 | 레포트 1절 |

- 명령 규약과 입력 이벤트 형식은 [bleuno README 2절](../../bleuno/README.md#2-명령과-응답)이 기준이다.
- 입력 이벤트(`{"event":"input",…}`)는 지금 펌웨어가 보내지 않는다. 실보드의 입력 수신은 `dht11` 응답으로 보인다.
- 시간 초과는 가짜 보드가 2초 만에 `준비됨`이 되어 시연 중에 나오지 않는다. 확인 화면을 레포트에 넣고, 질문 시간에 코드 줄로 설명한다.
- 선택(점수에 더하지 않음): Fake/실보드 전환(`useFake` 한 줄), [이력 지우기] 같은 본인 기능. 넣은 기능 때문에 필수 기능이 망가지면 그 필수 기능 항목에서 깎인다.
- `collect { }` 안에서는 View만 바꾸고 `startActivity`를 넣지 않는다(7주차). Toast는 화면의 함수로 빼서 부른다(14주차).

## 학생 범위와 안전

- 학생은 **Android 앱만** 만든다. 보드 펌웨어를 고치거나 올리지 않고, 회로를 바꾸지 않는다. 강의자 전용 명령(`config`·`reboot` 등)은 보내지 않는다.
- 실보드에는 LED 번호 `0`~`3`과 `-1`만 보낸다. 보드는 번호 범위를 검사하지 않는다.
- 보드 하나에 폰 하나다. 발표 전에 내 보드의 칩 ID 라벨을 확인하고, 다른 사람 발표 중에는 보드에 연결하지 않는다.
- 보드가 이상하면 강의자에게 교환을 요청한다. 학생이 복구하지 않는다.

## 2~3분 시연 절차

Fake(에뮬레이터)로 할 때:

```text
0:00  [권한 확인] → 권한 OK
0:10  [검색] → ESP32_BLE_FAKE1 줄 탭 → 연결 중 → 서비스 확인 중 → 준비됨
0:30  [제어 화면] → 3 입력 → LED 켜기·끄기 → on 3 / 응답 줄
0:50  [온습도 받기 시작] → 약 6초 → 이력 3줄 → 이력 줄 하나 탭(Toast) → [중지]
1:20  [뒤로] → [끊김 시험] → 끊김 + Toast + [재연결]
1:40  [재연결] → 준비됨
2:00  [해제] → 연결 안 됨
2:10  마무리 한 문장
```

실보드로 할 때는 1:20 줄부터 바뀐다.

```text
1:20  제어 화면에서 받는 중에 보드 전원 끄기 → 상태: 끊김 + Toast → [뒤로]
1:40  보드 전원 켜기 → 파랑 깜빡임 → [재연결] → 준비됨
2:20  [해제] → 연결 안 됨
2:30  마무리 한 문장
```

- 3분이 되면 평가자가 시연을 멈춘다. 보드가 다시 켜지는 시간까지 리허설에서 재 둔다.
- 시연 전 앱은 첫 화면(`연결 안 됨`)에 둔다. `끊김` 상태로 시작하지 않는다.
- 캡처는 세로 화면으로 찍는다. 받는 중에 화면을 돌리면 입력 이력이 빈다(정해진 동작).

## 발표 — 1인 5분

```text
0:00–1:00  자리 잡기, 앱을 첫 화면에, (실보드) 보드 파랑 깜빡임 확인
1:00–4:00  시연 2~3분 (3분이 되면 멈춘다)
4:00–5:00  평가자 질문 한 개 → 파일 열기 → 줄 가리키기 → 한 문장으로 답하기
```

- 앞 사람이 발표하는 동안 내 앱을 실행해 첫 화면에 두고, 코드 설명에 쓸 파일을 편집기 탭에 열어 둔다.
- 3분 안에 보이지 못한 장면은 레포트 캡처로 보되, 그 항목은 **최대 절반**이다. 예외는 조교 장애 기록이 있을 때다([채점표](rubric.md)).
- 코드 설명 질문의 예는 [슬라이드 2일차 12–20분](slides.md)에 있다. 질문은 평가자가 시연에서 보인 장면 중에서 고른다.
- 발표 자료(PPT)는 만들지 않는다. 앱과 코드 편집기, Logcat만 쓴다.

## 레포트

| 항목 | 내용 |
|---|---|
| 형식 | PDF 한 개, 3~5쪽. 파일 이름 `학번_이름_2차과제.pdf` |
| 함께 내는 것 | 프로젝트의 `app/src/main` 폴더를 압축한 파일 한 개(`학번_이름_2차과제_src.zip`) |
| 위치·마감 | 수업 공지의 LMS 제출 칸. 마감은 공지를 따른다 |

레포트에 넣을 다섯 절:

1. **실행 방법과 시연 절차** — Fake와 실보드 중 무엇으로 확인했는지(`useFake` 값), 2~3분 시연 순서(누르는 것 → 보이는 것), 내가 만들거나 고친 파일 이름과 하는 일 한 줄씩.
2. **필수 기능 캡처와 코드 위치** — 아래 표를 채운다. 캡처는 에뮬레이터 창의 카메라 모양 버튼(Take Screenshot)이나 실기기 화면 캡처로 찍는다.

| 칸 | 캡처 | 이 장면을 만드는 코드(파일 이름과 줄 번호) |
|---|---|---|
| 권한 안내 | Toast `권한 OK` 또는 AlertDialog `권한이 필요합니다` | |
| 장치 목록 | `검색된 장치`에 `ESP32_BLE…` 줄 | |
| 준비됨 | 상태 `준비됨`, [제어 화면] 켜짐 | |
| 출력 제어 | 명령 로그 `on 3`과 응답 줄(실보드면 LED 사진) | |
| 입력 수신 | 입력 이력 3줄 이상 | |
| 끊김 + [재연결] | 상태 `끊김`과 [재연결] | |
| 시간 초과 | Toast `연결 시간이 초과되었습니다`와 [다시 시도] | |

3. **Logcat 근거** — `package:mine tag:BLE` 캡처 한 묶음(온습도 한 번 받기의 `writeCharacteristic` → `onCharacteristicChanged`, 또는 끊김 → [재연결]의 `connectGatt` → `준비됨`)과, 그중 어느 줄이 앱이 보낸 것이고 어느 줄이 보드(또는 가짜 보드)가 보낸 것인지 한 줄씩.
4. **오류 해결 기록** — 만들면서 겪은 오류 한 개 이상. 빨간 오류 메시지 원문(또는 앱이 멈춘 증상과 Logcat 줄), 원인, 고친 방법.
5. **확인 환경과 알려진 한계** — 에뮬레이터 API 또는 실기기 Android 버전, 확인한 방법(Fake/실보드), 알고 있는 한계(예: 받는 중 회전하면 이력이 빈다, 실보드는 입력 이벤트가 없다), 발표·연습 중 장애가 있었다면 그 기록.

생성형 AI에게 받은 코드를 그대로 넣었다면 그 부분을 레포트에 밝힌다. 코드 설명 질문은 내가 제출한 코드로 한다.

## 발표 정원 계산

발표 시간이 60분을 넘지 않는지 분반 인원이 정해지면 바로 계산한다.

```text
발표 시간 T = ceil(N / E) × D ≤ 60분
N = 발표 인원(팀이면 팀 수), E = 동시에 따로 듣는 평가자 수, D = 5분(보드 연결 대기 포함)
ceil(x) = 소수점 올림
```

팀을 허용한 분반은 코드 설명을 한 사람씩 하므로 2인 팀이면 D = 6분(자리·시연 4분 + 질문 1분 × 2)으로 계산한다.

| N | E | ceil(N / E) × 5 | 운영 |
|---|---|---|---|
| 12 | 1 | 12 × 5 = 60분 | 2일차 60분에 끝난다 |
| 24 | 2 | 12 × 5 = 60분 | 평가자 두 명이 두 조로 나눠 동시에 듣는다 |
| 30 | 2 | 15 × 5 = 75분 | 넘친다 → 조교 평가자를 늘려 E = 3 → 10 × 5 = 50분 |
| 40 | 3 | 14 × 5 = 70분 | 넘친다 → E = 4 → 10 × 5 = 50분 |

- 넘치면 조교 평가자를 늘려 조를 나눈다. 조마다 자리를 떨어뜨려 보드 검색이 섞이지 않게 한다.
- 조 배정과 순서표는 1일차에 공지한다. 조가 달라도 채점 기준과 레포트 마감은 같다.

## 실물 장비가 안 될 때 — 앱과 장비 나누기

**먼저 손을 든다.** 조교가 시각·증상·Logcat `tag:BLE` 마지막 줄을 기록한다. 빨간 오류, 앱이 멈추는 것처럼 **내 코드 때문에 생긴 문제는 장애가 아니다.**

| 증상 | Logcat `tag:BLE`에서 볼 것 | 대체 절차 |
|---|---|---|
| 목록에 보드가 뜨지 않는다 | `onScanResult:` 줄이 없다. 또는 `startScan: 권한이 없어 무시함` | 권한 경고면 내 앱 문제다. 경고가 없으면 보드 LED가 파랑 깜빡임인지(다른 폰이 연결했는지) 본다. 1분 안에 안 되면 Fake로 바꾼다 |
| `연결 중`에서 멈추고 10초 뒤 시간 초과가 된다 | `connectGatt(…)` 뒤에 `onConnectionStateChange:` 줄이 없다 | 보드 전원을 껐다 켜고 한 번 더 한다. 그래도 안 되면 Fake로 바꾼다 |
| `준비됨`인데 온습도 응답이 오지 않는다 | `writeCharacteristic("dht11")` 뒤에 `onCharacteristicChanged:` 줄이 없다 | 보드·센서 문제일 수 있다. 출력 제어가 되는지 먼저 보이고, 입력 수신은 Fake로 보인다 |
| 실기기가 Android Studio에 잡히지 않는다 | — | 에뮬레이터 + Fake로 바꾼다 |
| 에뮬레이터가 켜지지 않거나 멈춘다 | — | Device Manager에서 ⋮ › **Cold Boot Now**. 3분 안에 안 되면 순서를 맨 뒤로 미룬다 |

Fake로 바꾸는 순서: `MainActivity.kt`의 `private val useFake = false`를 `true`로 → `Run ▶` → [2~3분 시연 절차](#23분-시연-절차)의 Fake 순서대로. 끊김은 [끊김 시험]으로 만든다.

- **Fake에서 필수 기능이 모두 되면** 앱은 정상이고 장비 쪽 문제다. 조교 기록과 함께 장애로 보고, 실보드로 못 보인 장면은 Fake 시연으로 만점까지 인정한다.
- **Fake에서도 안 되면** 내 코드 문제다. 남은 시간에 보일 수 있는 장면을 보이고 레포트 캡처로 설명한다.
- PC가 멈추거나 수업 안에 끝내지 못하면 기록을 근거로 다음 수업 시작 전에 발표한다. 결석(공결)은 대학 규정과 수업 공지를 따른다.

## 제출 전 점검표

- [ ] 마지막으로 고친 뒤 저장 → 다시 실행해서 필수 기능 일곱 가지를 한 바퀴 확인했다.
- [ ] 레포트 2절 표의 캡처 일곱 칸과 코드 위치가 제출한 소스의 줄 번호와 같다.
- [ ] 시연 절차대로 2~3분 안에 끝나는 것을 재 보았다(실보드면 보드가 다시 켜지는 시간까지).
- [ ] `useFake` 값이 발표할 방법과 맞고, 실보드가 안 될 때 Fake로 바꾸는 순서를 안다.
- [ ] 캡처에 계정·알림 내용 같은 개인정보가 보이지 않는다.
- [ ] 소스 압축 파일에 `app/src/main`이 들어 있다.
