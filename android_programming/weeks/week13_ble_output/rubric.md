# 과제 채점표 — 계획안 발표 10 + 최종 제출 20 = 30점

필수 기능과 제출 방법은 [과제 안내](project_brief.md)에 있다. 이 채점표는 발표 전에 공개하며, 평가자는 아래 기록 양식에 근거를 적는다.
팀 운영 여부와 팀원 점수 적용은 수업 공지를 따른다. 팀이어도 **코드 설명은 한 사람씩** 하고 학생별로 기록한다.

## 배점 검산

| 구분 | 때 | 배점 |
|---|---|---|
| 계획안 발표 | 13주차 2일차 | 10 |
| 최종 제출 — 시연 | 15주차 | 12 |
| 최종 제출 — 레포트 | 15주차 | 8 |
| **합계** | | **30** |

두 시점은 **따로 채점한다.** 계획안 발표에서 깎인 점수를 최종 제출로 되돌릴 수 없고, 반대도 마찬가지다.

## 1부. 계획안 발표 — 10점 (13주차 2일차)

발표하는 날 앱은 아직 12주차 수준이다. **완성도를 채점하지 않는다.** 무엇을 만들지 정했는지, 그 계획이 필수 기능과 맞는지, 지금 코드를 설명할 수 있는지를 본다.

| 항목 | 배점 | 만점 | 부분 점수 | 0점 |
|---|---|---|---|---|
| 만들 앱과 화면·기능 목록 | 2 | 앱 한 줄 소개가 있고, 화면 두 개(연결·제어)에 둘 버튼·칸과 하는 일이 적혀 있다. 필수 기능 일곱 가지가 어느 화면에 들어가는지 표시했다 | 1.5: 화면·기능 목록은 있으나 필수 기능 두 가지 이상이 어디에도 없다 / 1: 앱 소개만 있고 화면·기능 목록이 한두 줄뿐이다 | 무엇을 만들지 정하지 못했다 |
| 보드 명령 목록 | 2 | 보낼 명령 글자를 규약대로 적었고(`on 3`·`off -1`·`pwm 0 128`·`dht11` 등), 각 명령을 어느 버튼이 보내는지 함께 적혀 있다 | 1.5: 명령은 맞지만 어느 버튼이 보내는지 없다 / 1: 명령 글자가 규약과 다르다(`on3`·`led on`처럼 띄어쓰기나 이름이 틀림), 또는 보드가 모르는 명령이 섞였다 | 명령 목록이 없다 |
| 남은 2주 일정 | 1.5 | 14주차에 할 것과 15주차 제출 전에 할 것이 나뉘어 있고, 필수 기능과 짝이 맞는다 | 1: 일정이 있으나 둘로 나뉘지 않았거나 필수 기능과 짝이 맞지 않는다 / 0.5: "열심히 하겠다" 수준으로 할 일이 없다 | 일정이 없다 |
| 막힐 것 같은 곳과 대비책 | 1.5 | 걱정되는 것 한 가지 이상을 구체적으로 적고, 안 될 때 무엇으로 대신할지(예: Fake로 같은 흐름) 적혀 있다 | 1: 막힐 곳만 있고 대비책이 없다 / 0.5: "아직 모르겠다"만 있다 | 없다 |
| 지금 되는 화면 시연 | 1.5 | 앱이 실행되고 [검색] → 줄 탭 → `준비됨`까지 간다(Fake 인정). 어디까지 됐는지 말로 설명한다 | 1: `준비됨`까지 가지만 설명이 없다 / 0.5: 앱은 실행되지만 `준비됨`까지 가지 못한다 | 앱을 실행하지 못했다 |
| 코드 설명(개인 구술) | 1.5 | 질문을 받고 해당 파일과 줄을 스스로 찾아 가리키며, 그 줄이 하는 일을 맞게 한 문장으로 말한다 | 1: 줄은 찾지만 설명이 틀리거나 빠진다 / 0.5: 평가자가 파일을 알려 준 뒤에야 줄을 찾는다 | 줄을 찾지 못하고 설명하지 못한다 |
| 소계 | **10** | | | |

- 발표는 2분에서 멈추고 질문으로 넘어간다. 2분 안에 보이지 않은 장면은 계획안 1쪽의 글로 판단하되 **해당 항목 최대 절반**까지만 준다(조교 장애 기록이 있으면 만점까지).
- 아직 만들지 않은 기능이 있다는 사실로는 깎지 않는다. 깎이는 것은 계획이 없거나 필수 기능과 어긋나는 경우다.
- 계획안 1쪽이 없으면 앞의 네 항목(7점)을 발표 내용만으로 판단한다. 말로 다 설명했으면 인정한다.
- Fake와 실보드는 같은 기준으로 본다. 이 시점에 실보드 연결을 요구하지 않는다.

### 코드 설명 질문 — 지금까지 만든 코드에서만

질문은 평가자가 고른다. **아직 만들지 않은 기능은 묻지 않는다.** 예:

| 질문 | 답이 있는 곳(수업 예제 기준) |
|---|---|
| 회전해도 연결이 이어지는 까닭은? | `MainActivity.kt`의 `client = Bleuno.client ?: Bleuno.create(this, useFake)` |
| `ESP32_BLE`로 시작하는 보드만 목록에 넣는 줄은? | `onFound` 안의 `if (name.startsWith("ESP32_BLE"))` |
| 목록 줄을 눌렀을 때 어느 주소로 연결하나? | `addresses.get(position)` → `client.connect(address)` |
| `준비됨`일 때만 [제어 화면]이 켜지는 줄은? | 연결 상태 collect 안의 `ConnState.READY` 가지 |
| 제어 화면이 연결 화면과 같은 연결을 쓰는 까닭은? | `object Bleuno`의 `client` 하나를 두 화면이 같이 쓴다 |
| (13주차 1일차를 한 사람) 보낸 명령과 받은 응답을 가르는 줄은? | `send("on $index")`와 `onStart`의 `onMessage { json -> }` |

- 화면만 보여 주고 질문에 줄을 가리키지 못하면 코드 설명 항목을 충족한 것으로 보지 않는다.
- 12주차 완성본을 받아 시작한 학생도 같은 질문을 받는다. 받은 코드라도 무엇을 하는 줄인지는 설명할 수 있어야 한다.

## 2부. 최종 제출 — 20점 (15주차)

### 시연 — 12점 (필수 기능별)

제출한 앱·캡처 세트·소스로 확인한다. 직접 시연을 받는 분반은 수업 시간과 별도로 공지한 시간에 본다(15주차 두 날의 60분은 공개 리허설과 본시험이 쓴다).

| 항목 | 필수 기능 | 배점 | 만점 | 부분 점수 | 0점 |
|---|---|---|---|---|---|
| 권한 안내 | 1 | 1 | [권한 확인]으로 Toast `권한 OK`, 또는 두 번 거절 뒤 AlertDialog `권한이 필요합니다`와 [설정으로]가 보인다 | 0.5: 권한을 요청하지만 결과를 화면으로 알리지 않는다 | 권한 안내가 없다 |
| 연결 흐름 | 2 | 3 | 검색 목록 `ESP32_BLE…` → 줄 탭 → `연결 중`·`서비스 확인 중`·`준비됨` 상태 표시 → [해제]로 `연결 안 됨`까지 막힘 없이 동작한다 | 2: 한 부분이 빠진다([해제] 없음, 중간 상태가 보이지 않음 등) / 1: `준비됨`까지는 가지만 두 부분 이상 빠진다 | `준비됨`까지 가지 못한다 |
| 출력 제어와 명령 규약 | 3·6 | 2 | 출력을 하나 이상 규약대로(`on 3`·`off -1` 등) 보내고 응답 `{"result":"ok",…}`이 로그에 보인다(실보드면 LED가 바뀐다). 허용되지 않는 번호는 보내지 않는다 | 1: 명령은 나가지만 응답이 보이지 않는다 / 규약과 다른 명령으로 `fail`이 난다 / 허용되지 않는 번호를 막지 않는다 | 출력 제어가 없거나 명령이 나가지 않는다 |
| 입력 수신과 입력 이력 | 4 | 2 | [온습도 받기 시작] → 입력 이력에 시각이 붙은 `[온도,습도]` 줄이 2줄 이상(시각이 약 3초 간격인 줄) 쌓이고 [중지]로 멈춘다(Fake는 입력 이벤트 2줄도 인정) | 1: 1줄만 보인다 / 시각이 없다 / [중지]로 멈추지 않는다 | 입력이 화면에 보이지 않는다 |
| 끊김·재연결·시간 제한 | 5 | 2 | 끊김(실보드 전원 끄기 또는 [끊김 시험]) → 안내 Toast와 [재연결] → `준비됨`이 되고, 연결 시간 초과 안내도 보인다 | 1: 끊김 안내·[재연결]과 시간 초과 안내 중 하나만 된다 / [재연결]이 `준비됨`까지 가지 못한다 | 끊겨도 안내와 재시도가 없다 |
| 2~3분 절차 재현 | 7 | 2 | 레포트 1절의 순서대로 눌러 같은 화면이 나오고, 2~3분 안에 끝난다 | 1: 절차대로 나오지만 3분을 넘긴다 / 한 단계가 실제 앱과 다르다 | 절차가 없거나 절차대로 동작하지 않는다 |
| 소계 | | **12** | | | |

- 시간 초과는 가짜 보드가 2초 만에 `준비됨`이 되어 저절로 나오지 않는다. 레포트 캡처로 보여도 감점하지 않는다.
- Fake와 실보드는 같은 기준으로 본다. Fake만으로 보인 제출도 만점이 가능하다. 실보드 시연을 추가로 받을지는 수업 공지를 따른다.
- 별도로 공지한 직접 시연 자리에서는 3분이 되면 평가자가 멈춘다. 그 안에 보이지 않은 장면은 레포트 캡처로 판단하되 **해당 항목 최대 절반**까지만 준다(조교 장애 기록이 있으면 만점까지).

### 레포트 — 8점

| 항목 | 배점 | 만점 | 부분 점수 | 0점 |
|---|---|---|---|---|
| 실행 방법과 시연 절차 | 2 | Fake/실보드 여부와 `useFake` 값, 누르는 것 → 보이는 것 순서의 2~3분 시연 절차, 고친 파일 목록이 있고, 절차대로 누르면 같은 화면이 나온다 | 1: 셋 중 하나가 빠지거나 절차가 실제 앱과 다르다 | 없다 |
| 필수 기능 캡처와 코드 위치 | 3 | 일곱 칸(권한 안내·장치 목록·준비됨·출력 제어·입력 수신·끊김+[재연결]·시간 초과)의 캡처가 모두 있고, 칸마다 코드 파일과 줄 번호가 제출 소스와 맞다 | 2: 한두 칸의 캡처가 빠지거나 코드 위치가 틀리다 / 1: 세 칸 이상 빠지거나, 캡처는 있지만 코드 위치가 하나도 없다 | 캡처가 없다 |
| Logcat 근거 | 1 | `tag:BLE` 캡처 한 묶음과, 앱이 보낸 줄과 보드가 보낸 줄을 맞게 구분한 설명이 있다 | 0.5: 캡처만 있고 구분 설명이 없거나 틀리다 | 없다 |
| 오류 해결 기록 | 1 | 오류 메시지 원문(또는 증상과 Logcat 줄), 원인, 고친 방법이 한 건 이상 맞게 적혀 있다 | 0.5: 셋 중 하나가 빠진다 | 없다 |
| 확인 환경과 알려진 한계 | 1 | 확인한 기기·방법(Fake/실보드), 알고 있는 한계, 장애가 있었다면 그 기록이 사실대로 있다 | 0.5: 환경만 있고 한계가 없다 | 없다 |
| 소계 | **8** | | | |

- 계획안과 달라진 점을 5절에 적었는지는 가점·감점 항목이 아니다. 적혀 있으면 평가자가 계획안 점수를 다시 보지 않는다는 뜻이다.
- 캡처 칸이 Fake 화면인데 실보드라고 적었으면 그 칸은 인정하지 않는다. Fake라고 적으면 인정한다.

## 공통 판단

- 같은 원인으로 여러 항목이 깎이면 가장 가까운 항목 하나에서만 뺀다. 예: 입력 이력 어댑터를 붙이지 않아 제어 화면에서 앱이 멈추면 입력 수신에서만 빼고, 출력 제어는 멈추기 전 화면으로 본다.
- 장비 장애(조교 기록이 있는 것)와 내 코드 때문에 생긴 문제를 나눈다. 판단 절차는 [과제 안내의 보드가 없을 때](project_brief.md#보드가-없을-때--fake로-대체하기)를 따른다. Fake에서 필수 기능이 되면 장비 장애로 보고, 실보드로 못 보인 장면은 Fake로 만점까지 인정한다.
- (시험용) [끊김 시험] 버튼과 `as FakeBleunoClient` 줄은 채점하지 않는다. 넣지 않은 경우 Fake 끊김은 레포트의 실보드 캡처나 코드 설명으로 본다.
- 본인이 더한 기능(선택)은 점수에 더하거나 빼지 않는다.
- 제출 소스로 빌드되지 않으면 보인 화면과 제출물이 같은지 확인할 수 없다. 이때 처리(재제출 허용 여부)는 수업 공지를 따른다.
- 기말고사(개인 실기)와 이 과제는 따로 채점한다. 기말 실기 코드를 과제 제출물로 대신 낼 수 없다.
- 공개 저장소에는 학생 이름·학번·점수·제출물을 올리지 않는다.

## 0점 또는 인정하지 않는 증거

- 펌웨어를 고치거나 올린 결과를 Android 앱 구현 대신 낸 것
- 다른 학생(팀)의 계획안·시연 영상·캡처·Logcat을 자기 것으로 낸 것
- 실보드로 하지 않은 장면을 실보드 캡처라고 적은 것(Fake 캡처는 Fake라고 적으면 인정한다)
- 소스·실행 방법이 없어 무엇을 만들었는지 확인할 수 없는 것
- 계획안만 내고 발표 자리에 오지 않은 것(공결은 대학 규정과 수업 공지를 따른다)

표절·부정행위·지각 제출의 처리는 이 채점표가 아니라 대학 규정과 수업 공지를 따른다.
