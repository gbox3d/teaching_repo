# 과제 안내 — Smart I/O Controller 완성하기

이 문서는 학생과 평가자가 함께 보는 공개 안내다. 제출 위치·마감·팀 운영처럼 분반마다 다를 수 있는 것은 수업 공지(LMS)가 이 문서보다 **우선**한다.
점수 기준은 [채점표](rubric.md)에 있다.

이번 학기 과제는 **하나**다. 대상은 4주차부터 만들어 온 `SmartIO`(Smart I/O Controller) 앱이다.
두 시점으로 나눠 낸다. 13주차 2일차에 **계획안을 발표**하고, 15주차에 **완성본을 제출**한다.

## 한눈에 보기

| 항목 | 13주차 2일차 — 계획안 발표 | 15주차 — 최종 제출 |
|---|---|---|
| 때 | 13주차 2일차 실습 시간(60분) | 15주차. 제출 날짜·시각은 수업 공지 |
| 배점 | 10점 (과제 30점 중) | 20점 (과제 30점 중) |
| 내는 것 | 계획안 1쪽 + 지금까지 만든 앱으로 하는 3분 발표 | 완성 앱 소스 + 캡처 세트 + 레포트 |
| 완성 여부 | **완성하지 않아도 된다.** 12주차까지 만든 화면을 보여 주며 앞으로 무엇을 만들지 설명한다 | 필수 기능 일곱 가지가 모두 동작해야 한다 |
| 기기 | 에뮬레이터 + 가짜 클라이언트(Fake)로 해도 된다 | 실기기 + 수업 보드, 또는 에뮬레이터 + Fake |

- 과제는 **개인 과제**를 기준으로 안내한다. 2인 팀을 허용할지와 팀 점수 적용은 수업 공지를 따르며, 팀이어도 **코드 설명은 한 사람씩** 한다.
- 공지는 12주차 1일차에 했다. 13주차 2일차 발표까지 2주, 15주차 제출까지 4주가 있다.

## 대상 앱 — Smart I/O Controller

4주차부터 한 주에 한 겹씩 쌓아 온 그 앱을 그대로 이어서 쓴다. 새 프로젝트를 만들지 않는다.

```text
연결 화면 (MainActivity)                제어 화면 (ControlActivity)
[권한 확인] [검색] [중지] [해제]         상태: 준비됨
검색된 장치                              [3        ]  LED (●)
ESP32_BLE_FAKE1 (00:11:22:33:44:01)     [전체 끄기]
  └ 줄 탭 → 연결 중 → 서비스 확인 중     명령 로그
            → 준비됨 → [제어 화면]        on 3
                                         응답: {"result":"ok","ms":"led(s) on"}
```

프로젝트가 없거나 실행되지 않으면 강의자에게 12주차 완성본(`week12_ble_gatt/examples/day2`)을 받아 시작한다.
범위는 2~14주차에 배운 것이다(View·ViewBinding·Intent·생명주기·코루틴·ViewModel·StateFlow·권한·ListView·SharedPreferences·제공 bleuno 라이브러리).

## 필수 기능 — 일곱 가지

최종 제출에서 모두 동작해야 한다. 계획안 발표에서는 **아직 안 된 것이 있어도 된다.** 무엇이 되고 무엇이 남았는지만 분명히 말한다.

| # | 필수 기능 | 보여 줄 장면 | 만드는 코드(수업 예제 기준) |
|---|---|---|---|
| 1 | 권한 안내 | [권한 확인] → Toast `권한 OK`, 또는 두 번 거절 뒤 AlertDialog `권한이 필요합니다` → [설정으로] | 10주차 권한 요청 틀, `showPermissionDialog()` |
| 2 | 검색·연결·해제·상태 표시 | [검색] → `검색된 장치`에 `ESP32_BLE…` → 줄 탭 → `연결 중` → `서비스 확인 중` → `준비됨` → [해제]로 `연결 안 됨` | 12주차 `startScan`·`connect`·`disconnect`, 연결 상태 collect |
| 3 | 출력 1개 이상 제어 | 제어 화면 LED Switch 켜기·끄기 → 명령 로그 `on 3`과 `응답: {"result":"ok","ms":"led(s) on"}`(실보드면 LED가 켜진다) | 13주차 `send("on $index")`·`onMessage` |
| 4 | 입력 수신 | [온습도 받기 시작] → 입력 이력에 `시:분:초 [온도,습도]` 2줄 이상(시각이 약 3초 간격인 줄) → [중지]. Fake는 입력 이벤트 `시:분:초 입력=1` 2줄도 된다 | 14주차 `inputJob`·`addHistory()`·`BleunoMessage.value/event` |
| 5 | 끊김·시간 초과 안내와 재시도 | 끊김(실보드 전원 끄기 또는 Fake [끊김 시험]) → Toast + [재연결] → `준비됨`. 연결이 10초를 넘으면 Toast `연결 시간이 초과되었습니다`와 [다시 시도] | 14주차 `ConnState.LOST` 가지·`connect(lastAddress)`·`waitConnectTimeout()` |
| 6 | 명령 규약 준수 | 명령 이름 + 띄어쓰기 한 칸 + LED 번호 `0`~`3`(`-1`은 전체). 허용되지 않는 번호는 보내지 않는다 | 14주차 `isAllowedIndex()`, 13주차 명령 글자 |
| 7 | 재현 가능한 2~3분 시연 절차 | 레포트 1절에 적은 순서대로 누르면 누구든 같은 화면을 볼 수 있다 | 레포트 1절 |

- 명령 규약과 입력 이벤트 형식은 [bleuno README 2절](../../bleuno/README.md#2-명령과-응답)이 기준이다.
- 입력 이벤트(`{"event":"input",…}`)는 지금 펌웨어가 보내지 않는다. 실보드의 입력 수신은 `dht11` 응답으로 보인다.
- 시간 초과는 가짜 보드가 2초 만에 `준비됨`이 되어 시연 중에 나오지 않는다. 확인 화면을 레포트에 넣고, 질문 시간에 코드 줄로 설명한다.
- 3·4·5·6번 기능 가운데 13주차·14주차 수업에서 함께 만드는 것이 있다. 13주차 1일차에 3번, 14주차 1일차에 6번, 14주차 2일차에 4·5번을 다룬다.
- 선택(점수에 더하지 않음): Fake/실보드 전환(`useFake` 한 줄), [이력 지우기] 같은 본인 기능. 넣은 기능 때문에 필수 기능이 망가지면 그 필수 기능 항목에서 깎인다.

## 13주차 2일차 — 계획안 발표

### 완성 앱 시연이 아니다

이 자리는 **앞으로 무엇을 만들지 설명하는 자리**다. 발표하는 날 앱은 아직 12주차 수준(검색·연결·`준비됨`과 제어 화면 명령 로그)이다.
"아직 안 만들어졌는데 무엇을 보여 주나"로 헷갈리지 않게 정리하면 이렇다.

| 보여 주는 것 | 말하는 것 |
|---|---|
| **지금 되는 화면** — 12주차까지 만든 앱을 실행해 `준비됨`까지 간다. 13주차 1일차를 한 사람은 명령 로그도 보인다 | 어디까지 됐는지 |
| **계획안 1쪽** — 화면·기능 목록, 보드 명령 목록, 남은 2주 일정, 막힐 것 같은 곳과 대비책 | 무엇을 더 만들지, 언제 만들지 |

완성본 시연은 15주차 최종 제출에서 한다. 오늘 안 되는 기능이 있다는 사실로는 점수를 깎지 않는다.
깎이는 것은 **무엇을 만들지 정하지 못한 경우**와 **계획이 필수 기능과 어긋나는 경우**다.

### 계획안에 담을 다섯 가지

계획안은 **1쪽**으로 적는다(A4 한 장 또는 화면 한 장). 파일 이름은 `학번_이름_계획안.pdf`다. 제출 위치와 마감은 수업 공지를 따른다.

| # | 담을 것 | 적는 방법 |
|---|---|---|
| 1 | 만들 앱 한 줄 소개 | "Smart I/O Controller — 보드의 LED를 켜고 온습도를 받는 앱"처럼 한 문장 |
| 2 | 화면·기능 목록 | 화면 두 개(연결·제어)에 어떤 버튼·칸을 두고 각각 무슨 일을 하는지. 필수 기능 일곱 가지를 어느 화면에 둘지 표시한다 |
| 3 | 보드 명령 목록 | 내 앱이 보낼 명령 글자를 그대로 적는다(`on 3`·`off -1`·`pwm 0 128`·`dht11`). 각 명령을 어느 버튼이 보내는지 함께 적는다 |
| 4 | 남은 2주 일정 | 14주차에 할 것과 15주차 제출 전에 할 것을 나눈다. "14주차 1일차: 번호 검사와 오류 창", "14주차 2일차: 온습도 받기"처럼 적는다 |
| 5 | 막힐 것 같은 곳과 대비책 | 지금 가장 걱정되는 것 한두 가지와, 안 될 때 무엇으로 대신할지. 예: "보드를 못 받으면 Fake로 같은 흐름을 보인다" |

- 3번은 [bleuno README 2절](../../bleuno/README.md#2-명령과-응답)의 표에서 고른다. 표에 없는 명령은 보드가 모른다.
- 5번은 솔직하게 적는다. "모르겠다"가 아니라 **무엇이 왜 어려울 것 같은지**를 적으면 발표 뒤 답을 받을 수 있다.
- 발표 자료(PPT)는 만들지 않는다. 계획안 1쪽과 앱, 코드 편집기만 쓴다.

### 발표 방법 — 1인 3분

```text
0:00–0:20  이름, 만들 앱 한 줄 소개
0:20–1:00  지금 되는 화면 — 앱 실행 → [검색] → 줄 탭 → 준비됨 (→ 제어 화면)
1:00–1:40  계획안 1쪽 — 화면·기능 목록과 보드 명령 목록
1:40–2:00  남은 2주 일정, 막힐 것 같은 곳과 대비책
2:00–3:00  평가자 질문 한 개 → 파일 열기 → 줄 가리키기 → 한 문장으로 답하기
```

- 2분이 되면 평가자가 발표를 멈추고 질문으로 넘어간다.
- 앞 사람이 발표하는 동안 내 앱을 실행해 첫 화면(`연결 안 됨`)에 두고, 코드 설명에 쓸 파일을 편집기 탭에 열어 둔다.
- 질문은 **지금까지 만든 코드**에서 나온다. 아직 안 만든 기능은 묻지 않는다. 질문의 예는 [채점표](rubric.md)에 있다.
- 2분 안에 보이지 못한 장면은 계획안 1쪽의 글로 보되, 그 항목은 **최대 절반**이다. 예외는 조교 장애 기록이 있을 때다.

### 발표 정원 계산

2일차 60분 가운데 앞 10분은 발표 순서 확인과 계획안 마무리, 뒤 10분은 질문 정리와 15주차 제출 방법 확인이다.
발표에 쓰는 구간은 **10–50분, 40분**이다. 분반 인원이 정해지면 이 40분에 들어가는지 바로 계산한다.

```text
발표 시간 T = ceil(N / E) × D ≤ 40분
N = 발표 인원(팀이면 팀 수), E = 동시에 따로 듣는 평가자 수, D = 3분(발표 2분 + 질문 1분)
ceil(x) = 소수점 올림
평가자 한 명이 듣는 인원 = 40 ÷ 3 → 13명까지
```

| N | E | ceil(N / E) × 3 | 운영 |
|---|---|---|---|
| 20 | 1 | 20 × 3 = 60분 | 넘친다 → E = 2 → 10 × 3 = 30분 |
| 26 | 2 | 13 × 3 = 39분 | 발표 구간 40분 안에 끝난다 |
| 38 | 3 | 13 × 3 = 39분 | 평가자 세 명이 세 조로 나눠 같은 시간에 듣는다 |
| 45 | 4 | 12 × 3 = 36분 | 네 조로 나눈다. E = 3이면 15 × 3 = 45분으로 넘친다 |

- 평가자 수로 보는 수용 인원은 E = 1이면 13명, E = 2면 26명, E = 3이면 39명, E = 4면 52명이다. 넘치면 조교 평가자를 늘려 조를 나눈다.
- 조마다 자리를 떨어뜨려 보드 검색이 섞이지 않게 한다. 분반 인원과 평가자 수, 조 나누는 방식은 수업 공지로 알린다.
- 조 배정과 순서표(학번 순 또는 조 안의 번호 순)는 13주차 1일차에 공지한다. 조가 달라도 채점 기준과 제출 마감은 같다.
- 팀을 허용한 분반은 코드 설명을 한 사람씩 하므로 2인 팀이면 D = 4분(발표 2분 + 질문 1분 × 2)으로 계산한다. 이때는 평가자 한 명이 10팀까지 듣는다.

## 15주차 — 최종 제출

15주차는 기말고사(개인 실기)와 같은 주다. 제출 날짜·시각·위치는 [15주차 안내](../week15_final_exam/README.md)와 수업 공지를 따른다.
기말고사와 과제는 **따로 채점한다.** 기말 실기 코드를 과제 제출물로 대신 낼 수 없다.

### 제출물 세 가지

| 항목 | 내용 |
|---|---|
| 완성 앱 소스 | 프로젝트 폴더 전체를 압축한 파일 한 개(`학번_이름_과제_src.zip`). 넣을 것과 뺄 것은 아래 [소스 압축하는 방법](#소스-압축하는-방법)에 있다 |
| 캡처 세트 | 레포트 2절 표의 일곱 칸. 레포트 안에 넣는다 |
| 레포트 | PDF 한 개, 3~5쪽. 파일 이름 `학번_이름_과제.pdf` |

- 제출한 소스로 빌드되어야 한다. 빌드되지 않으면 캡처가 내 앱의 화면인지 확인할 수 없다.
- 캡처는 에뮬레이터 창의 카메라 모양 버튼(Take Screenshot)이나 실기기 화면 캡처로 찍는다. 세로 화면으로 찍는다.

### 소스 압축하는 방법

`settings.gradle.kts`가 들어 있는 **프로젝트 폴더**를 통째로 압축한다(Android Studio에서 프로젝트를 열 때 고르는 그 폴더다).
`app/src/main`만 압축하면 받는 쪽에서 프로젝트로 열 수 없어 빌드 확인이 되지 않는다.

| 구분 | 폴더·파일 |
|---|---|
| 넣는다 | `settings.gradle.kts`, `build.gradle.kts`, `gradle.properties`, `gradle/`, `gradlew`, `gradlew.bat`, `app/`(안에 `app/build.gradle.kts`와 `app/src/`가 들어 있다) |
| 뺀다 | `build/`, `app/build/`, `.gradle/`, `.idea/`, `local.properties` |

- 빼는 것은 빌드할 때 다시 만들어지는 폴더와 내 PC 경로가 적힌 파일이다. 그대로 넣으면 압축 파일이 수백 MB가 되고 받는 PC에서 경로가 맞지 않는다.
- 빼고 나면 압축 파일이 몇 MB 안쪽으로 작아진다. 100MB를 넘으면 `build/`나 `.gradle/`이 아직 들어 있다.
- 압축한 뒤 **다른 폴더에 풀어** Android Studio의 **File › Open**에서 `settings.gradle.kts`가 있는 폴더를 고르고 `Run ▶`까지 한 번 해 본다. 이것이 제출 전 마지막 확인이다.

### 2~3분 시연 절차

레포트 1절에 적을 순서다. 적은 대로 누르면 누구든 같은 화면이 나와야 한다.

Fake(에뮬레이터)로 할 때:

```text
0:00  [권한 확인] → 권한 OK
0:10  [검색] → ESP32_BLE_FAKE1 줄 탭 → 연결 중 → 서비스 확인 중 → 준비됨
0:30  [제어 화면] → 3 입력 → LED 켜기·끄기 → on 3 / 응답 줄
0:50  [온습도 받기 시작] → 약 3초 → 이력 2줄 → 이력 줄 하나 탭(Toast) → [중지]
1:20  [뒤로] → [끊김 시험] → 끊김 + Toast + [재연결]
1:40  [재연결] → 준비됨
2:00  [해제] → 연결 안 됨
2:10  마무리 한 문장
```

실보드로 할 때는 1:20 줄부터 바뀐다.

```text
1:20  제어 화면에서 받는 중에 보드 전원 끄기 → 상태: 끊김 + Toast → [뒤로]
1:40  보드 전원 켜기 → 파랑 깜빡임 → [재연결] → 준비됨
2:20  [해제] → 연결 안 됨
2:30  마무리 한 문장
```

- 시연 전 앱은 첫 화면(`연결 안 됨`)에 둔다. `끊김` 상태로 시작하지 않는다.
- 받는 중에 화면을 돌리면 입력 이력이 빈다(정해진 동작). 캡처는 세로에서 찍는다.
- 실보드로 할 때는 보드가 다시 켜지는 시간까지 재 둔다.

## 보드가 없을 때 — Fake로 대체하기

보드나 Android 실기기가 없어도 과제를 끝까지 할 수 있다. 채점표의 항목은 Fake와 실보드를 **같은 기준**으로 본다.

1. `MainActivity.kt`의 `private val useFake` 값을 `true`로 둔다. 예제 기본값이 `true`이므로 그대로면 손댈 것이 없다. 실보드로 바꾸며 `false`로 고쳤다면 `true`로 되돌린다.
2. `Run ▶`로 에뮬레이터(API 33 이상)에서 실행한다.
3. [위의 Fake 시연 절차](#23분-시연-절차) 그대로 누른다. 가짜 보드 두 개(`ESP32_BLE_FAKE1`·`ESP32_BLE_FAKE2`)가 1초·2초 뒤에 목록에 들어온다.

| 필수 기능 | Fake에서 보이는 모습 |
|---|---|
| 출력 제어 | LED는 없지만 명령 로그와 `응답: {"result":"ok","ms":"led(s) on"}`이 같다 |
| 입력 수신 | `dht11` 응답이 온다. `준비됨`이면 10초마다 입력 이벤트도 온다 |
| 끊김·재연결 | [끊김 시험] 버튼으로 끊김을 만든다(14주차에 만든다) |
| 시간 초과 | 가짜 보드는 2초 만에 `준비됨`이 되어 저절로 나오지 않는다. 확인 화면을 레포트에 넣는다 |

- 레포트 5절에 **Fake로 확인했다고 적는다.** Fake 캡처를 실보드 캡처라고 적으면 그 항목은 인정하지 않는다.
- 실보드로 하다가 장비가 안 되면 먼저 손을 든다. 조교가 시각·증상·Logcat `tag:BLE` 마지막 줄을 기록한다. 빨간 오류나 앱이 멈추는 것처럼 **내 코드 때문에 생긴 문제는 장애가 아니다.**
- Fake에서 필수 기능이 모두 되면 앱은 정상이고 장비 쪽 문제다. 조교 기록이 있으면 실보드로 못 보인 장면을 Fake로 만점까지 인정한다.

## 레포트 양식 — 다섯 절

1. **실행 방법과 시연 절차** — Fake와 실보드 중 무엇으로 확인했는지(`useFake` 값), 2~3분 시연 순서(누르는 것 → 보이는 것), 내가 만들거나 고친 파일 이름과 하는 일 한 줄씩.
2. **필수 기능 캡처와 코드 위치** — 아래 표를 채운다.

| 칸 | 캡처 | 이 장면을 만드는 코드(파일 이름과 줄 번호) |
|---|---|---|
| 권한 안내 | Toast `권한 OK` 또는 AlertDialog `권한이 필요합니다` | |
| 장치 목록 | `검색된 장치`에 `ESP32_BLE…` 줄 | |
| 준비됨 | 상태 `준비됨`, [제어 화면] 켜짐 | |
| 출력 제어 | 명령 로그 `on 3`과 응답 줄(실보드면 LED 사진) | |
| 입력 수신 | 입력 이력 2줄 이상(시각이 약 3초 간격인 줄) | |
| 끊김 + [재연결] | 상태 `끊김`과 [재연결] | |
| 시간 초과 | Toast `연결 시간이 초과되었습니다`와 [다시 시도] | |

3. **Logcat 근거** — `package:mine tag:BLE` 캡처 한 묶음(온습도 한 번 받기의 `writeCharacteristic` → `onCharacteristicChanged`, 또는 끊김 → [재연결]의 `connectGatt` → `준비됨`)과, 그중 어느 줄이 앱이 보낸 것이고 어느 줄이 보드(또는 가짜 보드)가 보낸 것인지 한 줄씩.
4. **오류 해결 기록** — 만들면서 겪은 오류 한 개 이상. 빨간 오류 메시지 원문(또는 앱이 멈춘 증상과 Logcat 줄), 원인, 고친 방법.
5. **확인 환경과 알려진 한계** — 에뮬레이터 API 또는 실기기 Android 버전, 확인한 방법(Fake/실보드), 알고 있는 한계(예: 받는 중 회전하면 이력이 빈다, 실보드는 입력 이벤트가 없다), 발표·연습 중 장애가 있었다면 그 기록.

13주차 계획안에 적은 계획과 최종 결과가 달라졌으면 5절에 **무엇을 왜 바꿨는지** 한두 줄 적는다. 계획이 바뀐 것 자체로는 깎지 않는다.
생성형 AI에게 받은 코드를 그대로 넣었다면 그 부분을 레포트에 밝힌다. 코드 설명 질문은 내가 제출한 코드로 한다.

## 학생 범위와 안전

- 학생은 **Android 앱만** 만든다. 보드 펌웨어를 고치거나 올리지 않고, 회로를 바꾸지 않는다. 강의자 전용 명령(`config`·`reboot` 등)은 보내지 않는다.
- 실보드에는 LED 번호 `0`~`3`과 `-1`만 보낸다. 보드는 번호 범위를 검사하지 않는다.
- 보드 하나에 폰 하나다. 발표 전에 내 보드의 칩 ID 라벨을 확인하고, 다른 사람 발표 중에는 보드에 연결하지 않는다.
- 보드가 이상하면 강의자에게 교환을 요청한다. 학생이 복구하지 않는다.
- 캡처와 사진에 계정 이름·알림 내용 같은 개인정보가 보이지 않게 한다.

- [ ] 계획안 1쪽에 다섯 가지(앱 소개·화면과 기능·보드 명령·남은 2주 일정·막힐 곳과 대비책)가 모두 있다.

- [ ] 레포트 2절 표의 캡처 일곱 칸과 코드 위치가 제출한 소스의 줄 번호와 같다.
- [ ] 시연 절차대로 2~3분 안에 끝나는 것을 재 보았다(실보드면 보드가 다시 켜지는 시간까지).

- [ ] 소스 압축 파일에 `settings.gradle.kts`와 `app/build.gradle.kts`가 들어 있고, `build/`·`.gradle/`·`.idea/`·`local.properties`는 빠져 있다.

- [ ] 캡처에 계정·알림 내용 같은 개인정보가 보이지 않는다.
