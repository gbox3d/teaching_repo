# 2주차 실습 — 깨지지 않는 mock 장치 제어판

## 공통 규칙

- XML을 작성하기 전에 View tree와 폭·높이 정책을 예측한다.
- 실제 BLE·ESP32-C3 대신 코드 내부의 mock 상태만 사용한다.
- 한 번에 layout 조건 하나만 바꾸고 전후를 기록한다.
- 고정 픽셀 좌표, 사용자 표시 문자열 하드코딩, 색만으로 상태 전달을 피한다.

## 1일차 실습 — View tree와 단일 render 만들기 (60분)

### 상황과 문제

`Device Info` 화면을 장치 제어판으로 확장해야 한다. 화면에는 앱 제목, 긴 장치 이름, 연결 상태, 연결 동작, 디지털 출력 동작이 있어야 하며 아직 장치가 연결되지 않았을 때 출력 버튼을 누를 수 없어야 한다.

### 시간 배분

| 단계 | 구간 | 시간 | 활동 |
|---|---:|---:|---|
| 구조 예측 | 0–8분 | 8분 | View tree와 크기 정책 작성 |
| resource 준비 | 8–18분 | 10분 | 문자열·간격 resource 작성 |
| XML 구현 | 18–35분 | 17분 | constraint 기반 화면 구성 |
| 상태 render | 35–48분 | 13분 | 두 mock 상태와 이벤트 연결 |
| 실패 재현·복구 | 48–56분 | 8분 | 긴 이름·고정 폭 문제 확인 |
| 검증·기록 | 56–60분 | 4분 | 체크리스트와 화면 증거 |
| **합계** |  | **60분** |  |

### 1. 구현 전 예측

다음 표를 먼저 작성한다.

| View | width 정책 | height 정책 | 기준 위치 | 상태에 따른 변화 |
|---|---|---|---|---|
| title |  |  |  | 없음 |
| deviceName |  |  |  | 없음 |
| connectionStatus |  |  |  | text |
| connectButton |  |  |  | text |
| outputButton |  |  |  | enabled |

두 상태의 예상도 고정한다.

| 상태 | 상태 문구 | 연결 버튼 | 출력 버튼 |
|---|---|---|---|
| `DISCONNECTED` |  |  |  |
| `READY` |  |  |  |

### 2. resource와 XML 구현

요구사항:

1. 사용자에게 보이는 문구는 `strings.xml`에서 참조한다.
2. 화면 바깥 간격은 `dimens.xml`의 `screen_padding`을 사용한다.
3. 장치명과 상태 문구는 부모 start/end에 연결하고 폭을 관계로 결정한다.
4. 버튼 ID는 역할을 드러내는 이름으로 만든다.
5. 작은 화면에서 내용이 길어질 수 있음을 고려한다.

View tree를 XML과 비교하고 빠진 연결을 표시한다.

### 3. mock 상태와 `render()`

```kotlin
enum class MockConnection { DISCONNECTED, READY }
```

- 최초 상태는 `DISCONNECTED`다.
- 연결 버튼을 누르면 두 상태를 전환한다.
- `render()` 한 곳에서 상태 문구, 연결 버튼 text, 출력 버튼 enabled를 모두 갱신한다.
- 출력 버튼은 `READY`에서만 mock 출력 문구를 바꾼다.

### 4. 예측한 실패 재현

장치 이름 TextView의 폭을 잠시 고정값으로 만들고 다음 긴 가짜 이름을 표시한다.

```text
DEMO-LAB-SMART-IO-CONTROLLER-DEVICE-WITH-A-LONG-NAME
```

제로 폭, 겹침, 잘림 중 나타난 증상을 기록한다. 그런 다음 start/end constraint와 `0dp` 또는 적절한 `wrap_content` 정책으로 최소 수정한다.

### 5. 정상·경계·실패 확인

- **정상:** `DISCONNECTED`와 `READY`의 세 UI 요소가 상태표와 일치한다.
- **경계:** 긴 가짜 장치명에서도 연결 상태와 두 버튼에 접근할 수 있다.
- **실패:** 고정 폭 버전의 문제를 재현했고 최소 수정 후 같은 입력으로 재검증했다.
- **이벤트:** `DISCONNECTED`에서 출력 버튼이 비활성이고 클릭 결과가 생기지 않는다.

### 단계별 힌트

<details>
<summary>힌트 1 — constraint 경고가 남는다</summary>

선택한 View가 수평 축과 수직 축에서 각각 어디에 연결되는지 문장으로 읽는다. 미리보기의 위치를 드래그한 것만으로는 실행 constraint가 생기지 않을 수 있다.
</details>

<details>
<summary>힌트 2 — 상태 전환 뒤 일부만 바뀐다</summary>

listener에서 View를 각각 바꾸지 말고 상태 변수만 바꾼 뒤 항상 `render(state)`를 호출한다.
</details>

<details>
<summary>힌트 3 — `0dp` 뒤 View가 사라진다</summary>

ConstraintLayout에서 폭 `0dp`를 쓰려면 start와 end constraint가 모두 있어야 남은 공간을 계산할 수 있다.
</details>

### 확장

출력 상태 `OFF`/`ON`을 별도 enum으로 추가한다. 단, 연결이 끊길 때 출력 UI가 어떤 정책으로 바뀌어야 하는지 상태표를 먼저 확장한 뒤 구현한다.

## 2일차 실습 — 방향·글꼴·접근성 검증 (60분)

### 상황과 문제

기준 제어판은 기본 세로 화면에서만 확인되었다. 가로 화면, 큰 글꼴, 긴 장치명에서도 핵심 정보와 동작을 잃지 않고, 색을 보지 않아도 연결 상태를 알 수 있도록 개선하라.

### 시간 배분

| 단계 | 구간 | 시간 | 활동 |
|---|---:|---:|---|
| 조건 예측 | 0–8분 | 8분 | 검증 매트릭스와 예상 실패 작성 |
| 회전·폭 검증 | 8–20분 | 12분 | 세로/가로 비교와 간격 resource |
| 큰 글꼴 검증 | 20–34분 | 14분 | 글자 잘림·겹침 수정 |
| 접근성 점검 | 34–48분 | 14분 | label·상태·enabled·읽기 순서 |
| 실패 복구 | 48–56분 | 8분 | 색 전용/고정 높이 문제 수정 |
| 검증·회고 | 56–60분 | 4분 | 매트릭스와 증거 정리 |
| **합계** |  | **60분** |  |

### 1. 조건별 결과 예측

| 방향 | 글꼴 | 장치명 | 예상 위험 | 실제 | 수정 |
|---|---|---|---|---|---|
| 세로 | 기본 | 짧음 |  |  |  |
| 가로 | 기본 | 김 |  |  |  |
| 세로 | 크게 | 김 |  |  |  |
| 가로 | 크게 | 김 |  |  |  |

### 2. 방향과 resource qualifier

1. 세로에서 기준 화면을 기록한다.
2. `READY`로 전환한 뒤 가로로 회전하고 상태와 layout을 관찰한다.
3. 이번 주에는 상태 초기화를 억지로 고치지 말고 3주차 질문으로 남긴다.
4. 가로에서 바깥 간격만 달라야 한다면 `values-land/dimens.xml`에서 같은 resource 이름의 값을 제공한다.
5. 공통 XML을 복사하기 전에 값 분기로 충분한지 설명한다.

### 3. 큰 글꼴과 긴 문자열

- 에뮬레이터/기기의 글꼴 크기를 강의자 안내 수준으로 키운다.
- 긴 가짜 장치명을 넣는다.
- 핵심 상태 문구와 버튼 label이 잘리거나 겹치는지 확인한다.
- 고정 높이, 불필요한 single-line 제한, 부족한 constraint를 최소 수정한다.
- 실습 후 기기 글꼴 설정을 원래 값으로 복구한다.

### 4. 접근성 점검

| 점검 | 합격 조건 | 결과 |
|---|---|---|
| 상태 의미 | 색 없이 상태 문구로 구분 |  |
| 버튼 동작 | text만 읽어도 행동을 예측 |  |
| 비활성 이유 | 연결 필요라는 문맥 제공 |  |
| 큰 글꼴 | 핵심 정보와 동작 유지 |  |
| 읽기 순서 | 제목→장치→상태→동작이 자연스러움 |  |

아이콘을 추가했다면 장식인지 기능인지 결정한다. 기능 아이콘은 의미 있는 설명을, 장식 요소는 중복 낭독을 만들지 않는 정책을 적용한다.

### 5. 정상·경계·실패 확인

- **정상:** 세로·기본 글꼴·짧은 이름에서 상태표와 일치한다.
- **경계:** 가로·큰 글꼴·긴 이름에서도 상태와 두 핵심 동작을 확인할 수 있다.
- **실패:** 상태를 색만으로 표현하거나 TextView 높이를 작게 고정해 문제를 재현한 뒤 문구/크기 정책으로 복구한다.
- **회전:** 상태가 초기화되었다면 호출·상태 보존 문제로 분류하고 3주차 질문으로 남긴다.

### 단계별 힌트

<details>
<summary>힌트 1 — 가로 전용 layout을 복사해야 할지 모르겠다</summary>

구조가 같은지 먼저 본다. 간격만 다르면 `values-land/dimens.xml`처럼 값만 분기하는 편이 두 구조의 불일치를 줄인다.
</details>

<details>
<summary>힌트 2 — 큰 글꼴에서 아래 버튼이 보이지 않는다</summary>

고정 높이를 제거하고 내용이 화면보다 길 수 있는지 판단한다. 필요하면 하나의 세로 콘텐츠를 `ScrollView` 안에 두되 직접 자식 규칙을 확인한다.
</details>

<details>
<summary>힌트 3 — 접근성 점검 결과를 어떻게 쓰는지 모르겠다</summary>

“색을 제거하면 Ready를 알 수 없음 → `제어 준비` 텍스트 추가 → 색 없이 상태를 식별함”처럼 조건, 문제, 수정, 재검증을 한 줄로 쓴다.
</details>

### 확장

상태 TextView에 live region을 적용할 필요가 있는지 검토하고, 자주 변하는 값이 과도한 안내를 만들 수 있는 trade-off를 3문장으로 적는다. 실제 적용 여부는 근거와 함께 선택한다.
