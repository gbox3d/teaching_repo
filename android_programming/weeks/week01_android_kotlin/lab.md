# 1주차 실습 — 실행 증거와 Device Info

## 공통 규칙

- 코드를 옮기기 전에 결과를 먼저 예측한다.
- 강의자가 제공한 개인 실습 프로젝트에서만 수정한다.
- 한 번에 한 원인만 바꾸고 정상 기준선으로 복구한다.
- 화면 캡처에 계정, 알림 내용, 전화번호, 단말 고유 ID가 보이지 않게 한다.
- ESP32-C3 펌웨어 코딩·빌드·플래싱은 이번 실습 및 학생 범위가 아니다.

## 1일차 실습 — 앱 실행 경로를 증거로 설명하기 (60분)

### 상황과 문제

팀원이 “Run을 눌렀는데 앱이 보이니 설정은 모두 끝났다”고 말한다. 기준 프로젝트의 시작 경로를 추적하고, 정상 실행 증거를 만든 뒤 안전한 오류 하나를 재현·복구해 이 판단이 충분한지 설명하라.

### 시간 배분

| 단계 | 구간 | 시간 | 활동 |
|---|---:|---:|---|
| 문제·예측 | 0–8분 | 8분 | 시작 파일과 예상 로그 작성 |
| 기준선 실행 | 8–20분 | 12분 | 대상·화면·Logcat 증거 확보 |
| 프로젝트 지도 | 20–34분 | 14분 | 핵심 경로와 참조 연결 추적 |
| 실패 재현·진단 | 34–48분 | 14분 | resource 오류 한 개 재현·복구 |
| 경계 확인 | 48–56분 | 8분 | 회전·재실행 관찰 |
| 검증·회고 | 56–60분 | 4분 | 체크리스트 제출 준비 |
| **합계** |  | **60분** |  |

### 2. 정상 기준선 만들기

1. 실행 대상 이름을 기록하고 앱을 실행한다.
2. `MainActivity.kt`의 `onCreate()`에 고유 태그 로그를 한 줄 추가한다.
3. Logcat을 실행 앱 프로세스와 태그로 필터링한다.
4. 화면 제목, 대상 이름, 로그 한 줄을 증거로 기록한다.
5. 다음 경로의 역할과 연결 화살표를 작성한다.

```text
AndroidManifest.xml → MainActivity.kt → activity_main.xml → strings.xml
```

완료 조건:

- [ ] 실행 대상이 명확하다.
- [ ] 화면과 Logcat 증거가 모두 있다.
- [ ] 네 경로의 역할을 서로 바꾸지 않고 설명한다.

### 3. 실패 하나만 재현하고 복구하기

강의자 복사본에서 `setContentView(R.layout.activity_main)`의 resource 이름을 존재하지 않는 이름으로 잠시 바꾼다.

1. 실행 전 어느 단계에서 실패할지 적는다.
2. Build를 수행하고 첫 관련 오류의 파일·줄·핵심 문구를 기록한다.
3. 에뮬레이터 문제인지 코드/자원 참조 문제인지 판정한다.
4. 바꾼 한 곳만 원복한다.
5. 다시 빌드·실행해 기존 화면과 로그가 돌아왔는지 확인한다.

### 4. 정상·경계·실패 확인

- **정상:** 선택한 대상에서 첫 화면과 `DeviceInfo` 로그가 보인다.
- **경계:** 화면을 한 번 회전하거나 Activity를 재시작했을 때 로그 호출 횟수를 기록한다.
- **실패:** 없는 layout resource 참조가 빌드에서 검출되고, 원복 후 다시 실행된다.

### 단계별 힌트

<details>
<summary>힌트 1 — Run 대상이 없다</summary>

Device Manager에서 에뮬레이터가 부팅되었는지 확인한다. 실기기라면 강의자 안내에 따라 USB 연결과 디버깅 허용 상태만 확인한다. 임의 드라이버나 계정을 설치하지 않는다.
</details>

<details>

현재 실행 앱의 process를 선택하고 코드에 쓴 고유 태그 `DeviceInfo`로 검색한다. 메시지 전체보다 태그 철자를 먼저 비교한다.
</details>

<details>
<summary>힌트 3 — 오류 원인을 모르겠다</summary>

Build Output에서 자신의 `MainActivity.kt` 파일과 줄 번호가 나온 첫 항목을 찾고 `R.layout` 뒤 이름이 실제 파일명과 같은지 비교한다.
</details>

### 확장

Logcat에 `BuildConfig`의 디버그 여부처럼 개인 식별이 아닌 실행 조건 하나를 추가하고, 이 정보가 진단에 언제 유용한지 한 문장으로 적는다.

## 2일차 실습 — Kotlin으로 안전한 Device Info 만들기 (60분)

### 상황과 문제

장치 제어 앱의 진단 화면에는 제조사, 모델, 플랫폼 API 수준과 새로고침 횟수가 필요하다. 일부 문자열이 `null` 또는 공백이어도 앱이 종료되거나 빈 문구를 보여서는 안 된다.

### 시간 배분

| 단계 | 구간 | 시간 | 활동 |
|---|---:|---:|---|
| 문제·예측 | 0–8분 | 8분 | 네 입력과 클릭 결과 예측 |
| Kotlin 모델 | 8–20분 | 12분 | 데이터 클래스, 정규화 함수와 format resource 작성 |
| XML 연결 | 20–35분 | 15분 | 정보 TextView와 버튼 연결 |
| 경계·실패 입력 | 35–48분 | 13분 | 정상·공백·null 검증 |
| 변형·설명 | 48–56분 | 8분 | 문구/로그 일치와 코드 설명 |
| 검증·제출 | 56–60분 | 4분 | 완료 증거 정리 |
| **합계** |  | **60분** |  |

### 1. 코드 작성 전 예측

```kotlin
fun normalizeBuildValue(raw: String?, unknownSentinel: String): String? =
    raw?.trim()?.takeIf {
        it.isNotEmpty() && !it.equals(unknownSentinel, ignoreCase = true)
    }
```

| 입력 | 예상 결과 | 실제 결과 | 일치 여부 |
|---|---|---|---|
| `" Pixel "` |  |  |  |
| `"   "` |  |  |  |
| `null` |  |  |  |
| `"unknown"` |  |  |  |

버튼을 0회, 1회, 3회 눌렀을 때 화면과 로그의 횟수도 먼저 적는다.

### 2. 데이터와 표시 format 구현

개인 프로젝트의 package에 맞춰 다음 역할을 구현한다.

```kotlin
data class DeviceSummary(
    val manufacturer: String,
    val model: String,
    val apiLevel: Int,
)
```

요구사항:

- 제조사와 모델은 `normalizeBuildValue(raw, Build.UNKNOWN)`를 거친 뒤, `null`일 때 `R.string.value_unknown`을 사용한다.
- 한 줄 요약은 `R.string.device_summary_format`과 `getString(...)`으로 만든다.
- 원본 데이터 프로퍼티는 `val`이다.
- 고유 단말 ID, 계정, 전화번호는 읽지 않는다.

### 3. XML View와 이벤트 연결

1. 요약용 `TextView`, 새로고침 횟수용 `TextView`, 버튼을 XML에 둔다.
2. 문자열 기본값은 `strings.xml`에 둔다.
3. `onCreate()`에서 View를 찾고 최초 정보를 표시한다.
4. 버튼 클릭마다 `refreshCount`를 1 증가시키고 화면과 Logcat을 함께 갱신한다.
5. 화면 회전 후 횟수가 어떻게 되는지 관찰만 하고 이번 주에는 보존 해법을 넣지 않는다.

### 4. 정상·경계·실패 확인

- **정상:** 실제 제조사·모델·API 수준이 한 화면에 보인다.
- **경계:** 테스트 함수에서 공백·`null`·`"unknown"`이 `null`로 정규화되고, 화면 경계에서 resource의 `알 수 없음`으로 바뀐다.
- **실패:** `raw!!`를 사용한 별도 예측만 작성하고 제출 코드에는 사용하지 않는다. nullable 값을 강제 해제하면 어떤 예외 가능성이 있는지 설명한다.
- **상태:** 3회 클릭 뒤 화면 횟수와 Logcat의 마지막 횟수가 모두 3이다.

### 단계별 힌트

<details>
<summary>힌트 1 — resource ID를 찾지 못한다</summary>

XML의 `android:id="@+id/..."` 이름과 Kotlin의 `R.id...` 철자를 비교한 뒤 프로젝트를 다시 빌드한다.
</details>

<details>
<summary>힌트 2 — 공백이 그대로 표시된다</summary>

null 확인만으로는 공백과 `Build.UNKNOWN` sentinel을 거르지 못한다. `trim()`과 두 조건을 적용하는 순서를 추적한다.
</details>

<details>
<summary>힌트 3 — 클릭 횟수와 로그가 다르다</summary>

증가, 화면 갱신, 로그 출력에 서로 다른 변수를 쓰지 않았는지 확인한다. 클릭 리스너 안에서 증가 후 같은 값을 사용한다.
</details>

### 확장

`device_summary_multiline` format resource를 추가해 같은 `DeviceSummary`를 여러 줄로 표시하고, 원본 데이터와 화면 format의 책임 차이를 설명한다.
