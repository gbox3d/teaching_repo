# 기말 개인 실기 Blueprint — 공개판

## 목적

학기 프로젝트의 화려함을 다시 평가하지 않고, 학생 개인이 제한 시간 안에 Android starter를 읽고 최소 변경을 구현·검증·설명하는 역량을 확인한다.

## 공개 평가 구조

| 영역 | 점수 |
|---|---:|
| 구현 | 15 |
| 시연 | 5 |
| **합계** | **20** |

세부 배점은 [rubric.md](rubric.md)를 따른다.

## 공개 범위

- Kotlin과 XML View의 event/render 관계
- Activity/Fragment lifecycle과 상태 보존
- coroutine/Flow와 lifecycle-aware 수집
- Service, BroadcastReceiver, ContentProvider 중 수업에서 다룬 component/data 경계
- 버전 인식 권한과 사용자 복구 UX
- 제공 BLE abstraction, fake transport, 연결 상태 기계
- 출력 요청, 입력 관찰, disconnect/timeout 등 상태·오류 범주
- 정상·경계·실패 검증과 개인 코드 설명

위 주제 예시가 한 시험 prompt에서 각각 독립 과제로 같은 작업량을 차지한다는 뜻은 아니다. 그러나 실제 prompt는 rubric의 다섯 구현 평가 차원인 `요구·UI 상태`, `lifecycle·비동기·component`, `BLE abstraction·상태 기계`, `validation·실패·검증`, `코드·제출 무결성`을 **모두** 평가할 수 있는 식별 가능한 과업과 증거 지점을 제공한다. 구체 과업과 한 과업 안에서 차원이 결합되는 비중만 달라질 수 있으며, 공개된 `3 + 3 + 4 + 3 + 2 = 15점` 중 어느 차원도 `N/A`로 두거나 재배점하지 않는다.

## 2일 운영

| 일차 | 안내 | 개인 실기 | 공개 목적 |
|---|---:|---:|---|
| 1일차 | 30분 | 60분 | 요구 분석, 정상 경로, 중간 저장 |
| 2일차 | 30분 | 60분 | 실패·복구, 최종 검증, 제출·시연 |

분반 인원에 따른 시연 순서는 별도 공지하되 모든 학생에게 같은 구현 시간과 개인 설명 기회를 보장한다.

### DEMO_CAPACITY_TBD

개강 전에 `N=분반 인원`, `E=동시에 평가 가능한 평가자 수`, `D=학생당 시연 분`을 확정한다.

```text
T_demo = ceil(N / E) × D
수업 블록 내 운영 조건: T_demo ≤ 60분
```

조건을 만족하지 않으면 `E`를 늘려 병렬 평가하거나 모든 학생에게 동일한 별도 공식 시연 슬롯을 사전 공지한다. 대기 순서 때문에 일부 학생의 `D`나 실기시간을 줄이는 방식은 허용하지 않는다. 최종 값과 운영안은 실제 문제와 분리된 공식 시험 공지에서 고정한다.

## 공개 starter 역할

```text
starter/
├─ README.md                 # 실행·허용 수정·제출 계약
├─ app/src/main/res/layout/  # XML View contract
├─ ui/                       # event, render, UiState
├─ domain-or-component/      # 시험 당일 지정 경계
└─ transport/                # 제공 fake/BLE abstraction 경계
```

위는 역할 지도이며 실제 패키지명·파일·TODO는 시험 배포본에서 확정한다.

## 문제 설계 원칙

- 현재 실행 가능한 기준점과 명확한 수정 범위를 제공한다.
- 요구는 관찰 가능한 입력·출력·상태·오류·완료 증거로 작성한다.
- firmware 코딩·빌드·플래싱 능력을 요구하지 않는다.
- 실물 장치만으로 결과가 좌우되지 않도록 제공 fake 경로 또는 공지된 대체 절차를 둔다.
- 도구/SDK 정확한 버전은 시험 전 검증된 inventory에서 고정한다.
- 실제 prompt와 정답은 이 공개 폴더에 두지 않는다.

## 시연 구조

- 제출본 실행과 요구된 정상/실패 검증
- event → state → UI 또는 component/transport 흐름 설명
- 관찰된 오류의 마지막 성공 지점과 다음 진단 설명
- 공지된 범위의 짧은 후속 질문 또는 현장 진단

## 공정성·장애 원칙

- 전체 환경 장애는 감독이 시각과 영향을 기록하고 공지된 기준으로 처리한다.
- 개인 PC·보드·제출 장애는 즉시 신고하고 승인된 예비 절차를 따른다.
- 학생이 장비 문제를 해결하기 위해 firmware를 변경하지 않는다.
- 접근성 조정과 추가 시간은 승인된 학사 절차와 사전 공지를 따른다.
- 실제 학생 이름·학번·코드·점수는 공개 blueprint에 기록하지 않는다.

## 비공개 운영 자료 경계

이 blueprint는 다음을 생성하거나 보관하는 장소가 아니다.

- 실제 문제 문장과 데이터
- 정답 구현
- 비공개 평가 사례
- 학생별 변형·배정 정보
- 감독 내부 메모와 학생 성적
