# 기말고사 채점표 — 20점 (구현 15 + 시연 5)

본시험 채점과 1일차 리허설 자기 채점에 같은 표를 쓴다.
**구현 15점**은 제출한 두 파일(`MainActivity.kt`, `ControlActivity.kt`)을 배포 starter에 넣어, 채점 PC의 에뮬레이터(API 33 이상)에서 가짜 클라이언트(`useFake = true`)로 실행해 보고 매긴다.
**시연 5점**은 2일차 본시험 5–55분에 좌석 순서대로 실보드 앞에서 본다.

코드 모양이 교재와 달라도 요구한 동작이 보이면 점수를 준다. "코드 확인"이라고 적은 기준만 코드를 읽어 본다.
아래 기준의 문구와 숫자(`권한 OK`, `허용되지 않는 번호`, 10초 등)는 리허설 것이다. 본시험은 **문항지의 문구와 숫자로 바꿔 읽는다.**

## 구현 세부 기준 (15)

기준마다 1점이다. 기록할 때는 기준 번호(U1, S2 …)를 쓴다.
S1·S2·P3은 학생이 새로 쓴 코드가 아니라, starter에 완성되어 있던 기능이 제출본에서도 그대로 동작하는지 보는 기준이다. starter를 그대로 내면 S1·S2·P3만 받는다.

### UI·이벤트 (3)

| 번호 | 기준 | 점수 |
|---|---|---:|
| U1 | `준비됨` 제어 화면에서 LED 번호 칸이 빈 채로 Switch를 누르면 `LED 번호를 입력하세요` Toast가 뜨고, 명령을 보내지 않으며, 앱이 멈추지 않는다 | 1 |
| U2 | 명령을 보낸 직후 LED Switch·[전체 끄기]가 잠깐(약 0.3초) 회색이 되었다가 다시 켜진다 | 1 |
| U3 | 요구한 Toast·창·상태 글자가 문항 문구와 같다(한 곳이라도 다르면 0) | 1 |

### 상태 보존·StateFlow (3)

| 번호 | 기준 | 점수 |
|---|---|---:|
| S1 | 목록 줄을 누르면 연결 화면 상태 글자가 `연결 중` → `서비스 확인 중` → `준비됨`으로 바뀌고, `준비됨`일 때만 [해제]·[제어 화면]이 켜진다 | 1 |
| S2 | `준비됨`에서 회전해도 상태 글자와 버튼이 그대로이고, 제어 화면의 LED Switch·[전체 끄기]는 `준비됨`일 때만 켜진다 | 1 |
| S3 | 연결 중에 회전해도 시간 제한이 다시 걸린다(채점 사본: 목록 줄을 누르고 곧바로 회전 → 약 1초 뒤 시간 초과 안내) | 1 |

### 코루틴 timeout·취소·오류 (3)

| 번호 | 기준 | 점수 |
|---|---|---:|
| C1 | 채점 사본(제한 시간 숫자만 1000으로 바꿈)에서 목록 줄을 누르면 약 1초 뒤 상태 글자가 바뀌고 연결이 끊긴다(Logcat `tag:BLE`에 `disconnect(가짜) → 연결 안 됨`). `연결 시간이 초과되었습니다` Toast는 먼저 뜬 `선택: …` Toast가 사라진 뒤 뜨므로, 줄을 누르고 3초 안에 뜨는지 본다 | 1 |
| C2 | C1을 받은 제출본을 그대로 실행해 목록 줄을 누르면 `준비됨`이 되고, 제한 시간이 지나도 안내가 뜨지 않으며 `준비됨`이 그대로다 | 1 |
| C3 | 코드 확인: 시간 제한 코루틴을 `Job` 변수에 보관하고, 새로 걸기 전에 앞 것을 `?.cancel()`로 취소한다. `delay`는 `launch { }` 안에서 도는 코드(또는 거기서 부르는 `suspend fun`)에 있다 | 1 |

### 권한·SharedPreferences (3)

| 번호 | 기준 | 점수 |
|---|---|---:|
| P1 | 권한이 모두 허용된 상태에서 [권한 확인] → 요청 창 없이 `권한 OK`. 권한을 끈 상태에서 [권한 확인] → 요청 창 → 허용 → `권한 OK`. 둘 다 맞아야 1점 | 1 |
| P2 | 요청 창에서 거절하면 `권한이 필요합니다` 창이 뜨고, [설정으로]가 이 앱(Smart I/O Controller)의 정보 화면을 연다 | 1 |
| P3 | 장치 이름을 넣고 [연결]한 뒤 앱을 완전히 껐다 켜도 `마지막 장치: …`가 보인다(starter에 있던 저장·복원이 제출본에서도 동작) | 1 |

### `send`·`onMessage`·재연결 (3)

| 번호 | 기준 | 점수 |
|---|---|---:|
| M1 | `준비됨` 제어 화면에서 `3` → Switch 켜기·끄기로 `on 3`·`off 3`이 명령 로그에 한 줄씩 쌓이고, Logcat `writeCharacteristic(가짜)`의 글자가 같다 | 1 |
| M2 | 약 0.3초 뒤 `응답: {"result":"ok","ms":"led(s) on"}`이 초록 글자로 쌓인다. 코드 확인: 결과가 `ok`가 아니면 빨간 글자와 문항이 정한 알림(리허설은 AlertDialog)으로 알리는 가지가 있다 | 1 |
| M3 | `9` → Switch는 `허용되지 않는 번호` Toast만 뜨고 보내지 않는다(명령 로그·Logcat에 새 줄 없음). 그리고 연결 화면 [끊김 시험] → [재연결]로 다시 `준비됨`이 된다. 둘 다 맞아야 1점 | 1 |

## 시연 세부 기준 (5)

시연은 Android 실기기와 실보드로 한다. 2일차 설명 시간에 기기에 설치해 둔 내 `SmartIO` 앱(`useFake = false`)을 쓴다. 리허설 TODO(1)·(2)를 끝내지 못했으면 설치 전에 두 파일을 허용 자료인 `rehearsal_solution`으로 바꿔 둔다([따라하기 17단계](walkthrough.md#17-실기기와-내-보드-점검)).
보드·기기 장애가 강의자 확인으로 장애 기록지에 적히면, 에뮬레이터의 Fake 앱으로 같은 기준을 본다(LED 대신 명령 로그와 Logcat `tag:BLE`).

### 출력 제어 (2)

| 번호 | 기준 | 점수 |
|---|---|---:|
| O1 | 앱에서 명령을 보내 보드의 LED를 켠다(LED Switch 또는 `LED 0 밝기` 막대) | 1 |
| O2 | LED를 끄고(Switch 끄기 또는 [전체 끄기]), 명령 로그에서 보낸 명령과 그 응답 줄(`응답: …`)을 가리킨다. 응답 줄이 붙지 않는 앱(응답 가지가 빈 앱)이면 LED가 꺼져도 0점이다 | 1 |

### 입력 수신 (2)

| 번호 | 기준 | 점수 |
|---|---|---:|
| I1 | [온습도 받기 시작]으로 입력 이력에 `시:분:초 [온도,습도]` 줄이 2줄 이상 쌓인다 | 1 |
| I2 | [중지]를 누르면 새 줄이 더 쌓이지 않는다(평가자가 3초 넘게 지켜본다). Fake로 대신 볼 때는 `[온도,습도]` 줄만 본다. 가짜 보드가 10초마다 보내는 `시:분:초 입력=N` 줄은 [중지]와 상관없이 쌓인다 | 1 |

### 구술 (1)

| 번호 | 기준 | 점수 |
|---|---|---:|
| T1 | 평가자가 본시험 프로젝트 코드에서 가리킨 콜백 한 개가 **언제 불리는지** 한 문장으로 맞게 말한다 | 1 |

- 질문은 한 문항이고 모양은 "이 콜백은 언제 불리나" 하나다. 대상은 starter에 있는 콜백이다: `permissionLauncher`의 `{ _ -> }`, `bluetoothLauncher`의 `{ result -> }`, `startScan`의 `onFound = { device -> }`·`onFinished = { }`, `client.connectionState.collect { state -> }`, `setOnClickListener { }`·`setOnCheckedChangeListener { _, isChecked -> }`·`setOnItemClickListener { _, _, position, _ -> }`, `onStart()`·`onStop()`, `onMessage { json -> }`, `batteryReceiver`의 `onReceive`. 이 목록 밖에서는 묻지 않는다.
- 사용자가 무엇을 했을 때, 또는 무슨 일이 일어났을 때(때와 조건)를 말하면 맞다. 코드 줄을 소리 내어 읽기만 하면 0점이다. 부분 점수는 없다.

## 기본점수 5점 — 구현 시도 흔적 (운영 메모)

- **규칙**: 구현 점수(15점 만점)가 5점보다 낮아도, 문항 세 기능 가운데 **하나 이상의 TODO 자리에 요구와 관련된 코드를 쓴 흔적**이 있으면 구현 점수를 **5점**으로 한다. 빌드가 되지 않는 제출도 같다. 구현 점수가 5점 이상이면 그 점수 그대로다.
- 시연 5점에는 적용하지 않는다. 시연은 시연 기준으로만 매긴다.
- **흔적으로 본다**: TODO 자리에 요구 문장과 관련된 호출·조건문·변수를 쓴 것. 예: `checkSelfPermission`, `AlertDialog.Builder`, `permissionLauncher.launch`, `send(…)`, `listOf(…).contains(…)`, `append`, `connectTimeoutJob`, `delay`. 빨간 줄이 남았거나 끝까지 쓰지 못했어도 흔적이다.
- **흔적으로 보지 않는다**: starter를 바꾸지 않고 낸 것, TODO 주석만 지우거나 옮긴 것, 요구와 관계없는 줄(빈 `Log.d`, 관계없는 함수 복사)만 넣은 것, 다른 프로젝트의 파일을 낸 것.
- **판정**: 채점자 한 명이 흔적 줄(파일·행)을 기록 양식에 적고, 다른 채점자 한 명이 확인한다. 둘의 판단이 다르면 강의자가 정한다.
- **공지**: 1일차 채점표 공개 때와 시험 공지에 같은 문장으로 알린다. 빌드되지 않는 제출이 늘지 않도록 "모르는 곳은 비워 둔 채 빌드되게 둔다"를 함께 말한다.

## 채점 원칙

- **한 원인은 한 번만** 뺀다. 예: 빈 칸 검사보다 `toInt()`를 먼저 해 빈 칸에서 앱이 멈추면 U1에서만 빼고, 번호를 넣은 뒤의 전송·응답(M1·M2)은 따로 본다.
- 제출본의 제한 시간이 이미 짧은 숫자(예: 1000)로 남아 있으면 C2에서만 빼고, 나머지 기준은 채점자가 문항 숫자로 되돌린 사본으로 본다.
- 동작으로 판단한다. 코드 길이·주석·변수 이름은 점수와 관계없다.
- starter에 완성되어 있던 기능(연결 상태 표시, 마지막 장치, [재연결] 등)도 제출본에서 동작해야 그 기준 점수를 준다.
- 권한 기준(P1·P2)은 권한을 끈 상태와 허용한 상태를 모두 본다. 채점 기기의 설정 › 앱 › Smart I/O Controller › 권한에서 바꾼다.
- 제출 파일의 `useFake`가 `false`이면 채점자가 `true`로 바꿔 실행한다(감점 없음).
- 장애 기록지에 적힌 장비·제출 문제와 학생 코드의 문제를 구분해 기록한다. 각 항목 점수는 그 항목 배점을 넘지 않는다.

## 채점 순서(채점자) — 구현

1. 배포 starter 프로젝트를 복사하고 제출한 `MainActivity.kt`·`ControlActivity.kt`로 바꾼다. `useFake = true`인지 본다.
2. Run ▶. 빌드가 실패하면 첫 `e:` 줄을 기록하고 [기본점수](#기본점수-5점--구현-시도-흔적-운영-메모) 판정으로 간다.
3. 채점 기기의 설정 › 앱 › Smart I/O Controller › 권한 › 근처 기기를 `허용`으로 바꿨다가 `허용 안함`으로 끄고 시작한다 → [권한 확인] → 요청 창에서 허용 → `권한 OK` → 다시 [권한 확인] → 요청 창 없이 `권한 OK`(P1) → 설정에서 근처 기기를 다시 `허용 안함`으로 끈다 → [권한 확인] → 요청 창에서 거절 → `권한이 필요합니다` 창과 [설정으로] 확인(P2). 설정에서 끈 뒤 요청 창에서 한 번 거절하면 다음부터 요청 창이 뜨지 않는다(Android 14 에뮬레이터에서 확인). 그래서 허용(P1)을 먼저 보고, 시작할 때도 `허용`을 거쳐 끈다.
4. [검색] → `ESP32_BLE_FAKE1` 줄 탭 → 상태 글자·버튼(S1) → 제한 시간보다 오래 기다림(C2) → 회전(S2).
5. [제어 화면] → 빈 칸 Switch(U1) → `3` Switch 켜기·끄기(M1·M2·U2) → `9` Switch(M3 앞) → [뒤로] 전에 버튼 켜짐 확인(S2).
6. [뒤로] → [끊김 시험] → [재연결] → `준비됨`(M3 뒤).
7. 장치 이름 칸에 이름이 있는 채로 [연결] → [뒤로] → 앱을 완전히 닫고 다시 실행 → `마지막 장치: …`(P3).
8. 채점 사본에서 제한 시간 `delay` 숫자만 1000으로 바꿔 Run → 목록 줄 탭 → 약 1초 뒤 상태 글자·끊김, 3초 안에 Toast(C1) → 다시 [검색] → 줄 탭 직후 회전 → 약 1초 뒤 같은 상태 글자(S3).
9. 코드에서 C3·M2의 코드 확인 부분을 보고, 문항 문구와 화면 글자를 대조한다(U3).
10. 아래 기록 양식을 채운다.

## 시연 진행(평가자)

1. 좌석표 순서대로 자리에 가서 시작 시각을 적는다. 학생은 저장(Ctrl+S)하고 편집을 멈춘다.
2. ① 약 30초: 시연 기기 앱 → [검색] → 학생 보드 이름 줄 → `준비됨` → [제어 화면].
3. ② 약 1분: 출력 제어(O1·O2). ③ 약 1분: 입력 수신(I1·I2).
4. ④ 약 30초: 본시험 프로젝트 코드에서 콜백 한 개를 가리키고 "이 콜백은 언제 불리나"를 묻는다(T1). 평가자는 콜백 목록을 차례대로 돌려 쓰고, 같은 줄에 앉은 학생에게 같은 콜백을 연달아 묻지 않는다.
5. 끝난 시각을 적는다. 시연 구간은 본시험 5–55분이다. 시연 D분은 모든 학생이 똑같이 한 번 쓰므로 제출 마감은 모두 60분이다. 장비 장애나 평가자 사정으로 D분을 넘긴 몫만 장애 기록지에 적고, 60분 뒤 같은 자리에서 그만큼 이어서 한다. 순서가 밀려 55분까지 시연하지 못한 학생은 제출 뒤 같은 자리에서 시연한다.
6. 보드가 검색되지 않거나 파랑 깜빡임이 없으면 1분 안에 해결되지 않을 때 장애로 기록하고, 보드를 바꿔 차례를 뒤로 미루거나 Fake 시연으로 본다. 코드 도움은 주지 않는다.
