# 15주차

## 기말 개인 실기

읽기 → 예측 → 최소 구현 → 검증 → 개인 설명

---

# 공개 평가 구조

| 구분 | 점수 |
|---|---:|
| 구현 | 15 |
| 시연 | 5 |
| 합계 | 20 |

실제 문제·정답·학생별 값은 이 공개 자료에 없다.

# 1일차 — 요구 분석과 1차 구현

30분 설명·절차 시연

---

## 0–5분 — 시험 경계

- 개인 실기와 개인 설명
- 허용 자료·도구는 시험 공지 우선
- 제공 abstraction/starter만 사용
- firmware 코딩·빌드·플래싱은 평가 밖
- 실제 prompt는 감독 지시에 따라 시험 시간에 제공

---

## 5–10분 — starter 먼저 실행

```text
README / allowed scope
  → XML View contract
    → ViewModel / UiState
      → domain/component boundary
        → fake BLE transport
```

수정 전에 현재 실행 결과와 첫 로그를 기록한다.

---

## 10–15분 — 요구를 검증문으로 바꾸기

| 읽을 것 | 기록할 것 |
|---|---|
| 입력 | 어떤 event/사용자 행동인가 |
| 출력 | 어떤 UI/state가 보여야 하는가 |
| 정상 | 최소 성공 trace |
| 경계 | 0건·반복·전이 중 행동 |
| 실패 | 권한·timeout·disconnect 등 공개 범주 |

시험 당일 값과 구체 요구는 prompt를 따른다.

---

## 15–20분 — 전체 상태 기계 확인

```text
Idle → Scanning → Connecting → Discovering → Ready
          │            │             │          │
          └────────────┴─────────────┴──────────┤
                                                ▼
                                      Disconnected / Error
```

현재 요구가 어느 상태·사건·불변 조건을 바꾸는지 표시한다.

---

## 20–25분 — 최소 구현 순서

1. 현재 앱 실행·관찰
2. 요구를 체크리스트화
3. 한 정상 경로
4. validation·경계
5. 실패·복구
6. diff·재실행·commit

주변 구조를 전면 재작성하지 않는다.

---

## 25–30분 — 1일차 증거

- 요구 체크리스트
- 중간 실행 결과
- 첫 정상 trace
- 해결되지 않은 항목과 관찰 근거
- 중간 저장/commit

감독의 시작 신호 전에는 실제 prompt 작업을 시작하지 않는다.

---

<!-- _class: lead -->
# 2일차 — 실패 대응과 개인 시연

30분 설명·절차 시연

---

## 0–5분 — 제출 무결성

- 공지된 파일 범위만 제출
- 최종 source와 SHA 일치
- secret·기기 주소·개인정보 제거
- 제출 성공 화면 확인
- 마감 뒤 재작성하지 않음

실제 제출 채널·파일명은 LMS/시험 공지를 따른다.

---

## 5–10분 — 실패 검증

```text
예측
  → 실패 주입
    → 화면 + state + event log 관찰
      → 데이터/연결 불변 조건 확인
        → 사용자 복구
```

오류 문구 하나만으로 검증을 끝내지 않는다.

---

## 10–15분 — 시연 5점

| 항목 | 점수 |
|---|---:|
| 실행·검증 | 2 |
| 코드·상태 설명 | 2 |
| 현장 진단·후속 질문 | 1 |
| 합계 | 5 |

현재 코드를 따라 개인 언어로 답한다.

---

## 15–20분 — 막혔을 때 조사 순서

1. 첫 compile/runtime 오류
2. 현재 UiState와 LinkState
3. 마지막 성공 event
4. 입력과 실제 호출 인자
5. lifecycle·collector
6. fake scenario와 real 차이

증거로 범위를 줄인다.

---

## 20–25분 — 공정한 장애 처리

- 전체 환경 장애: 감독이 시작·종료 시각 기록
- 개인 PC 문제: 즉시 알리고 공지된 예비 절차 사용
- 실물 보드 문제: 강의자 확인 후 fake/교환 절차
- 제출 시스템 문제: 마감 전 source/SHA를 먼저 고정

학생이 임의로 firmware를 수정하지 않는다.

---

## 25–30분 — 최종 체크

1. 저장
2. 요구 체크
3. 정상·경계·실패 재실행
4. diff 확인
5. 최종 commit/SHA
6. 제출·성공 화면

시연 대상은 최종 제출본과 같아야 한다.

---

# 공개 자료의 한계

이 슬라이드는 시험 운영·범위·평가 구조만 설명한다.

- 실제 prompt 없음
- 정답 없음
- 비공개 채점 사례 없음
- 학생 데이터 없음
