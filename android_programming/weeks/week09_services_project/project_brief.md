# 9주차 1차 과제 안내 — 7주차까지 만든 앱으로 3분 발표

이 문서는 학생과 평가자가 함께 보는 공개 안내다. 제출 위치·마감·팀 운영처럼 분반마다 다를 수 있는 것은 수업 공지(LMS)가 이 문서보다 **우선**한다.
점수 기준은 [채점표](rubric.md)에 있다.

## 한눈에 보기

|---|---|

## 주제 — 둘 중 하나

### (a) SmartIO 시뮬레이터 + 본인 기능 1개

7주차까지 만든 `SmartIO`를 이어서 쓴다. 없으면 7주차 완성본(`examples/day2`)을 받아 시작한다.

```text
장치 이름 입력 → [검색] → 연결 중… 5 … 1 → 서비스 확인 중 ─┬─ 준비됨 → [연결] → 제어 화면 → Switch로 on 3 / off 3 로그
                                                            └─ 끊김 + [다시 시도] → 서비스 확인 중 → …
```

여기에 **본인 기능 1개**를 더한다. 2~7주 범위에서 고르고, 발표에서 한 문장으로 소개할 수 있어야 한다. 예:

| 본인 기능 예 | 쓰는 것(배운 주) |
|---|---|
| 장치 이름이 비어 있으면 [검색]을 시작하지 않고 Toast로 알린다 | `Toast`(3주)·`isEmpty()`(4주) |
| `준비됨`일 때만 [연결]이 켜진다 | `when (state)`·`isEnabled`(5·7주) |
| 제어 화면의 명령 로그를 회전해도 남긴다 | `onSaveInstanceState`·`Bundle`(3주) |
| 제어 화면에 [로그 지우기] 버튼을 둔다 | `setOnClickListener`·`binding.logText.text`(2·4주) |
| `끊김`일 때만 상태 글자 아래에 `[다시 시도]를 눌러 보세요` 안내를 보인다 | TextView(2주), `visibility`(5주), `collect { }` 안의 `when`(7주) |
| [다시 시도]를 누른 횟수를 `끊김 (2번째)`처럼 보여 준다 | `MutableStateFlow`(7주), `"$변수"`(1주). 상태 틀이 글자를 덮어쓰므로 7주차 `// 9.`처럼 상태 틀 **아래에** 틀을 하나 더 둔다 |

위 표에 없는 기능도 2~7주 범위면 된다. BLE·권한·BroadcastReceiver·ListView(10주 이후)는 쓰지 않는다.

- `collect { }` 안에서는 **View만 바꾼다**. `startActivity`·Toast를 넣으면 [뒤로]로 돌아오거나 회전할 때 상태를 다시 받아 또 실행된다(7주차). 예를 들어 `준비됨`이 되자마자 `collect { }` 안에서 제어 화면으로 가게 하면, [뒤로]로 돌아오자마자 다시 제어 화면으로 가서 연결 화면에 돌아올 수 없다. 화면 이동은 [연결] 리스너에 둔다.

### (b) 5~7주 범위 자유 앱

5~7주 범위로 내가 정한 앱을 만든다. (b)는 강의자가 수업 공지로 허용한 분반만 고를 수 있다.

- 제공 파일 [FakeRequest.kt](examples/fake_request/FakeRequest.kt)를 **그대로** 복사해 첫 줄 `package`만 내 프로젝트에 맞춘다. 함수 안은 고치지 않는다.
- 앱 안에서 `fakeRequest()`를 **한 곳 이상** 부른다. 1초 뒤 절반은 `Exception("요청 실패")`를 던지고, 나머지는 `"성공"`을 돌려준다.
- 실패하면 앱이 꺼지지 않고 실패 문구와 **[다시 시도]** 버튼이 보여야 한다.
- 부르는 모양의 본보기는 예제 [RequestViewModel.kt](examples/fake_request/RequestViewModel.kt)·[MainActivity.kt](examples/fake_request/MainActivity.kt)이고, 만드는 순서는 [따라하기 13단계](walkthrough.md#13-b-새-프로젝트-project1-만들기)부터다.

## 필수 조건 — 채점 축 네 개

(a)·(b) 모두 같은 네 축으로 채점한다.

| 축 | (a)에서 보여 줄 장면 | (b)에서 보여 줄 장면 |
|---|---|---|
| 정상 흐름 | 장치 이름 → 카운트다운 → `준비됨` → 제어 화면 명령 로그, 그리고 본인 기능 | 앱의 주 흐름과 `fakeRequest()` 성공 결과 |
| 실패·재시도 | `끊김`과 [다시 시도] → 다시 시도해 `준비됨` | 실패 문구와 [다시 시도] → 다시 시도해 성공 |
| 회전 유지 | `연결 중… 3`이나 `끊김`에서 화면을 돌려도 글자·숫자·버튼이 그대로 | 요청 중이나 실패 화면에서 돌려도 문구·[다시 시도]가 그대로 |
| 코드 설명(개인 구술) | 평가자 질문 한 개에 파일과 줄을 가리키며 답한다 | 같음 |

공통 조건:

- 제출한 소스로 빌드되고 에뮬레이터에서 실행된다.
- 회전 유지는 7주차 방식(`ViewModel` + `StateFlow` + `repeatOnLifecycle` 틀 안의 `collect`)으로 만든다. 6주차처럼 Activity의 `lifecycleScope.launch { }`에서만 부르면 회전할 때 처음 문구로 돌아가 이 축을 받지 못한다.
- 실패는 `try { … } catch (e: Exception) { … }`로 받는다. 실패할 때 앱이 꺼지면 실패·재시도 축을 받지 못한다.
- 가짜 연결(`connectFake()`)이나 `fakeRequest()`의 확률을 발표용으로 고정하지 않는다. 고정하면 성공이나 실패 중 하나가 나오지 않는다.
- 9주차 1일차에 본 Service·Fragment 코드는 넣지 않아도 된다. 넣었어도 점수에 더하거나 빼지 않는다.

## 발표 — 3분

1인 3분 = **시연 2분 + 코드 설명 질문 1분**(자리 교체 포함). 2분이 되면 시연을 멈추고 질문으로 넘어간다.

```text
0:00–0:15  앱 이름, 고른 주제 (a)/(b), 본인 기능 한 문장
0:15–1:00  정상 흐름
1:00–1:30  실패 → [다시 시도] → 성공
1:30–1:50  진행 중이나 실패 화면에서 회전
1:50–2:00  마무리 한 문장
2:00–3:00  평가자 질문 한 개 → 파일 열기 → 줄 가리키기 → 한 문장으로 답하기
```

- 앞 사람이 발표하는 동안 내 앱을 실행해 첫 화면에 두고, 에뮬레이터 **자동 회전**을 켜 둔다.
- 2분 안에 보이지 못한 장면은 레포트 캡처로 보되, 그 항목은 **최대 절반**이다. 예외는 장애 기록이 있을 때와 아래 실패 확률의 경우다([채점표](rubric.md)).
- 실패가 세 번 눌러도 나오지 않으면 레포트에 넣은 실패 캡처를 보여 주고 넘어간다. 질문 시간에 한 번 더 눌러 나오면 만점이고, 그래도 나오지 않으면 실패 캡처를 보여 주며 `catch` 줄을 가리키면 만점이다(확률을 고정하지 않은 경우).
- 코드 설명 질문의 예는 [리허설 4번](lab.md#4-코드-설명-연습)에 있다. 질문은 평가자가 고른다.
- 발표 자료(PPT)는 만들지 않는다. 앱과 코드 편집기만 쓴다.

| 항목 | 내용 |

레포트에 넣을 다섯 절:

1. **앱 소개와 실행 방법** — 주제 (a)/(b), 한 줄 소개, 실행 순서(무엇을 누르면 무엇이 보이는지 3~6줄).
2. **파일 목록** — 내가 만들거나 고친 파일 이름과 하는 일 한 줄씩(예: `ConnViewModel.kt` — 카운트다운과 가짜 연결).
3. **채점 축 캡처와 코드 위치** — 아래 표를 채운다. 캡처는 에뮬레이터 창의 카메라 모양 버튼(Take Screenshot)으로 찍는다.

| 축 | 캡처 | 이 장면을 만드는 코드(파일 이름과 줄 번호) |
|---|---|---|
| 정상 흐름 | (캡처) | |
| 실패·재시도 | 실패 문구와 [다시 시도]가 함께 보이는 캡처 | |
| 회전 유지 | 같은 상태의 세로 화면과 회전한 가로 화면 두 장 | |

4. **본인 기능 설명** — (a)는 본인 기능이 무엇이고 어느 파일·줄에 있는지. (b)는 `fakeRequest()`를 부르는 곳과 [다시 시도]가 보이게 되는 줄.
5. **오류 해결 기록** — 만들면서 겪은 오류 한 개 이상. 빨간 오류 메시지 원문(또는 앱이 꺼진 증상), 원인, 고친 방법을 적는다.

## 발표 정원 계산

발표 시간이 60분을 넘지 않는지 분반 인원이 정해지면 바로 계산한다.

```text
발표 시간 T = ceil(N / E) × D ≤ 60분
N = 발표 인원(팀이면 팀 수), E = 동시에 따로 듣는 평가자 수, D = 3분
ceil(x) = 소수점 올림
```

팀을 허용한 분반은 코드 설명을 한 사람씩 하므로 2인 팀이면 D = 4분(시연 2분 + 질문 1분 × 2)으로 계산한다. 팀 허용 여부는 수업 공지를 따른다.

| N | E | ceil(N / E) × 3 | 운영 |
|---|---|---|---|
| 20 | 1 | 20 × 3 = 60분 | 2일차 60분에 끝난다 |
| 38 | 2 | 19 × 3 = 57분 | 평가자 두 명이 두 조로 나눠 동시에 듣는다 |
| 26 | 1 | 26 × 3 = 78분 | 넘친다 → 1일차 실습 20–60분에 앞 순서 13명(39분), 2일차에 13명(39분) |
| 45 | 2 | 23 × 3 = 69분 | 넘친다 → 1일차 실습 20–60분에 조마다 앞 순서 13명씩, 2일차에 나머지 |
| 45 | 3 | 15 × 3 = 45분 | 평가자를 늘리면 2일차 60분에 끝난다 |

넘칠 때는 1일차 실습 시간의 뒤쪽 40분(20–60분, 최대 13명, 39분)에 나눠 시작하거나 조교 평가자를 늘린다. 어느 쪽인지와 순서표는 1일차에 공지한다.
1일차 발표자는 희망자와 준비된 사람부터 정한다. 1일차에 발표하는 사람도 채점 기준과 레포트 마감은 같다.

## 장애가 나면

**먼저 손을 든다.** 조교가 시각·증상·조치를 기록한다. 빨간 오류, 앱이 꺼지는 것처럼 **내 코드 때문에 생긴 문제는 장애가 아니다.**

| 상황 | 대체 절차 |
|---|---|
| 에뮬레이터가 켜지지 않거나 멈춘다 | Device Manager에서 그 기기의 ⋮ › **Cold Boot Now**. 3분 안에 안 되면 순서를 맨 뒤로 미루고 다시 시도한다 |
| PC가 멈추거나 꺼진다 | 다시 켜고 순서를 뒤로 미룬다. 수업 안에 끝내지 못하면 기록을 근거로 다음 수업 시작 전에 발표한다 |
| 회전 버튼이 앱을 돌리지 않는다 | 에뮬레이터 빠른 설정에서 자동 회전을 켠다. 그래도 안 되면 레포트의 회전 캡처 두 장으로 보여 준다(장애 기록) |
| 결석(공결) | 처리와 발표 일정은 대학 규정과 수업 공지를 따른다 |
