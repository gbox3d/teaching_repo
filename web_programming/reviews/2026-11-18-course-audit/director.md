# 전체 수업 구성 심사와 리허설 기준

작성일: 2026-11-18. 대상: 강의자의 웹프로그래밍 15주 교재. 역할: 총괄 디렉터.

## 현재 결정과 문서 범위

결정: 9개 독립안을 받은 뒤 같은 기준으로 심사한다. 이 문서는 특정 SPA 배치안이나 전체 수업안을 확정하지 않는다. 기획·구현 순서와 배점의 정본은 [brief.md](brief.md)와 [plan.md](plan.md)다.

근거: SPA를 추가하는 위치만 정하면 기존 수업의 과밀, 제공 코드와 학생 작성 코드의 혼동, 11주와 12주 사이의 인계 문제를 해결하지 못한다. 전체 30차시의 학생 활동과 다음 차시 시작 파일을 함께 비교해야 한다.

대안: 현재 순서를 보존하는 안, 정규 차시를 줄여 SPA 전환을 넣는 안, 선택 특강에서 전환하는 안을 모두 심사한다. 어느 방식을 골랐는지만으로 가점이나 감점을 주지 않는다.

재검토: 9안 접수 후 기획 심사, 승자안의 대표 차시 리허설, 전체 구현 후 독립 최종 심사에서 다시 판단한다. 앞서 전달한 디렉터 개인의 배치 의견도 확정안이 아니다.

본 작업에서는 이 보고서만 작성한다. 기존 교재·예제·시험·다른 과목·실행 도구는 수정하지 않는다.

## 확인한 자료와 검토의 한계

운영 근거는 `web_programming/AGENTS.md`, 과목 `README.md`, `weeks/README.md`, `specials/README.md`다. 15개 주차의 README와 lab에서 목표·차시 시간표·완료 조건·다음 주 인계를 확인했다. 저장소에서 별도 `tableofcontents` 파일은 찾지 못했으며 주차 색인과 각 문서의 목차를 기준으로 삼았다.

코드 근거로 7·10·11주 방명록, 11주 ex06·ex07, 12주 ex01~ex03과 `.http`, 13주 조회·등록, 14주 방명록 HTML과 목록 코드를 읽었다. 아래 내용은 수업 구성의 검토다. 모든 예제의 실행 검증이나 학생 대상 소요 시간 측정을 마쳤다는 뜻이 아니다. 개별 파일 전수 조사와 브라우저 검증은 선정안 구현 단계에서 담당자를 나누어 수행한다.

공통 사실은 모든 기획자가 사용할 수 있다. 다른 기획자의 해석·권고·점수는 독립안 제출 전까지 공유하지 않는다.

## 60분 강의와 30분 실습을 판단하는 방법

60분 강의에는 개념 설명·예측 질문·실행 시연·오류 관찰·실습 인계가 들어간다. 강의 시간에 학생이 장문의 완성 코드를 계속 타이핑하게 하고 별도로 30분 실습을 배정하면 실제 작업 시간은 계획과 달라진다. 함께 입력하는 시간이 있다면 표에서 구분한다.

30분 실습에는 대략 준비 확인 3~5분, 학생 수정 15~20분, 동작 확인·오류 수정 5~7분, 증거 저장 3분을 확보한다. 이것은 모든 주의 분 단위를 고정하는 규칙이 아니라 제안의 누락을 찾는 점검 틀이다. 파일 다운로드·저장소 생성·배포가 포함되면 그 시간을 명시한다. 수업 전후로 옮기는 활동도 학생 부담에서 사라진 것으로 계산하지 않는다.

필수 실습은 한 화면에서 확인할 수 있는 학습 결과 하나로 좁힌다. 개념별 비교 예제는 모두 남길 수 있지만 강의자 시연·학생 필수·선택 확장을 표시한다. 코드 줄 수 자체보다 학생이 동시에 판단할 대상 수, 오류를 찾기 위해 오갈 파일 수, 설명 없이 새로 만나는 문법 수를 비교한다.

리허설 기록에는 시작 파일, 완성까지의 변경 목록, 각 단계 소요 시간, 막힌 지점, 도움말을 사용한 횟수와 실제 결과를 쓴다. 에이전트나 숙련자의 수행 시간은 초보 학생 소요 시간으로 표시하지 않는다. 학생 리허설이 없으면 그 한계를 밝히고 보수적인 분량 근거를 남긴다.

## SPA 제안에 요구할 판단과 구현 계약

SPA 판단은 기존 동작과 학생이 새로 얻는 이해로 평가한다. 탭처럼 보이는 버튼을 추가하거나 페이지 여러 개를 한 파일에 붙이는 것만으로 학습 효과가 입증되지는 않는다. 반대로 프레임워크 도입이 없다는 이유로 SPA 학습이 불가능한 것도 아니다.

| 선택지 | 후보가 설명할 교육적 이득 | 후보가 부담으로 계산할 것 |
|---|---|---|
| 정규 과정의 전체 전환 | 페이지 이동과 화면 전환, 화면 상태와 데이터 상태를 실제 프로젝트에서 비교 | 이동·초기 진입·주소·기존 링크·다음 주 예제·시험까지 모두 변경 |
| 정규 과정의 짧은 비교 | 같은 입력과 목록을 두 방식으로 실행해 문서 재요청과 상태 변화를 관찰 | 직접 구현하지 않는 범위와 시험 제외 여부, 비교가 들어갈 기존 시간의 조정 |
| 선택 연결 특강 | 저장까지 배운 방명록을 별도 단계로 전환하고 필요하면 REST와 연결 | 정규 미참여 학생의 다음 주 시작점 보장, 별도 자료와 유지 비용 |
| 정규 전환 보류 | 현재 개념을 익히는 데 필요한 시간을 확보 | SPA의 필요성 검토 근거, 학습자가 확인할 비교 자료와 이후 도입 조건 |

단순한 vanilla-JS 전환안은 다중 페이지 `index.html`·`about.html`·`guestbook.html`과 단일 HTML의 동일 내용을 비교할 수 있다. 새 개념을 줄이려면 `#home`·`#about`·`#guestbook` 같은 해시, `location.hash`, `hashchange`, `hidden`, 짧은 함수와 if로 구성하는 방식을 검토할 수 있다. 이 구현 예시는 의무 선택이 아니다. 라우트 객체·동적 import·일반화된 라우터를 추가하면 그 필요성과 선수 지식을 입증해야 한다.

후보는 다음 동작을 명시한다.

1. 주소에 해시가 없을 때의 초기 화면과 알 수 없는 해시의 처리.
2. 메뉴 링크로 화면을 바꿀 때 주소·선택 메뉴·보이는 본문이 함께 바뀌는 규칙.
3. 새 탭에서 방명록 주소를 직접 열거나 새로고침했을 때 같은 화면을 여는 규칙.
4. 뒤로·앞으로 이동 시 화면과 주소가 일치하는 규칙.
5. 화면만 이동할 때 입력·배열·목록을 유지하거나 초기화하는 규칙.
6. 새로고침 뒤에는 메모리 상태가 초기화되고, 브라우저 저장이나 서버에서 복원하는 별도 코드가 필요하다는 구분.
7. section의 id 중복 방지, 보이는 제목, 현재 메뉴 표시, 키보드 탐색을 확인하는 방법.

해시 변경은 `hashchange`로 관찰한다. `pushState`나 `replaceState`로 주소를 바꿨을 때는 같은 이벤트가 발생한다고 가정하면 안 된다. History API를 채택하는 후보는 `popstate`와 서버의 직접 경로 응답까지 별도 검증한다. [MDN hashchange](https://developer.mozilla.org/en-US/docs/Web/API/Window/hashchange_event), [MDN pushState](https://developer.mozilla.org/en-US/docs/Web/API/History/pushState).

GitHub Pages는 HTML·CSS·JavaScript를 제공하는 정적 호스팅이며 프로젝트 사이트 주소에는 저장소 경로가 들어간다. `/guestbook` 같은 가상 경로를 쓰는 안은 새로고침과 직접 접속에 필요한 파일 또는 배포 처리를 제시해야 한다. 해시를 쓰는 안도 `/web-weekNN/` 아래에서 상대 자산 경로가 맞는지 검증한다. [GitHub Pages 공식 설명](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages).

SPA의 화면 전환은 저장 기능이 아니다. GitHub Pages의 같은 사용자 도메인 아래 프로젝트들은 경로가 달라도 같은 origin일 수 있다. localStorage를 저장소별로 자동 격리한다고 설명하지 않는다. localhost의 포트가 달라지거나 HTTPS 공개 주소로 옮겨지면 같은 저장값이 보이지 않는 조건도 분리해서 설명한다.

## 채점과 독립 심사 절차

배점은 [brief.md의 독립 심사](brief.md#독립-심사)를 그대로 사용한다. 학습 순서 2점, 차시 분량 2점, SPA 판단 1.5점, 기술 정확성 1.5점, 재현 1점, 교재·평가 일관성 1점, 실행 가능성 1점으로 총 10점이다. 이 문서에서 별도 배점을 추가하지 않는다.

각 심사자는 안별로 항목 점수, 합계, 근거 파일, 필수조건 위반, 해결되지 않은 위험, 수정 후 재심 조건을 독립적으로 기록한다. 시간표에 30분이라고 썼다는 이유만으로 분량 점수를 주지 않는다. SPA를 필수로 넣었다는 이유만으로 SPA 점수를 주지 않는다. 코드를 제공한다는 이유만으로 선수 지식 문제를 없앤 것으로 보지 않는다.

세 심사자가 모두 8/10 이상을 준 안만 통과 후보가 된다. 필수조건 위반이나 재현 불가능한 결함은 합계와 별개로 탈락 또는 보완 사유다. 통과안은 평균 점수로 순위를 정하고, 동점이면 최저 심사 점수, 그다음 학생 구현 부담이 작은 안을 우선한다. 전부 미달이면 지적을 반영해 다시 심사하며 기준을 낮추지 않는다.

SPA가 선택·시연 범위이면 중간·기말 필수 문항으로 출제하지 않는다. 정규 필수 구현으로 편성하면 실제로 작성한 부분에 맞추어 문제은행과 채점표를 수정한다. 직접 주소·뒤로·앞으로처럼 한 장의 캡처로 입증되지 않는 동작은 채점자의 재현 절차에 포함한다. 기술 시연과 실제 구현 능력을 같은 점수로 취급하지 않는다.

기획 심사를 통과한 것은 교재 구현 완료가 아니다. 승자안을 확정한 뒤 주차별 담당자가 각 README·slides·walkthrough·lab·examples·시험 문항·한영 자료를 조사하고 갱신한다. 통합 담당자는 주차 인계와 공통 문서·사이트 색인을 맞춘다. 마지막으로 구현에 직접 참여하지 않은 평가자 3명이 전체 결과를 심사하여 각각 8/10 이상일 때 완료한다.
