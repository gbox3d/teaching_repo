# C03 · 10주차에는 목록과 화면 상태를 비교하고 SPA 구현은 특강으로 분리한다

작성일: 2026-11-18. 강의자의 수업의 입문자 기준으로 작성한 독립안이다. 다른 제안서는 읽지 않았으며 원고·코드는 변경하지 않았다. 아래 경로의 기준은 `web_programming/`이다.

## 결정 기록

- 결정: 정규 방명록은 다중 페이지를 유지한다. 10주 2차시에 SPA 완성 예제를 10분 시연하고 학생은 5분 동안 탐색과 상태 보존을 비교한다.
- 근거: 10주는 배열·반복문·DOM 생성·재생성·삭제가 처음 만나는 주다. 여기에 주소 해석과 초기 진입 처리를 직접 구현하게 하면 목록 이해를 확인할 시간이 줄어든다.
- 대안: 10주 전체를 SPA로 바꾸면 화면 전환 동기는 선명하지만 11주 객체·저장과 12주 REST의 출발 파일까지 동시에 바뀐다. 14주에 넣으면 수정·삭제 실습을 압박한다.
- 재검토: 첫 운영에서 10주 필수 목록 과제를 학생 80% 이상이 실습 20분 안에 끝내면 다음 학기에 화면 전환 구현을 검토한다. 이번 학기 시험에는 SPA 구현을 넣지 않는다.
- SPA 구현은 14주 이후 선택 연구 특강으로 편성한다. 배열 상태, 브라우저 저장, 서버 저장을 모두 경험한 뒤 탐색과 데이터의 수명을 비교한다.

## 90분 운영과 선수 지식

일반 차시 27회는 강의·시연 60분과 학생 실습 30분으로 운영한다. 8·15주 2차시와 9주 2차시만 평가 운영의 예외다. 일반 차시의 총 강의·시연은 1,620분, 학생 실습은 810분이며 평가 차시 270분을 더해 총 2,700분이다.

일반 차시 기본 배분은 0~10분 복습, 10~30분 첫 개념, 30~50분 두 번째 개념·시연, 50~60분 실패 비교·실습 안내다. 실습은 60~65분 시작 확인, 65~85분 지정 코드·값 수정, 85~90분 동작 확인·캡처다. 7·11주는 기존의 세부 시간표를 유지한다. 강의·시연 60분에 학생의 필수 타이핑을 숨기지 않는다. 표의 학생 수정만 30분 안에 평가하며 나머지 예제는 수업 후 선택 복습이다.

1·2주 계정과 설치는 사전 점검하고, 2주 첫 push는 수업 안에서 수행한다. 접속 장애가 생기면 해당 학생은 로컬 결과를 제출하고 다음 차시 시작 점검을 받는다. 3주 이후 Git은 재설명하지 않는다. 4주부터 새 저장소·Pages 설정은 준비 루틴, 최종 push는 수업 후 정리로 분리하고 업로드만의 별도 점수는 두지 않는다. 매주 배포 누락은 다음 수업 시작 5분 복습에서 확인한다. Pages 지연 시 로컬 화면과 Commits 캡처를 인정한다. 필수 새 개념은 주당 3~5개 묶음으로 제한한다. 10주는 배열, 반복, DOM 생성, 목록 재생성, 제공 삭제 틀의 다섯 묶음이다.

10주의 SPA는 이름·현상 관찰이며 새 API 구현 과제가 아니다. `hashchange`·주소 초기화·접근성 처리는 선택 특강에서 새로 설명한다.

## SPA의 도입 범위와 상태 계약

10주 비교 예제는 새 `week10_array_list/examples/day2/ex08/`에 둔다. 강의자가 제공하는 `index.html`·`app.js`와 W3.CSS로 두 화면만 만든다. `#list`와 `#about`을 `<a>`로 오가고 이미 존재하는 두 section을 `hidden`으로 전환한다. 메뉴, 현재 제목, 목록 데이터가 서로 다른 값임을 보여 준다. 정규 학생은 목록 두 개 입력→소개→뒤로→앞으로→새로고침만 실행한다. 라우터 작성·영구 저장·fetch 연결은 정규 과제가 아니다. `showList()`는 배열을 목록으로 그리는 함수이고 `showPage()`는 주소에 따라 section을 선택하는 함수다. 화면 전환에서 배열을 초기화하거나 submit 이벤트를 다시 등록하지 않는다. 정규 완성 방명록은 기존 `guestbook.html` 주소를 유지한다. 10주 ex08은 대조 예제이므로 11~14주의 시작 파일에 섞지 않는다.

| 상태 | 10주 비교 예제 계약 | 14주 이후 SPA 특강 계약 |
|---|---|---|
| 현재 화면 | URL hash에서 읽음. 빈 hash는 목록, 알 수 없는 hash는 안내 화면 | 같은 규칙으로 홈·목록·작성 세 화면을 선택 |
| 목록 | `items` 배열. 탐색 중 유지, 새로고침하면 초기화 | 서버가 정본. 시작·새로 불러오기·쓰기 성공 후 GET |
| 입력 중인 글 | DOM 입력값. section 숨김으로 유지, 새로고침하면 초기화 | 초안만 전용 localStorage 키에 저장, 목록과 합치지 않음 |
| 편집 키 | 없음 | 사용자가 입력한 메모리 값만 사용, 저장·URL·캡처에 포함하지 않음 |
| 통신 상태 | 없음 | 불러오는 중·완료·실패, 요청 중 버튼 비활성, finally에서 복구 |
| 이벤트 | 최초 실행에서 한 번 등록 | 최초 실행에서 한 번 등록. 탐색 시 POST·PATCH·DELETE를 자동 실행하지 않음 |

특강 첫 단계는 ex08의 숨김·주소 처리, 둘째는 14주 REST 코드의 화면 통합, 셋째는 탐색·지연·실패 실험이다. 분량·차시 수는 고정하지 않는다. 전체 목록 DOM을 갈아 끼워 폼과 이벤트를 잃지 않도록 폼 section은 보존하고 목록 안쪽만 다시 그린다. 사용자 글은 `textContent`, `innerHTML = ''`는 목록 비우기에만 쓴다. 주소는 `https://<id>.github.io/<repo>/#list` 또는 예제 폴더의 `index.html#list`다. fragment는 서버 파일 경로를 바꾸지 않으므로 초기 문서를 읽고 hash에 맞는 section을 표시한다. 첫 실행에서 `showPage()`를 직접 호출하고 이후 `hashchange`에서도 호출한다. 따라서 직접 주소·새로고침·뒤로/앞으로를 같은 규칙으로 처리한다. [MDN hashchange](https://developer.mozilla.org/en-US/docs/Web/API/Window/hashchange_event) `/list` 같은 경로를 History API로 만드는 방식은 사용하지 않는다. Pages에서 해당 파일이 없는 직접 요청은 별도 처리가 필요하고 이번 범위를 늘린다. [GitHub Pages 파일 경로](https://docs.github.com/en/pages/getting-started-with-github-pages/creating-a-github-pages-site) 자산은 `./app.js`·`./shared/examples.css`처럼 저장소 하위 경로에서도 동작하게 한다. 화면 전환마다 title·현재 메뉴의 aria-current·제목 포커스를 갱신한다. 알 수 없는 hash는 안내 화면과 목록 링크를 표시해 주소를 몰래 바꾸지 않는다. 이 동작도 직접 주소와 뒤로가기 검사에 포함한다. SPA 특강에서는 book_id와 API 주소를 화면 이동 중 바꾸지 않는다. 요청 중에는 다른 화면으로 이동해도 요청 완료를 처리하고, 목록 상태만 갱신해 포커스를 빼앗지 않는다.

## REST 실행·키·장애 처리

12주 비교 예제 앞에 `examples/day1/ex00_connection/`을 추가해 `01_about/`→`02_help/` 순서로 열고 실행 가능한 `.http`를 각각 둔다. 이후 GET·POST·PATCH·DELETE 예제에도 해당 요청 파일을 둔다. `/rest/v1/about`·`/rest/v1/help`는 수업 서버가 준비한 읽기 전용 뷰다. 강의자가 사전에 200과 배열 응답을 확인하고 학생에게 계정·SQL 실행을 요구하지 않는다. REST Client `humao.rest-client` 설치, `baseUrl`, `apikey`, `bookId` 설정과 요청 위 **Send Request**를 각 README에서 설명한다. 실제 자격증명은 로컬 환경값·입력 프롬프트로 받는다.

공개 키와 `book_id`는 편집 권한이 아니다. 서비스 역할 비밀 키는 학생에게 배포하지 않고, 편집 키는 해당 방명록의 PATCH·DELETE 헤더 `X-Edit-Key`에만 넣는다. 기대 결과는 about/help/GET 200+배열, POST 201+한 행, PATCH 200+한 행, DELETE 204+빈 본문이다. PATCH·DELETE 뒤 같은 id GET으로 실제 변경을 확인한다. 204에서 JSON 파싱을 하지 않는다. 틀린 편집 키가 반드시 HTTP 오류를 만든다고 가르치지 않고 빈 배열·남아 있는 행도 실패로 판단한다.

서버 id와 배열 인덱스를 구분하고 모든 변경 요청에 자기 book_id·id를 함께 지정한다. 공용 데이터는 별칭과 연습 문장만 사용한다. 공용 API 장애는 강의자 로컬 연습 서버로 요청 문법을 계속 연습하되 다른 기기 공유 검증은 미완료로 표시하고 후속 확인한다. 모의 성공 캡처로 대체하지 않는다.

## 가상 수업 검증과 한계

프로그램 경험이 없는 학생이 직전 주 필수 과제만 끝냈다고 놓고, 이번 조사에서는 파일의 문법 순서와 표의 활동을 종이 위에서 추적했다. 실제 수업 측정값은 아니다. 10주에서는 문자열 배열 3개→li 3개→splice 후 2개→showList 호출을 순서대로 추적했다. 삭제 틀은 제공하되 배열이 바뀌는 줄·화면이 바뀌는 줄을 학생이 각각 찾게 한다. 11주는 ex06 성공만으로 다음 주에 들어가는 학생을 가정했다. 12주 첫 시연은 제공 객체 배열에서 `name`·`message`를 다시 짚어 저장 참고본 미구현의 공백을 메운다.

| 예상 실패·검증 장면 | 통과 조건 | 실패 시 조정 |
|---|---|---|
| 10주 17분 안에 6개 빈칸을 못 채움 | 3개 추가·가운데 삭제·2개 표시 | SPA 학생 비교 5분을 목록 보강에 사용하고 시연만 남김 |

구현 후 `npm run build`, `npm run check`, `npm run test:labs`와 변경된 JavaScript 구문 검사를 실행한다. 실제 브라우저에서는 7→9→10→11→12→13→14의 인계·375px·Console·Network를 확인한다.

SPA는 로컬과 Pages의 저장소 하위 경로에서 첫 주소, 직접 #about, 새로고침, 뒤로, 앞으로, 잘못된 hash를 모두 확인한다. 자동 검사는 학습 시간을 증명하지 못한다. 파일 준비가 늦은 초보자는 30분 실습에서 불리하다. 준비 완료 여부를 사전에 확인하고 첫 운영에서는 실제 종료 시간·도움 횟수를 기록해 필수 수정 수를 재조정해야 한다. 이 안의 손실은 정규 수업에서 SPA를 직접 완성하지 않는다는 점이다. 대신 학기 말까지 방명록의 데이터·저장·REST 수정 흐름을 학생 과제로 유지한다.
