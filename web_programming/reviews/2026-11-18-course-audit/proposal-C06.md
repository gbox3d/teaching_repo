# C06 · CRUD를 완성한 뒤 SPA를 별도 단계로 전환한다

강의자의 수업의 14주 통합 시점을 검토한 독립안이다. 조사일은 2026-11-18이며 다른 기획안은 읽지 않았다.

## 결정과 근거

결정: 정규 14주는 수정·삭제 구현으로 마친다. 2차시 강의 안에 완성된 CRUD의 다중 페이지·SPA 비교 시연 8분을 두고, 실제 전환은 14주 완성본에서 출발하는 선택 특강으로 운영한다.
근거: CRUD를 배운 뒤에는 화면 이동과 서버 데이터의 수명을 비교하기 좋다. 그러나 현재 14주 완성본은 설정을 제외해도 JS 다섯 파일이 협력한다. 여기에 주소 해석·초기 진입·탐색·중복 초기화를 함께 맡기면 학생이 수정·삭제의 결과를 검증할 시간이 줄어든다.
대안: 14주 전체를 SPA 통합 주로 바꾸려면 PATCH·DELETE를 앞당기거나 제공 기능으로 돌려야 한다. 12주 읽기·13주 저장·14주 수정·삭제의 학습 순서를 지키기 위해 채택하지 않는다. 프레임워크·번들러도 도입하지 않는다.
재검토: 14주 두 실습을 초보 학생이 각각 30분 안에 완료하고, 별도 SPA 실습에서 주소·상태 차이를 설명할 수 있는지 확인한 다음 학기 편성 때 다시 판단한다. 시연을 본 사실을 구현 능력으로 평가하지 않는다.

일반 차시 G는 강의·시연 60분과 실습 30분이다. 강의 중 장문 타이핑은 없다. 실습은 준비 4분·수정 15분·확인 6분·증거/업로드 5분을 기본으로 하되 11·14주는 아래처럼 조정한다.

7주 이메일 입력은 화면 연습용이며 REST 데이터는 이름·메시지로 한정한다. 12주 제공본에서 이메일 칸 제거 이유와 기존 id의 유지/제거 목록을 표시한다. localStorage 글을 서버로 자동 업로드하지 않는다.
11주 제공 완성본도 `web-week11:guestbook:v1`처럼 키를 구분하고 JSON 손상·값 형식 검사와 복구 안내를 넣는다. 이 방어 코드는 제공 범위다. ex07의 탭 동기화와 배열 심화는 선택/특강으로 표시하고 정규 시험에서 제외한다.
W3.CSS는 `https://cdnjs.cloudflare.com/ajax/libs/w3-css/4.1.0/w3.min.css`를 유지한다. 추가 스타일은 `shared/examples.css`로 모으고 배포 묶음에 넣는다. 홈·소개와 방명록의 서로 다른 기존 CSS를 7~14주 담당자가 함께 확인한다.
13·14주의 기능별 JS 분할을 유지한다. 공통 규칙에 REST 완성본 예외를 명시하고 `config → guestbook → submit → actions → delete → edit`의 defer 로딩 순서와 전역 이름을 설명한다. 학생은 차시마다 요청 파일 하나만 수정한다.

## 14주 비교와 SPA 특강의 구현 계약

14주 시연은 같은 미제출 입력을 넣고 다른 메뉴로 이동했을 때, 서버 글은 남고 문서/입력 상태는 이동 방식에 따라 달라지는 모습을 비교한다. 다중 페이지의 브라우저 복원 동작도 있을 수 있으므로 “언제나 입력이 사라진다”로 일반화하지 않는다. 시연용 SPA는 강의자 제공이며 학생 작업·평가에 포함하지 않는다.
특강 결정: 새 `specials/spa_after_crud/`에 다중 페이지 기준본→해시 전환→CRUD 결합→공개 주소 검증 단계를 둔다. 기본 전제는 14주까지이며 배열 심화·Supabase 구축 수강을 요구하지 않는다. 각 단계가 동작할 때 다음 단계로 진행하고 시간 상한은 두지 않는다.
전환 파일: F14를 별도 `web-spa` 저장소에 복사한다. `index.html`에 홈·소개·방명록 section을 두고 id 충돌을 제거한다. 기존 CRUD 함수와 폼 id는 유지한다. 새 클래식 `route.js`는 `location.hash`와 if로 section의 `hidden`을 바꾸며 모든 DOM과 리스너는 한 번만 만든다. 기존 `web-week14` 주소와 파일은 보존한다.
주소: `/web-spa/#home`, `#about`, `#guestbook`을 사용한다. 해시 없음은 홈이며 알 수 없는 해시는 주소를 유지한 채 “페이지를 찾을 수 없습니다” 화면과 홈 링크를 표시한다. 메뉴 링크·본문·`aria-current`를 같은 함수에서 갱신한다.
직접 진입·새로고침: 초기화 때 route 함수를 한 번 호출하고 `hashchange`에도 등록한다. `/web-spa/#guestbook`을 새 탭에서 열거나 새로고침하면 방명록을 표시하고 GET을 한 번 실행한다. `pushState`·`replaceState`는 사용하지 않는다. 해당 메서드는 `hashchange`를 발생시키지 않는다. [MDN hashchange](https://developer.mozilla.org/en-US/docs/Web/API/Window/hashchange_event)
뒤로·앞으로: 일반 해시 링크의 이력 이동마다 같은 route 함수로 화면을 선택한다. 메뉴 재방문만으로 CRUD 리스너를 재등록하거나 GET을 자동 반복하지 않는다. 화면 복귀 후 최신 자료가 필요하면 기존 새로 불러오기 버튼을 사용한다.
상태: 같은 문서 안의 화면 이동은 작성 중 입력·수정 대상·목록·편집 키 메모리를 유지한다. 전체 새로고침은 입력·편집 대상·키를 초기화하고 서버 글만 GET으로 복원한다. 라우팅은 저장 기능이 아니며 키는 URL·localStorage에 넣지 않는다.
브라우저 저장: 선택 확장으로 초안을 저장할 경우 `web-spa:draft:v1` 같은 키를 사용한다. 같은 GitHub 사용자 도메인의 프로젝트 경로들은 localStorage를 공유할 수 있다. localhost 포트 변경·HTTPS 이동 때 origin이 달라지는 점을 11주 설명과 맞춘다.
Pages: 실제 `/web-spa/` 디렉터리의 index와 상대 자산 경로로 배포하고 `/guestbook` 가상 경로는 만들지 않는다. 프로젝트 사이트가 저장소 경로 아래 정적 파일을 제공한다는 조건을 사용한 설계다. [GitHub Pages 설명](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages)
기존 링크: 원래 `web-week14/about.html`·`guestbook.html`은 계속 동작한다. 새 저장소에 남겨 둔 같은 이름의 HTML에는 대응하는 `index.html#about`·`#guestbook` 이동 링크를 제공한다. README의 특강 링크만 새 주소로 바꾼다.
접근성·요청: 숨겨진 section에 포커스가 남지 않게 전환 후 보이는 제목에 포커스를 두고 키보드 왕복을 확인한다. 중복 id·중복 이벤트·같은 POST 두 번 발생을 검사한다. 화면 밖에서 끝난 요청은 목록/상태만 갱신하며 사용자를 강제로 방명록으로 이동시키지 않는다.

## 변경 순서와 평가·검증

1. 선정 후 각 주 담당자가 README·slides·slides_en·walkthrough·lab·examples의 조사 목록을 작성한다. 현재 표의 필수·시연·선택 범위를 먼저 고정하고 공통 60+30·준비·캡처 예외·저장소 규칙을 수정한다.
2. 4·5·9주 필수 예제를 줄이고 7→9→10주의 CDN·class·id·자산 인계를 먼저 맞춘다. 10주의 11주 예고, 11주의 필수 ex06과 제공 F11, 12주의 시작 파일을 함께 수정한다.
3. 12주 접속/about/help 폴더를 앞에 두고 이후 GET→POST→DELETE/PATCH 각 폴더에 실행 가능한 `.http`를 둔다. REST Client의 base URL·공개 헤더 설정, Send Request, 200 배열·201·204의 의미를 같은 순서로 설명한다. 실제 키는 환경값/실행 시 입력을 사용한다.
4. 13·14주 시작본을 완성본과 구분해 작성 지점을 표시한다. `book_id`는 구분값, 편집 키는 변경 권한이라는 설명을 유지한다. PATCH의 `200 []`, DELETE의 `204`가 실제 변경을 보장하지 않으므로 지정 ID 재조회와 목록 재조회를 모두 보존한다.
5. 8주 시험은 7주 제공 submit 코드 직접 구현을 제외한다. 9주 README의 SVG·Mermaid 배점을 제거하고 발표 운영을 인원에 맞춘다. 15주 은행은 11주 ex06·12~14주 실제 작성 범위로 맞추며 SPA는 제외한다. 별도 레포트는 14주 시간표·실습 점수에 섞지 않는다.
6. 시험용 서버·book_id·편집 키를 별도 배부한다. 서버 장애 시 강의자가 같은 계약의 로컬 API를 준비하며, 복구가 안 되면 REST 항목을 별도 시간에 재평가한다. 정적 캡처만으로 서버 변경 성공을 채점하지 않는다.
7. 정규 흐름이 통과한 다음 SPA 특강과 8분 비교본을 제작한다. 특강 README·한영 슬라이드·lab·walkthrough·단계별 예제와 specials 색인을 연결한다. 기존 배열·지도·IoT·신시사이저·Supabase 특강은 정규 선수 지식으로 추가하지 않는다.

검증 예정: 초보 학생 2~3명에게 제공본만 주고 7주 변환, 11주 ex04~06, 12주 첫 접속, 14주 삭제/수정을 수행하게 한다. 준비·수정·확인·도움 요청 시간을 나눠 기록하고 30분 초과 시 학생 수정량을 줄인다. 숙련 개발자의 수행 시간을 학생 시간으로 보고하지 않는다.
검증 예정: 7주 전후 같은 두 입력, 10주 세 글 중 가운데 삭제, 11주 없는 값/빈 문자열/손상 JSON, 12주 빈 목록/Offline 복구, 13주 빠른 재클릭/실패 후 입력 유지, 14주 틀린 키/204/지정 ID 재조회를 실행한다. Console 오류와 예기치 않은 요청이 없어야 한다.
검증 예정: SPA는 홈→소개→방명록→뒤로→앞으로, 해시 직접 진입·새로고침·알 수 없는 해시, 미제출 입력·키·서버 글의 수명, POST 도중 화면 이동, 키보드 탐색을 실제 Pages `/web-spa/`에서 확인한다. 한 장 캡처로 탐색 통과를 대신하지 않는다.
한계: 이 안은 초보자의 14주 시간 여유를 아직 측정하지 않았다. 정규 수강만으로 SPA 구현 능력을 얻지는 못하며, 특강의 새 배포본과 호환 링크를 유지해야 한다. 시간 초과 시 SPA 시연 8분부터 줄이고 수정·삭제의 직접 검증 시간은 보존한다.
