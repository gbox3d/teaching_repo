# C01: 기존 방명록을 이어 쓰고 실습과 평가의 범위를 맞춘다

강의자의 수업 구성 검토안이다. 2026-11-18의 공개 원고와 예제 코드를 근거로 작성했다. 기획안만 작성하며, 기존 교재·코드·배포본은 변경하지 않는다. 다른 기획안과 비공개 시험·키 파일은 열지 않았다.

## 결정 기록

**결정: 정규 15주는 현재 주제 순서와 세 HTML 페이지 구조를 유지한다.**

- 근거: 7주 W3.CSS → 10주 배열 → 11주 저장 → 12~14주 REST의 선수 지식 순서는 성립한다. 실제 방명록 HTML도 이미 상당 부분 연결되어 있다. 시간표와 인계·평가의 불일치를 먼저 고치는 편이 변경량이 작다.
- 대안: 9주 발표 시간을 SPA 구현으로 바꾸거나 10주 배열과 SPA를 함께 가르칠 수 있다. 이 경우 발표 평가를 옮겨야 하거나 배열과 화면 전환을 동시에 배워야 한다.
- 재검토: 개편본의 10주 배열 실습과 14주 수정·삭제 실습을 초보 학생이 각각 30분 안에 마친다는 관찰 자료가 쌓이면 다음 학기 SPA 정규 편입을 다시 판단한다.

**결정: 일반 수업은 모두 강의·시연 60분과 개별 실습 30분으로 맞춘다.**

- 근거: 시간표의 숫자만 바꾸면 기존 4주 13개, 5주 10개 비교 예제와 조립을 끝낼 수 없다. 비교 예제는 보존하되 필수 수정과 강의자 시연·추가 연습을 구분한다.
- 대안: 기존 30분 설명·60분 실습을 유지하면 타이핑 시간은 늘지만 강의자의 수업 모델과 주차별 운영이 달라진다.
- 재검토: 아래 실습 상한을 넘으면 시연 시간을 늘리지 않고 필수 수정 지점을 줄인다. 아직 배우지 않은 문법을 과제로 넘기지 않는다.

## 30차시 운영과 학생 수정량

## SPA는 14주 이후 별도 특강으로 도입한다

**결정: 정규 필수 SPA 구현은 0차시, 첫 구현 위치는 14주를 마친 뒤 선택 특강이다.**

- 근거: 세 페이지 링크는 이미 Pages에서 재현되며 REST를 쓰는 데 SPA가 필요하지 않다. 7주는 CSS 변환, 10주는 배열과 재그리기, 11주는 저장, 12~14주는 비동기 요청을 처음 이해해야 한다. 이 시기에 경로와 표시 상태까지 추가하면 매회 30분의 학생 수정량이 늘어난다.
- 대안: 9주에 hash 라우팅을 넣으면 발표·README 시간을 줄여야 한다. 14주에 넣으면 수정·삭제 검증 시간을 줄여야 한다. 두 대안 모두 이번 개편에서는 택하지 않는다.
- 재검토: 개편 후 정규 실습이 시간 안에 끝나고, 다음 학기 목표에 화면 전환과 상태 보존이 추가되면 9주 또는 학기 후반에 독립 차시를 확보한다.

특강은 `specials/hash_spa/`를 새로 두고 단계별로 진행한다. 전체 차시 수와 연구 시간을 제한하지 않는다. 1단계는 세 HTML과 세 section의 차이를 비교하고, 2단계는 같은 W14 화면을 `index.html` 한 파일에 모으며, 3단계는 주소·탐색·폼 상태·REST 재조회 정책을 검증한다. 프레임워크·번들러·npm·History API 기반 경로 라우터는 전제하지 않는다.

최소 구현은 `#home`, `#about`, `#guestbook` 링크와 `location.hash`, `hashchange`, section의 `hidden`, 선택 메뉴의 `aria-current`다. 최초 실행에서도 현재 hash를 읽어 화면을 선택한다. 없는 hash에는 안내 화면과 홈 링크를 보인다. section은 DOM에 유지하고 화면 전환 때 리스너를 다시 등록하지 않는다. title·제목 포커스 갱신을 포함하고 REST 함수는 기존 것을 유지한다.

GitHub Pages 예시는 `https://<아이디>.github.io/<저장소>/index.html#guestbook`이다. fragment는 서버에 전송되지 않으므로 직접 주소·새로고침 때 실제 `index.html`을 받고 클라이언트가 화면을 선택한다. hash 변경과 뒤로/앞으로에서 같은 표시 함수를 실행한다. 이 동작은 [MDN fragment](https://developer.mozilla.org/en-US/docs/Web/URI/Reference/Fragment)와 [hashchange](https://developer.mozilla.org/en-US/docs/Web/API/Window/hashchange_event)의 설명을 적용한 설계다.

`/<저장소>/guestbook` 같은 가상 경로를 만들지 않는다. GitHub Pages의 없는 파일 경로는 404 처리 대상이며, 별도 404 문서를 만들 수 있다는 사실이 SPA 경로 재작성을 제공한다는 뜻은 아니다. [GitHub Pages 404 안내](https://docs.github.com/en/pages/getting-started-with-github-pages/creating-a-custom-404-page-for-your-github-pages-site). 정규 MPA도 실제 `guestbook.html` 직접 주소·새로고침·뒤로/앞으로를 검증한다. 새로고침 때 7~10주 메모리 글은 사라지고 11주 저장 값과 12~14주 서버 글은 각 저장 위치에 남는 차이를 설명한다.

## REST 예제와 실행 설정

12주 `examples/day1/ex01`은 about 접속, `ex02`는 help, `ex03`은 자기 방명록 GET 순서로 정비한다. 기존 JSON 단독 비교는 11주 ex05를 참조하고, limit 비교는 GET 단계의 값 변경으로 흡수한다. 2일차 ex04 목록·ex05 HTTP 실패·ex06 연결 실패는 유지한다. 폴더별 README와 실행 가능한 `requests.http`를 붙여 단독 배포에서도 순서가 보이게 한다.

`.http`의 첫 요청은 about 200과 정보 배열, 다음은 help 200과 단계 목록이다. 이후 GET 200과 배열, POST 201과 생성 id, PATCH 200과 변경 행, DELETE 204와 빈 본문을 확인한다. `apikey`는 공통, JSON 쓰기는 `Content-Type`, 반환 행 확인에는 `Prefer: return=representation`, 편집은 `X-Edit-Key`가 필요하다. PATCH·DELETE 뒤에는 같은 id와 book_id로 다시 GET한다. PATCH `200 []`와 DELETE `204`만으로 변경 성공을 표시하지 않는다.

README에 VS Code 확장 `humao.rest-client`, base URL·헤더 설정, 요청 위 **Send Request**, 예상 status·본문·실패 복구를 적는다. 추적 요청 파일에는 localhost 가상 값 또는 환경 참조만 둔다. 실제 공개 키도 배부값을 추적 파일에 직접 적지 않고 REST Client의 무시되는 로컬 환경 파일에서 읽는다. 편집 키는 요청 prompt로 입력한다. 환경 파일과 키는 ZIP 배포 대상에서 제외한다.

브라우저의 공용 설정도 강의자 제공 설정 입력 패널에서 실행 중 입력하고 메모리에 둔다. 교재 설정 파일에는 로컬 가상 값만 둔다. 이 패널은 제공 기능이며 학생의 30분 구현 대상이 아니다. Pages에서도 설정 입력 후 GET을 실행하므로 실제 키를 저장소에 넣지 않아도 재현된다. 새로고침하면 설정과 편집 키를 다시 입력한다는 비용은 README에 적는다. 공개 키는 공개 호출용, 편집 키는 방명록 전체 수정 권한, 서버 비밀 키는 학생 클라이언트에 없는 값으로 구분한다. BOOK_ID는 분류 태그이며 사용자 인증이 아니다.

구현 후 저장소 루트의 `npm run build`, `npm run check`, `npm test`를 실행한다. 현재 `package.json`의 test는 덱 배치와 guestbook API·IoT·Supabase 실습 검사를 포함한다. 이 검사 통과만으로 30분 적합성이나 브라우저 CRUD를 통과시켜서는 안 된다. 기존 다른 과목 오류가 나오면 원인과 영향만 분리 기록하고 이 개편에서 다른 과목을 수정하지 않는다.

한영 슬라이드의 시간·예제 경로·입력값·완료 조건을 대조하고 README·lab·walkthrough의 상대 링크와 전체 코드 블록을 실제 예제와 맞춘다. 편집한 한국어 문서는 문체 검사 뒤 다시 읽는다. 구현에 참여하지 않은 평가자 3명이 각자 8/10 이상을 주기 전에는 완료로 표시하지 않는다.

이 안의 한계는 정규 수업에서 SPA 구현 경험을 얻지 못하며 11주 완성 방명록과 REST의 통신·오류 처리 일부를 제공 코드로 사용한다는 점이다. 또 60분 강의와 30분 실습을 유지하려면 파일 사전 준비와 짧은 수업 후 업로드가 필요하다. 학생이 모든 완성 파일을 처음부터 작성하는 목표라면 현재 시간 배분부터 다시 결정해야 한다.
