# 14주차 실습 — 글 하나를 수정하고 삭제하기

## 1일차 실습

| 시간 | 할 일 |
|---|---|
| 0–5분 | 13주 완성본을 새 `web-week14` 폴더에 준비한다. API 설정과 자기 `BOOK_ID`를 확인한다 |
| 5–15분 | ex01 배열의 순서를 바꾸고 위치와 ID를 비교한다 |
| 15–30분 | 자기 방명록에 글 세 개를 만들고 ex02로 가운데 글의 ID를 삭제한다 |
| 30–40분 | Network에서 DELETE의 메서드·헤더·204를 확인하고 목록을 다시 읽는다 |
| 40–50분 | 자기 공간에서 편집 키 한 글자를 바꿔 같은 실험을 한다. 실제 글이 남아 있는지 확인한다 |
| 50–60분 | 새 저장소에 add·commit·push 후 Pages를 켠다. 편집 키가 코드에 없는지 확인한다 |

### 문제와 힌트

1. 0번째 글의 ID가 반드시 0인지 비교한다. 힌트: `items[0].id`와 `0`은 다른 값이다.
2. 세 글 가운데 하나만 삭제한다. 힌트: URL의 `id=eq.숫자`와 `book_id=eq.자기값`을 함께 확인한다.
3. 204 뒤 `response.json()`을 호출하지 않는 이유를 Network의 Response로 확인한다.
4. 실패 실험은 자기 방명록에서만 한다. 남의 ID나 편집 키를 시험하지 않는다.

## 2일차 실습

| 시간 | 할 일 |
|---|---|
| 0–5분 | 같은 PC면 폴더를 열고, 다른 PC면 자기 저장소를 clone한다 |
| 5–15분 | ex03으로 자기 글의 메시지를 PATCH한다 |
| 15–25분 | ex04에서 같은 ID를 GET해 변경 내용을 확인한다 |
| 25–40분 | 수정 버튼으로 기존 메시지를 수정 폼에 넣고 저장 버튼을 연결한다 |
| 40–55분 | 완성본에서 추가·삭제·수정·재조회를 수행한다. 다른 브라우저에서도 확인한다 |
| 55–60분 | add·commit·push 후 공개 주소에서 확인하고 편집 키를 비워 캡처한다 |

### 문제와 힌트

1. 수정 버튼을 누르면 그 글의 ID와 메시지가 폼에 들어가야 한다. 힌트: 서버가 준 객체를 사용한다.
2. 새로 남기기는 POST, 기존 글 고치기는 PATCH다. 두 폼의 버튼과 안내 자리를 구별한다.
3. PATCH 응답이 빈 배열이면 성공 문구를 보여 주지 않는다. 힌트: 변경한 행의 수를 본다.
4. 요청 중에는 버튼을 다시 누르지 못하게 하고, 실패 후 다시 누를 수 있게 한다.

## 막혔을 때

| 상황 | 확인 |
|---|---|
| Pages 반영이 늦다 | 5분 넘으면 로컬 화면과 Commits 캡처를 제출하고 다음 수업에 공개 URL을 확인한다 |
| `Failed to fetch` | API 실행 여부·주소·CORS 설정을 강의자와 확인한다. 공용 HTTPS 페이지에서 localhost API를 서비스 주소로 쓰지 않는다 |
| `Unexpected end of JSON input` | DELETE의 204 응답에 `response.json()`을 호출했는지 확인한다 |
| PATCH가 `200 []`다 | 해당 ID가 자기 방명록에 있는지와 편집 키를 확인한다 |
| DELETE가 204인데 글이 남는다 | 204만으로 삭제를 단정하지 않는다. 키를 다시 입력하고 GET으로 확인한다 |
| 새로고침 후 키가 없다 | 키는 메모리에만 두므로 다시 입력한다 |

오류 문구는 브라우저·서버에 따라 달라질 수 있다. Network의 실제 상태와 응답을 함께 확인한다.

## 제출 — 캡처 한 장

수정한 글과 남은 목록, 주소창, PATCH 또는 DELETE 뒤의 GET 요청을 한 화면에 담는다. 키 입력 칸은 비워 둔다. 공개 API를 아직 준비하지 않은 리허설은 로컬 URL로 확인하고 제출 방식은 강의자 공지를 따른다. 레포트·발표 제출은 이 실습에 없다.

## 먼저 끝났다면

삭제할 글의 ID와 내용을 확인창에 함께 보여 준다. 서버에 저장된 글은 페이지를 새로고침해도 유지되는지 확인한다.
