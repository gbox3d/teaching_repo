# 6주차 실습 — 상태 기반 할 일 CRUD

정답 코드를 한 번에 찾지 말고, 각 단계에서 예상 상태를 적은 뒤 한 기능씩 검증한다. starter의 `TODO`가 작업 지점이다.

## 준비

1. [starter](examples/starter/)를 로컬 서버로 연다.
2. DevTools의 Console, Elements, Application → Local Storage를 열어 둔다.
3. 첫 commit을 만든다: `chore: start week06 dom crud`
4. 구현 전 데이터 모양을 적는다.

```js
{ id: "고유 문자열", title: "할 일", done: false }
```

## 1일차 60분 — Create·Read·Delete

### 문제

사용자가 form에 제목을 입력하면 항목이 추가되고, 목록의 삭제 버튼으로 정확한 항목 하나를 삭제할 수 있게 한다. 배열이 비면 empty 안내를 보여 준다.

### 시간 상자

| 시간 | 활동 | 남길 관찰 |
|---:|---|---|
| 0–8분 | 요구사항 읽기, 상태 예측 | 입력 전후 `todos` 모양 |
| 8–23분 | `render()` 구현 | 0개/1개/2개 DOM |
| 23–38분 | submit과 검증 | 유효/공백 입력 비교 |
| 38–50분 | id 기반 삭제 | 같은 제목 두 개 테스트 |
| 50–57분 | 실패 경로 수정 | Console 오류 0개 |
| 57–60분 | commit·증거 | 화면 캡처와 commit id |

### 필수 요구사항

- `render()`는 현재 배열 전체를 기준으로 목록을 만든다.
- 사용자 제목은 `textContent`로 출력한다.
- 유효한 제출은 `{ id, title, done }` 객체 하나를 추가한다.
- 빈 문자열과 공백만 있는 문자열은 추가하지 않는다.
- 성공한 뒤 입력창을 비우고 focus를 돌려준다.
- 각 항목에는 `data-id`와 삭제 버튼이 있다.
- 삭제는 `id`가 일치하는 항목만 제외한다.
- 0개일 때 empty 안내가 보인다.

### 단계별 힌트

**힌트 1 — 방향**

`form submit → trim → 새 객체 → 새 배열 → render` 순서로 함수 이름만 먼저 적는다.

**힌트 2 — DOM**

`document.createElement("li")`, `element.dataset.id`, `element.textContent`, `append`를 조사한다.

**힌트 3 — 삭제**

버튼의 `data-id`를 읽은 뒤 `todos.filter(...)`의 조건이 “남길 항목”을 뜻한다는 점을 확인한다.

### 검증표

- [ ] `"DOM 복습"`을 추가하면 배열 길이와 `<li>` 수가 모두 1 증가한다.
- [ ] `"   "` 제출 뒤 배열 길이는 그대로이고 안내 문구가 보인다.
- [ ] 같은 제목 두 개 중 두 번째 삭제 버튼을 누르면 하나만 사라진다.
- [ ] 마지막 항목 삭제 뒤 empty 안내가 다시 나타난다.
- [ ] 키보드 Enter로 추가할 수 있다.
- [ ] Console에 처리하지 않은 오류가 없다.

## 2일차 60분 — Update·저장·복구

### 문제

완료 상태와 제목을 수정하고, 변경 때마다 `localStorage`에 저장한다. 시작할 때 데이터를 복원하되 손상된 값 때문에 앱 전체가 멈추지 않아야 한다.

### 시간 상자

| 시간 | 활동 | 남길 관찰 |
|---:|---|---|
| 0–7분 | 전날 코드 재검증 | Create/Delete 통과 |
| 7–20분 | 완료 전환 | 대상 id와 전후 객체 |
| 20–35분 | 편집·저장·취소 | `editingId` 전이 |
| 35–47분 | save/load 연결 | 새로고침 전후 비교 |
| 47–55분 | 손상값 복구 | 사용자 메시지와 Console |
| 55–60분 | commit·회고 | 실패 원인 한 문장 |

### 필수 요구사항

- 목록 하나의 click handler가 `data-action`을 읽어 동작을 분기한다.
- 완료 전환은 해당 id 객체의 `done`만 바꾼다.
- 수정 시작 시 기존 제목을 입력값으로 제공한다.
- 공백 제목으로 저장할 수 없고, 취소하면 원래 제목이 유지된다.
- 모든 성공한 Create/Update/Delete 뒤 저장한다.
- 시작 시 저장값을 배열인지 확인한다.
- JSON 파싱 실패 시 빈 배열로 복구하고 사용자에게 알린다.
- 존재하지 않는 id 요청은 조용히 다른 항목을 바꾸지 않는다.

### 단계별 힌트

**힌트 1 — 동작 분기**

`button.dataset.action`을 `toggle`, `edit`, `delete` 같은 문자열로 두고 먼저 Console에 출력한다.

**힌트 2 — Update**

`map`에서 대상이면 `{ ...todo, 바꿀속성: 새값 }`, 아니면 기존 `todo`를 반환한다.

**힌트 3 — 저장**

저장은 배열 → JSON 문자열, 복원은 문자열 → 값 → 배열 여부 확인의 역순이다. `null`, 깨진 JSON, 객체 세 경우를 각각 생각한다.

### 실패 경로 재현

Application → Local Storage에서 starter가 정한 key 값을 다음처럼 바꾸고 새로고침한다.

```text
{broken
```

앱이 빈 상태로 열리고 복구 안내가 보여야 한다. 확인 후 정상 값으로 다시 저장한다.

### 검증표

- [ ] 첫 번째 항목 완료 전환이 두 번째 항목에 영향을 주지 않는다.
- [ ] 수정 저장과 취소가 구분된다.
- [ ] 공백 수정은 거부된다.
- [ ] 새로고침 후 제목과 완료 상태가 유지된다.
- [ ] 손상 저장값에서도 form을 다시 사용할 수 있다.
- [ ] 마우스 없이 주요 동작을 수행할 수 있다.

## 제출 증거

- 공개 URL 또는 로컬 실행 안내
- 1일차와 2일차 commit id
- 정상 CRUD 화면 1장
- 공백 입력 또는 손상 저장값 처리 화면 1장
- “상태와 DOM이 어긋났던 오류”의 원인·해결 각 한 문장

## 확장 주제

기본 검증을 모두 통과한 뒤 하나를 선택한다.

1. 전체/진행/완료 filter와 남은 개수 표시
2. Escape 편집 취소와 focus 복원
3. 삭제 직후 5초 동안 실행 취소
4. 저장 데이터에 `version`을 두고 이전 모양을 변환
5. `innerHTML`과 `textContent`의 사용자 입력 처리 차이 실험
