# 중간 개인 실기

## 1일차: 요구사항을 실행 순서로 바꾸기

이 자료에는 실제 학기 문제나 정답이 없다.

---

## 평가하는 통합 흐름

```text
Git 저장소
   ↓
시맨틱 HTML + 반응형 CSS
   ↓
사용자 event → 검증 → JavaScript state → DOM
   ↓
실행 확인 + 제출 증거
```

한 영역의 실패가 다음 영역에 어떤 영향을 주는지 설명할 수 있어야 한다.

---

## 문제지를 받으면 먼저 분류

| 표시 | 뜻 | 예 |
|---|---|---|
| S | 구조 | heading, form, list |
| V | 시각 | layout, narrow viewport, focus |
| B | 동작 | event, state, render |
| E | 경계 | empty, validation, missing target |
| P | 제출 | commit, URL, 파일 |

아직 코드를 쓰지 말고 검증 가능한 문장으로 바꾼다.

---

## 요구사항을 테스트 문장으로

모호함:

> 항목을 추가할 수 있다.

검증 문장:

> 유효한 입력을 제출하면 상태 길이와 목록 항목 수가 각각 1 증가한다.

> 공백만 제출하면 상태가 바뀌지 않고 이유가 화면에 나타난다.

---

## 최소 수직 조각부터

```text
HTML 요소 존재
  → selector 성공
  → event 1회 발생
  → state 1개 변경
  → 화면 1개 출력
```

처음부터 모든 CSS나 모든 기능을 끝내지 않는다. 한 경로를 처음부터 끝까지 연결한 뒤 확장한다.

---

## 상태와 render의 기준선

```js
let items = [];

function render() {
  // 현재 items만 보고 화면을 만든다.
}
```

- DOM을 임시 저장소처럼 사용하지 않는다.
- 제목이 같은 항목도 구분할 id가 필요하다.
- 사용자 문자열은 `textContent`로 출력한다.

---

## 제한 시간 배분 예

| 구간 | 할 일 |
|---:|---|
| 0–8분 | 문제 표시, 파일·실행 확인 |
| 8–20분 | 의미 구조와 기본 style |
| 20–40분 | 핵심 event-state-render |
| 40–50분 | 경계·오류 상태 |
| 50–57분 | viewport·키보드·Console |
| 57–60분 | 저장·commit·제출 확인 |

막힌 기능 하나에 전체 시간을 쓰지 않는다.

---

## 진단 순서는 고정한다

1. HTML 요소와 id/name이 있는가?
2. selector 결과가 `null`인가?
3. event가 한 번 발생하는가?
4. 입력값이 기대와 같은가?
5. state가 바뀌는가?
6. `render()`가 호출되는가?
7. Console 첫 오류는 무엇인가?

---

## 1일차 활동

공개용 모의 요구사항으로 60분을 측정한다.

- 기능별 완료 시각 기록
- 공백·empty·좁은 화면 확인
- 해결하지 못한 항목도 원인 위치 기록

목표는 암기가 아니라 **재현 가능한 해결 순서**다.

---

# 2일차: 검증하고 제출하기

“내 컴퓨터에서 한 번 보였다”와 “채점 가능한 제출”은 다르다.

---

## 시작 전 환경 점검

- 지정 폴더와 starter 버전
- 브라우저와 DevTools
- Git 사용자·현재 branch·working tree
- 로컬 서버 URL
- 제출 경로와 마감 시각

시험별 허용 자료와 네트워크 규칙은 LMS 공지를 따른다.

---

## 정상 화면만 보지 않는다

| 경로 | 입력/조건 | 기대 |
|---|---|---|
| normal | 유효 입력 | 상태·화면 변경 |
| validation | 공백 | 변경 없음 + 안내 |
| empty | 데이터 0개 | 다음 행동 안내 |
| missing | 없는 대상 id | 다른 데이터 보존 |
| responsive | 좁은 viewport | 가로 넘침 없음 |

---

## 접근성은 별도 장식이 아니다

- form label과 input 연결
- 동작은 button 사용
- Enter 제출
- 보이는 `:focus-visible`
- 상태 변화는 `role="status"`로 전달
- heading 순서와 landmark

키보드 검증은 event 구조 검증이기도 하다.

---

## Git 제출의 세 상태

```text
working tree → stage → commit
```

```bash
git status
git diff
git diff --staged
git log -1 --oneline
```

commit하지 않은 최신 변경이 제출에서 빠지지 않았는지 확인한다.

---

## 배포 확인은 새 환경에서

1. 제출 URL을 새 탭 또는 시크릿 창에서 연다.
2. 강력 새로고침한다.
3. Network 404를 확인한다.
4. 파일명 대소문자와 상대 경로를 확인한다.
5. 핵심 동작을 다시 수행한다.

로컬 cache가 성공을 가장할 수 있다.

---

## 오류가 나면 첫 원인을 기록

나쁜 보고:

> 안 됩니다.

좋은 보고:

> submit event는 발생하지만 selector가 `null`이어서 state 변경 전 중단됩니다.

관찰 사실과 추측을 구분하면 복구가 빨라진다.

---

## 마지막 5분 체크

- [ ] 요구사항별 정상·경계 검증
- [ ] Console의 처리하지 않은 오류 0개
- [ ] 좁은 화면과 키보드
- [ ] 모든 파일 저장
- [ ] `git status`와 마지막 commit
- [ ] 제출 파일/URL 재열기

---

## 평가의 핵심

완성 기능 수만 보는 것이 아니다.

- 의미 있는 구조
- 예측 가능한 상태 흐름
- 실패를 처리한 근거
- 재현 가능한 Git·실행 결과
- 본인이 설명할 수 있는 구현

실제 문항은 시험 당일 비공개 자료를 따른다.
