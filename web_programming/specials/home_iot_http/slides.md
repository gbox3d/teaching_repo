# HTTP로 제어하는 홈 IoT

Node.js 가상 거실에서 요청·상태·제어 정책을 연구한다.

- 전등과 선풍기를 HTTP로 제어한다.
- 수동 제어에서 주기적 조회와 자동 제어로 확장한다.
- 같은 입력으로 정책을 비교하고 실패·복구를 관찰한다.
- 방학 중 연구 수업이며 진행 시간과 차시 수를 고정하지 않는다.

[연구 실습지](lab.md) · [따라하기](walkthrough.md)

---

## 기초 구현과 연구 단계

| 단계 | 도달 기준 |
|---|---|
| 요청과 상태 | GET·PATCH 요청과 응답을 설명한다. |
| 센서 값과 판단 | 온도와 비교 기준으로 팬 상태를 정한다. |
| 주기적 조회 | 간격·요청 수·반응 지연을 비교한다. |
| 정책 비교 | 단일 기준과 히스테리시스를 같은 입력으로 시험한다. |
| 실패와 복구 | 재시도와 중지 동작을 관찰한다. |

각 단계의 관찰에서 다음 실험을 정한다. 자료 분량은 제한하지 않는다.

---

## 서버가 상태를 보관한다

브라우저 → HTTP 요청 → Node 서버 → JSON 응답 → 화면

- 서버는 전등·선풍기·온도를 메모리에 보관한다.
- 대시보드와 학생 화면은 같은 서버를 사용한다.
- 온도는 학생이 입력하는 모의 센서 값이다.
- 팬을 켜도 온도가 자동으로 내려가지 않는다.
- 서버 재시작 시 장치 상태와 요청 기록은 초기화된다.

---

## 로컬 서버 실행

현재 폴더: home_iot_http, 준비: Node.js 24 이상

```bash
node examples/simulator/server.mjs
```

- http://localhost:8014/ 에서 가상 거실을 연다.
- 별도 패키지 설치나 외부 계정은 필요 없다.
- 특강 폴더 전체가 있어야 예제 링크가 동작한다.
- 실행 확인은 로컬 URL에서 한다. GitHub Pages는 Node 서버를 실행하지 않는다.

## ex01: GET으로 현재 상태 읽기

```js
const response = await fetch('/api/state');
if (!response.ok) throw new Error('상태를 읽지 못했습니다.');
const state = await response.json();
```

- 첫 await는 응답을, 두 번째 await는 JSON 해석을 기다린다.
- GET은 서버에 저장된 현재 상태를 읽는다.
- /examples/ex01/에서 온도 변경 전후 응답을 비교한다.

---

## JSON과 Network를 대조한다

```js
state.light.on                    // true 또는 false
state.light.brightness            // 0~100 정수
state.fan.on                      // true 또는 false
state.environment.temperature     // 10~40 숫자
```

F12 → Network → 상태 조회 버튼

요청 메서드 GET, 경로 /api/state, 응답 번호 200과 JSON을 확인한다.
화면에 보이는 값과 서버 응답이 같은지 대조한다.

---

## ex02: PATCH로 전등 변경

```js
const response = await fetch('/api/devices/light', {
  method: 'PATCH',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ on: true, brightness: 65 })
});
```

/examples/ex02/app.js에서 밝기를 20과 90으로 바꾼다.
저장 → 새로고침 → 버튼 실행 후 요청 본문과 상태를 확인한다.

## 잘못된 요청과 상태 보존

밝기 101을 보내고 정상 요청과 비교한다.

| 확인 대상 | 예상 결과 |
|---|---|
| 응답 번호 | 400 |
| 응답 내용 | 허용 범위 안내 |
| 서버 밝기 | 직전의 유효한 값 유지 |

fetch는 HTTP 400만으로 예외를 던지지 않는다.
response.ok를 확인하고 Network에서 실패 응답을 읽는다.

## ex03: 온도를 읽고 한 번 판단

```js
const shouldRun = state.environment.temperature >= 28;
await fetch('/api/devices/fan', {
  method: 'PATCH',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ on: shouldRun })
});
```

온도 27°C와 29°C를 적용하고 버튼을 각각 누른다.
판단 기준을 30°C로 바꾸면 같은 입력의 결과가 달라진다.
이 예제는 버튼을 누를 때만 검사한다.

## 자동 제어 화면에서 주기적 조회

주소: /examples/automatic/

- 단일 기준 27.5°C, 조회 완료 뒤 대기 2000ms로 시작한다.
- 온도와 실제 팬 상태를 읽어 다음 팬 상태를 결정한다.
- 실제 상태와 판단 결과가 다를 때만 PATCH를 보낸다.
- 조회 횟수와 제어 횟수는 따로 누적된다.
- 자동 제어 화면은 하나만 실행한다.

다른 화면도 제어하면 어느 정책이 상태를 바꿨는지 구분하기 어렵다.

---

## 한 검사가 끝난 뒤 다음 검사 예약

```text
GET → 판단 → 필요한 경우 PATCH → 대기 → 다음 GET
```

- 실행기는 setTimeout으로 다음 검사를 예약한다.
- GET이나 PATCH가 진행 중이면 다음 검사를 시작하지 않는다.
- 실제 주기는 요청 처리 시간과 설정한 대기 시간의 합이다.
- 시작 버튼은 실행 중 비활성화된다.
- 중지하면 예약과 진행 중인 응답 대기를 취소한다.

반복 타이머를 추가하기 전에 runner.js의 예약 위치를 찾는다.

## 실험: 조회 간격과 반응 지연

같은 온도 입력 순서를 500·2000·5000ms 간격으로 비교한다.

| 변경 변수 | 고정 조건 | 관찰 |
|---|---|---|
| 조회 대기 간격 | 정책·입력 순서·관찰 구간 | GET 수·반응 지연 |

조회 직후와 다음 조회 직전에 각각 온도를 바꾼다.
짧은 간격에서 요청 수와 입력 반영 지연이 어떻게 달라지는지 기록한다.
Network와 화면의 관찰 기록을 함께 사용한다.

---

## 단일 기준은 경계에서 상태가 바뀐다

```js
return temperature >= settings.threshold;
```

기준 27.5°C에서 27.4 → 27.6 → 27.4 → 27.6°C를 입력한다.

- 각 입력이 조회된 다음 다음 값을 적용한다.
- 경계를 넘을 때마다 팬 상태가 바뀐다.
- 입력이 경계 근처에서 흔들릴수록 전환이 잦아질 수 있다.

온도 슬라이더는 0.1°C 단위다. 방향키로 미세 조정한다.

---

## 히스테리시스는 두 경계를 사용한다

```js
if (temperature >= settings.high) return true;
if (temperature <= settings.low) return false;
return currentOn;
```

- 상한 29°C 이상: 켜기
- 하한 26°C 이하: 끄기
- 26°C 초과, 29°C 미만: 이전 상태 유지

같은 27°C여도 이전 상태에 따라 결과가 달라진다.

---

## 같은 입력으로 두 정책 비교

초기 조건: 팬 정지, 온도 26°C, 다른 자동 제어 화면 중지

```text
26 → 27 → 28 → 27 → 28 → 29 → 28 → 27 → 26°C
```

1. 단일 기준 27.5°C에서 입력 순서를 실행한다.
2. 기록을 저장하고 초기 조건을 다시 맞춘다.
3. 하한 26°C·상한 29°C의 히스테리시스로 반복한다.
4. 팬 상태 변화와 제어 횟수의 차를 설명한다.

각 온도가 관찰 기록에 나타난 뒤 다음 값을 적용한다.

---

## 누적 기록과 실험 구간 구분

시작·중지는 횟수와 관찰 기록을 초기화하지 않는다.

- 실험별 기록을 다운로드하고 새로고침해 분리한다.
- 또는 시작 전·종료 후 조회 및 제어 횟수의 차를 기록한다.
- 새로고침 전에는 필요한 기록을 저장한다.
- 다운로드 기록의 시작·중지 항목과 설정을 대조한다.

단일 기준 실험의 누적 횟수를 히스테리시스만의 결과로 읽지 않는다.

## 학생 정책 함수 작성

편집 파일: examples/automatic_student/policy.js

```js
function decideFan(temperature, currentOn, settings) {
  // 단일 기준 / 상한 / 하한 / 이전 상태 유지
  return null; // TODO 완성 후 true 또는 false 반환
}
```

HTTP·시작·중지·재시도는 제공 실행기를 사용한다.
미완성 함수가 null을 반환하면 안내 후 중지된다.
두 정책을 구현하고 같은 입력 순서로 참고본과 비교한다.

## 통신 실패와 상태 값 구분

실패했다고 온도가 0°C이거나 팬이 정지했다고 판단하지 않는다.

- 마지막 성공 응답: 마지막으로 확인한 장치 상태
- 통신 실패: 현재 상태를 확인하지 못함
- 재시도 대기: 다음 요청을 보내기 전 대기

한 검사의 응답 대기는 3초로 제한한다.
AbortController는 브라우저의 응답 대기를 취소한다.
이미 서버에 적용된 PATCH를 취소하거나 되돌리지는 않는다.

---

## 실패가 이어지면 대기 간격 증가

기본 대기 2000ms에서 연속 실패를 관찰한다.

```text
실패 → 4000ms → 실패 → 8000ms → 실패 → 10000ms
```

- 재시도 대기는 최대 10000ms다.
- 요청을 마친 뒤에만 다음 재시도를 예약한다.
- 성공하면 연속 실패 수를 비우고 정상 간격으로 돌아간다.
- 중지하면 복구 후에도 자동으로 다시 시작하지 않는다.

실패 중 요청이 겹치거나 즉시 반복되는지 Network로 확인한다.

---

## 실험: 서버 중단과 복구

1. 자동 제어를 시작하고 Network의 Preserve log를 켠다.
2. 서버 터미널에서 Ctrl+C로 종료한다.
3. 브라우저를 새로고침하지 않고 실패·재시도 간격을 기록한다.
4. 같은 명령으로 Node 서버를 다시 시작한다.
5. 다음 재시도 성공과 정상 간격 복귀를 확인한다.

서버 메모리는 초기화된다. 온도 24°C·팬 정지로 돌아온다.
이 변화와 자동 제어 정책이 만든 변화를 구분한다.

---

## 실험: 실패 중 중지

- Network를 Offline으로 바꾸고 통신 실패를 확인한다.
- 자동 제어 화면에서 중지를 누른다.
- Offline을 해제하고 새 요청이 생기는지 확인한다.
- 시작을 눌러야 자동 제어가 다시 동작한다.

느린 연결은 Network throttling으로 추가 실험한다.
중지 전에 보낸 PATCH는 서버에서 이미 적용되었을 수 있다.
재연결 후 GET으로 실제 상태를 확인한다.

## 관찰 자료의 범위

| 자료 | 보관 범위 |
|---|---|
| 대시보드 요청 기록 | 최근 PATCH 12건, GET 제외 |
| 자동 제어 화면 | 최근 관찰 30건 |
| 관찰 JSON 다운로드 | 최근 관찰 500건 |
| Network | 브라우저 설정과 기록 상태에 따름 |

페이지 새로고침은 관찰 기록을 비운다. 긴 실험은 중간에 저장한다.
화면 캡처·코드·Network·JSON을 필요한 만큼 남긴다.

## 연구 기록

| 항목 | 기록 내용 |
|---|---|
| 가설 | 변경 후 예상하는 차이 |
| 변경 변수 | 이번 실험에서 바꾼 조건 |
| 고정 조건 | 시작 상태·입력 순서·다른 제어 화면 |
| 관찰 | 시각·상태·요청 수·실패와 복구 |
| 해석과 한계 | 가설을 지지하는 결과·반례·모델의 한계 |

관찰과 해석을 구분하고 설명되지 않은 차이는 다음 실험으로 남긴다.

---

## 이 시뮬레이터의 범위

- 가상 온도는 학생이 입력한다. 물리적 냉각 모델은 없다.
- 전환 수가 적어도 냉각 성능 향상을 입증한 것은 아니다.
- 브라우저 타이머는 정확한 실시간 제어 주기를 보장하지 않는다.
- 실제 장치의 센서 오차·전력·네트워크 조건은 포함하지 않는다.
- 이 특강은 15주 시험 범위에 포함하지 않는다.

실제 냉각 연구에는 열 유입·열용량·팬 효과를 정의한 모델이 필요하다.

## 후속 실험 설계

- 하한·상한 간격을 바꾸고 상태 유지 구간과 전환 수를 비교한다.
- 같은 입력을 반복해 결과의 재현성을 확인한다.
- 조회 간격과 통신 지연의 영향을 나누어 측정한다.
- 온도와 밝기 조건을 함께 사용한 제어 정책을 작성한다.
- 수동 입력 실험과 물리 모델 실험을 구분해 설계한다.
