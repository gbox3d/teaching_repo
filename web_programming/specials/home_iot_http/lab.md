## 단계 1: 요청과 상태

현재 폴더: home_iot_http. node examples/simulator/server.mjs로 시작한다.
대시보드 http://localhost:8014/와 ex01·ex02를 나란히 연다.

1. ex01에서 GET 응답의 light.brightness와 environment.temperature를 찾는다.
2. 대시보드에서 밝기나 온도를 적용한 뒤 다시 GET으로 읽는다.
3. ex02의 밝기 65를 20과 90으로 바꾸어 요청 본문과 빛의 세기를 비교한다.
4. 밝기 101을 요청한다. 오류 응답과 변경되지 않은 상태를 확인하고 유효한 값으로 되돌린다.

도달 기준: 화면을 먼저 바꾼 결과와 서버 응답으로 확인한 결과를 구분한다. 메서드·주소·본문·응답 번호를 Network에서 찾는다.

## 단계 2: 센서 값으로 제어

ex03은 GET → 비교 → PATCH 순서로 한 번 제어한다. 온도를 적용한 다음 버튼을 눌러야 새 판단이 일어난다.

1. 온도 27°C와 29°C에서 기본 기준 28°C의 동작을 비교한다.
2. 기준을 30°C로 바꾼 뒤 같은 온도를 다시 입력한다.
3. examples/student/app.js의 TODO를 채운다. 상태 읽기, 전등 밝기 40%, 온도 기준 27°C를 구현한다.
4. 26°C와 29°C에서 자신이 쓴 제어 코드를 확인한다.

도달 기준: 온도·비교 기준·현재 팬 상태를 구분한다. 팬을 켜도 모의 온도가 그대로인 이유를 설명한다.

## 단계 3: 주기적 조회

대시보드에서 자동 제어 연구를 열고 단일 기준 27.5°C를 선택한다. 자동 제어 화면은 하나만 시작한다.

1. 조회 완료 뒤 대기 간격을 2000ms로 두고 시작한다. Network에서 GET 사이 간격을 확인한다.
2. 온도를 적용한 시각과 제어가 반영된 시각을 비교한다. 입력은 조회 직후와 직전에 각각 적용해 본다.
3. 중지하고 간격을 500ms와 5000ms로 바꾸어 같은 실험을 반복한다.
4. 같은 관찰 구간의 요청 수와 반응 지연을 기록한다. 예를 들어 20초를 측정 구간으로 사용할 수 있다. 이는 수업 시간 제한이 아니다.
5. 시작을 반복해서 눌러도 조회가 중복되지 않는지 확인한다. 중지 후 새 요청이 생기지 않는지 확인한다.

실행기는 한 검사의 GET과 필요한 PATCH를 모두 마친 뒤 setTimeout으로 다음 검사를 예약한다. 실제 주기는 응답에 걸린 시간과 설정한 대기 시간의 합이다.
변경할 상태가 같으면 PATCH를 보내지 않는다. 조회 횟수와 제어 횟수가 다른 이유를 기록한다.

도달 기준: 간격을 짧게 했을 때 요청 수와 반응 지연이 어떻게 달라지는지 관찰 근거로 설명한다.

## 단계 4: 단일 기준과 히스테리시스

단일 기준은 27.5°C 이상에서 켜고 미만에서 끈다. 히스테리시스는 29°C 이상에서 켜고 26°C 이하에서 끄며 그 사이에서는 이전 상태를 유지한다.

각 실험 전에 자동 제어를 중지하고 대시보드에서 팬을 정지한다. 온도 26°C를 적용한 뒤 시작한다.
조회·제어 횟수와 관찰 기록은 시작·중지를 반복해도 누적된다. 실험을 바꿀 때 기록을 다운로드하고 자동 제어 화면을 새로고침하거나, 시작 전과 종료 후 횟수의 차를 사용한다.
아래 순서를 두 방식에 똑같이 적용한다. 각 값을 적용한 뒤 자동 제어의 관찰 기록에 그 값이 나타난 것을 확인하고 다음 값으로 넘어간다.

| 입력 순서 | 26 | 27 | 28 | 27 | 28 | 29 | 28 | 27 | 26 |
|---|---|---|---|---|---|---|---|---|---|
| 단일 기준 팬 상태 | 기록 | 기록 | 기록 | 기록 | 기록 | 기록 | 기록 | 기록 | 기록 |
| 히스테리시스 팬 상태 | 기록 | 기록 | 기록 | 기록 | 기록 | 기록 | 기록 | 기록 | 기록 |

1. 단일 기준 실험 기록을 다운로드한다.
2. 중지한 뒤 히스테리시스와 하한 26·상한 29를 선택한다. 팬과 온도를 초기 조건으로 맞추고 같은 순서로 진행한다.
3. 두 기록의 제어 횟수를 비교한다. 유지된 상태도 함께 본다.
4. examples/automatic_student/policy.js의 TODO 3개를 채운다. 실행기는 그대로 두고 판단 함수만 작성한다.
5. 작성한 정책으로 두 방식을 재현한다. 그다음 하한·상한의 간격을 바꾸어 새 가설을 시험한다.

경계 근처 실험에서는 27.4°C와 27.6°C를 번갈아 적용한다. 대시보드 온도 슬라이더의 간격은 0.1°C다. 슬라이더에 초점을 두고 방향키로 미세 조정한 뒤 온도 적용을 누른다.

도달 기준: 같은 온도라도 이전 상태에 따라 결과가 달라지는 구간을 찾아 설명한다. 전환 횟수가 줄었다고 실제 냉각 성능이 좋아졌다고 결론짓지 않는다.

## 단계 5: 통신 실패와 복구

기본 조회 간격은 2000ms로 둔다. Network의 Preserve log를 켜고 자동 제어를 시작한다.

1. Node 서버 터미널에서 Ctrl+C를 눌러 서버를 종료한다. 자동 제어 페이지는 새로고침하지 않는다.
2. 관찰 기록에서 실패와 재시도 대기 간격을 확인한다. 기본 설정에서는 실패가 이어질 때 4000→8000→10000ms로 늘어나고 10000ms를 넘지 않는다.
3. 같은 명령으로 서버를 다시 시작한다. 다음 재시도에서 조회가 복구되고 정상 대기 간격으로 돌아오는지 확인한다.
4. 서버 재시작 후 온도가 24°C, 팬이 정지 상태로 초기화된 것을 확인한다. 원하는 실험 온도를 다시 적용한다.
5. 별도 실험에서는 Network의 Offline을 적용한 뒤 중지 버튼을 누른다. Offline을 해제해도 자동으로 재시작하지 않는지 확인한다.

실행기는 한 검사의 응답 제한 시간을 3초로 두며 AbortController로 기다림을 취소한다. 느린 연결 실험은 Network throttling으로 추가할 수 있다. 실패 시 브라우저가 표시하는 문구는 버전에 따라 달라질 수 있다.
중지는 새 요청과 예약을 취소한다. 이미 서버에 도착해 적용된 PATCH까지 되돌리는 동작은 아니다.

도달 기준: 통신 실패를 센서 값 0이나 팬 정지로 간주하지 않는다. 마지막 확인 상태, 통신 상태, 재시도 대기를 구분해 해석한다.

## 연구 기록

| 항목 | 적을 내용 |
|---|---|
| 가설 | 무엇을 바꾸면 어떤 차이가 생길 것으로 보는가 |
| 변경 변수 | 기준 온도·조회 간격·제어 방식·통신 상태 중 이번에 바꾼 것 |
| 고정 조건 | 시작 온도·팬 상태·입력 순서·다른 제어 화면 중지 여부 |
| 관찰 | 입력 시각, 상태 변화, GET/PATCH 수, 실패와 복구, 기록 파일 |
| 해석과 한계 | 가설을 지지하는 결과, 반례, 센서·물리 모델이 없는 한계 |

화면 캡처·코드 변경·Network 기록·관찰 JSON을 필요한 만큼 남긴다. 분량을 맞추기 위한 항목 추가나 캡처 수 제한은 없다.
대시보드 기록은 최근 PATCH 12건뿐이다. 자동 제어 화면은 최근 30건, 다운로드는 최근 500건이며 새로고침하면 사라진다. 긴 실험은 중간에 기록을 다운로드한다.

## 막혔을 때

| 증상 | 확인할 것 |
|---|---|
| localhost 연결 실패 | Node 서버 실행 여부와 포트 번호 |
| HTTP 400 | 숫자·불리언 형식과 허용 범위 |
| 온도를 바꿔도 제어가 그대로임 | 온도 적용 여부, 기초 예제의 재클릭 또는 자동 제어 시작 여부 |
| 팬이 예상과 반대로 바뀜 | 자동 제어 탭이 둘 이상 실행 중인지 확인 |
| 학생 자동 제어가 즉시 중지됨 | policy.js가 true 또는 false를 반환하는지 확인 |
| 복구가 바로 일어나지 않음 | 실패 후 재시도 대기 중인지 확인, 상한은 10초 |
| 재시작 뒤 온도가 달라짐 | 서버 메모리 상태의 초기화 여부 |

## 후속 연구

- 동일한 온도 순서를 여러 차례 반복하고 전환 횟수가 같은지 확인한다.
- 하한·상한 간격을 넓힐 때 전환 수와 상태 유지 구간이 어떻게 달라지는지 비교한다.
- 조회 주기와 통신 지연을 함께 바꾸고, 요청 예약 방식이 만드는 차이를 분석한다.
- 온도와 전등 밝기 설정을 함께 쓰는 제어 조건을 작성한다.
- 물리적 냉각을 연구하려면 열 유입·방의 열용량·팬의 효과를 정의한 별도 모델이 필요하다. 현재 수동 온도 입력 결과와 혼동하지 않는다.
