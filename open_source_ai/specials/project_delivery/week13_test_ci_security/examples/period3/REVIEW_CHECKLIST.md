# 교차 코드리뷰 체크리스트

다른 사람(다른 팀)의 PR을 받아들이기 전에 확인할 항목이다. 리뷰어는 이 목록을 위에서부터 훑고,
**근거가 있는 항목만** 코멘트로 남긴다. 판정은 `승인(Approve)` 또는 `수정 요청(Request changes)` 중 하나다.
리뷰는 코드에 대해 하는 것이지 사람에 대해 하는 것이 아니다(2주차 규칙).

## 0. 리뷰 전 3분

- [ ] PR 제목·설명만 읽고 "무엇을 왜 바꿨는가"를 한 문장으로 말할 수 있다. 없으면 첫 코멘트로 설명을 요청한다.
- [ ] PR이 연결한 Issue가 있고, 변경 범위가 그 Issue를 넘지 않는다.
- [ ] 변경 파일 수·줄 수가 30분 안에 읽을 크기다. 너무 크면 나누어 달라고 요청한다.

## 1. 자동 검사(CI)

- [ ] PR의 상태 체크가 초록불이다. 빨간불이면 로그의 **실패한 step 이름과 첫 오류 줄**을 코멘트에 붙인다.
- [ ] 새 기능·버그 수정에 대응하는 테스트가 추가되었거나, 없어도 되는 이유가 설명에 있다.
- [ ] 테스트가 실제 모델 서버 없이 돈다(가짜 클라이언트 주입). 실제 서버가 필요한 테스트는 `integration` 마커가 붙어 있다.
- [ ] `ruff check`·`ruff format --check`를 통과했다. 수동으로 스타일을 지적하지 않는다 — 도구가 하게 둔다.

## 2. 코드

- [ ] 함수 하나가 한 가지 일을 한다. 이름만 읽고 무엇을 하는지 알 수 있다.
- [ ] 오류 경로가 있다: 연결 실패·모델 없음·시간 초과가 사람이 읽을 메시지나 상태 코드로 나온다.
- [ ] 설정(모델 이름·주소·경로)이 코드에 박혀 있지 않고 환경변수 + 기본값으로 읽힌다.
- [ ] 같은 논리가 두 곳에 복사되어 있지 않다.
- [ ] `outputs/`·`.venv/`·`__pycache__/` 같은 실행 산출물이 커밋되지 않았다.

## 3. 보안·공급망

- [ ] `.env`, 토큰, 비밀번호, 실제 개인정보가 diff에 없다(`security_check.ps1` 결과를 첨부하면 좋다).
- [ ] 새 의존성이 추가되었다면 이름이 정확하고(타이포스쿼팅 아님), 출처(PyPI 페이지·저장소)와 라이선스를 PR 설명에 적었다.
- [ ] `uv.lock`이 `pyproject.toml`과 함께 갱신되었다(의존성을 바꿨을 때).
- [ ] 모델 파일은 safetensors·GGUF이고 pickle 기반 파일(`.pkl`, `.pt`, `.bin`)이 저장소에 들어오지 않았다.
- [ ] `trust_remote_code=True`를 쓴다면 모델 저장소·revision이 고정되어 있고 그 코드를 읽었다는 기록이 있다.

## 4. 라이선스·출처·문서

- [ ] 가져온 코드·데이터·모델의 출처와 라이선스가 `SOURCES.md`(또는 PR 설명)에 있다.
- [ ] 사용법이 바뀌었으면 README의 실행 절차도 함께 바뀌었다.
- [ ] `CHANGELOG`의 `Unreleased`에 한 줄이 추가되었다(14주차부터 필수).

## 코멘트 쓰는 법

코멘트 하나는 **근거 → 문제 → 제안** 순서로 쓴다. 근거는 파일과 줄, 로그 줄, 실행 결과처럼 다른 사람이 확인할 수 있는 것이어야 한다.

```text
[근거] app/service.py 42줄: total_duration 을 1_000 으로 나눈다.
[문제] Ollama 의 total_duration 은 나노초라서 결과가 ms 가 아니라 µs 가 된다. tests/test_service.py 의 1500.0 기대값과 어긋난다.
[제안] 1_000_000 으로 나누고, 단위를 변수 이름(duration_ms)에 남긴다.
```

- 취향 문제는 `제안(nit)`이라고 표시하고 판정에 반영하지 않는다.
- 질문은 질문으로 쓴다("이 분기는 언제 타는가?"). 추측으로 단정하지 않는다.
- 좋은 점도 한 줄 적는다. 무엇이 좋았는지 구체적으로("가짜 클라이언트에 calls 기록을 둔 덕에 옵션 검사가 쉬워졌다").
- 수정 요청은 **어떤 조건이 되면 승인할지** 함께 적는다.
