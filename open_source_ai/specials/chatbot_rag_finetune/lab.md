# 특강 실습 — 기말 챗봇 개선(평가·RAG·파인튜닝)

각 교시는 설명 20분 뒤 아래 실습 30분을 진행하고 10분 쉰다. 1교시에 만든 내 문항과 기록표(점수 줄)를 2~4교시에도 이어 쓴다. 4교시의 `ex07` 점검과 버그 심기는 기록표가 아니라 4교시 절의 표에 적는다. 1교시가 끝나면 내 문항을 고치지 않는다. 고치면 `mine` 줄을 처음부터 다시 잰다. 명령은 `examples/` 또는 `finetune/` 루트에서 실행하고, 교시마다 프로젝트를 복사하지 않는다.

## 준비

수업 전 준비는 [따라하기](walkthrough.md#수업-전-준비)에 있다. `examples/`와 `finetune/`에서 `uv sync`를 실행하고, `qwen3.5:2b`·`bge-m3`를 받고, `uv run prepare`로 학습할 기본 모델을 받는다. GGUF 변환기와 학습 전 모델(`wku-base`) 등록까지 끝내 둔다. 수업 중에는 모델을 내려받지 않는다.

프로젝트 구조는 빈 위치에서 `uv init --package --python 3.12 --vcs none wku-special`로 새 프로젝트를 만들어 `examples/`·`finetune/`과 비교한다. `.python-version`, `pyproject.toml`의 `[project.scripts]`와 `[build-system]`, `src/<패키지>/__init__.py`의 `main()`이 명령을 만든다. scripts를 바꾸면 `uv sync`를 다시 실행한다.

## 1교시 — 내 평가 문항과 실패 분류

문제: 공개 20문항과 내 문항을 같은 채점기로 재고, 전체 평균을 가장 많이 깎은 실패 종류 하나와 고칠 것 하나를 정한다.

| 시간 | 활동 |
|---|---|
| 0~7분 | (examples/) 1. 공개 20문항으로 `ex04`와 `ex02`를 실행하고 점수 대조 |
| 7~15분 | 2. 내 문항 더하기, 3. 내 문항으로 실행 |
| 15~20분 | 4. 실패 종류 표 읽기 |
| 20~25분 | 5. 고칠 감점 하나 고르기, 6. 같은 설정으로 다시 실행 |
| 25~30분 | 7. 기록표 채우기 |

`ex04` 맨 위의 `BOT`은 `"student_bot"`으로 두고 `QUESTION_SET`만 바꾼다. 1단계는 `"public"`이고 3단계부터는 `"mine"`이다.

실행하기 전에 예상을 먼저 적고, 실행한 뒤 관찰을 적는다.

| 확인할 것 | 실행 전 예상 | 관찰 |
|---|---|---|
| 공개 20문항에서 `ex04`와 `ex02`의 범주별·전체 평균이 같은지, 다르면 그 문항 `id` | | |
| 내가 더한 문항의 내용 검사 결과(오류·경고 수와 문항 `id`) | | |
| `mine` 전체 평균이 `public`보다 높은지 낮은지 | | |
| `mine`에서 '전체 평균에서 빠진 점수'가 가장 큰 실패 종류 | | |
| 같은 설정으로 다시 실행했을 때 점수가 바뀐 문항 `id` | | |

단계별 힌트

1. 두 명령은 같은 채점기, 같은 문항, 같은 봇을 쓴다. 점수는 응답만으로 정해지므로 점수가 다르면 응답이 달라진 문항이 있다. 문항별 출력에서 그 문항을 찾는다.
2. 질문 파일과 정답 파일에 같은 `id`로 한 항목씩 더한다. 공개 문항에서 조사만 바꾼 문장, 학습 문항(`train`)과 같은 질문은 쓰지 않는다. 문항을 더하면 [문항 작성 규칙의 검사](examples/src/lab_shared/data/README.md#검사) 시험이 문항 수에서 실패하므로 시험 파일 맨 위의 문항 수 상수도 고친다.
3. 형식이 틀리면 `평가 시작 오류`로, 내용 검사에서 오류가 나오면 평가를 시작하기 전에 멈춘다. 내용 검사 메시지는 앞의 `[문항 id]`부터 본다. `평가 시작 오류` 메시지에 `id`나 파일 이름이 없으면 `uv run python -B -m unittest tests.test_my_data -v`로 짝 없는 `id`나 읽지 못한 파일을 찾는다. 실패한 문항은 `질문`, `응답`, `오류` 줄을 함께 읽는다.
4. 맞힌 사실이 하나도 없는 문항은 잃은 점수를 모두 '사실 누락·불필요한 답'에 넣는다. 한 문항이 사실과 출처 두 줄에 함께 들 수 있어서, 문항 수 열을 더한 값이 실패한 문항 수보다 클 수 있다.
5. 원인 가설은 근거 문서가 모델에 가지 않았다(2교시 `ex05`), 문서는 갔는데 답을 잘못 뽑았다(`SYSTEM_PROMPT`, 3교시 학습), 형식·시간·실행 오류가 났다(4교시 `ex07`) 가운데 하나로 적는다. 형식 오류·시간 초과·실행 오류 문항은 `질문` 줄의 문장을 `ex07`의 `질문>`에 그대로 넣어 본다.
6. 두 실행에서 점수가 다른 문항 `id`를 적는다. 설정을 바꾼 뒤의 차이가 이 변동보다 크지 않으면 개선으로 보지 않는다. Ollama는 기본으로 5분 동안 요청이 없는 모델을 내린다. 두 실행 사이에 5분 넘게 쉬면 모델을 다시 올리므로 설정이 같아도 응답이 달라질 수 있다.
7. '평가 뒤 올라가 있는 모델'에는 앞선 실행이나 다른 프로그램이 올린 모델도 나올 수 있다. `BOT`이 쓰는 모델의 줄만 옮긴다. `student_bot`은 `qwen3.5:2b`를 쓴다. 모델 이름과 digest 앞 12자리를 함께 적는다.

완료 기준

- 기록표에 `student_bot`의 `public`·`mine` 줄과 같은 설정으로 다시 잰 줄이 있다.
- 내가 더한 문항이 내용 검사 오류 없이 채점됐다.
- 가장 큰 감점 종류, 원인 가설, 바꿀 것 하나, 고치면 줄어야 할 문항 `id`를 적었다.

명령, 출력 읽는 법, 기록표 양식, 과제 폴더로 옮기는 방법은 [1교시 안내](examples/period1/README.md)에 있다.

## 2교시 — 임베딩 RAG와 검색 관찰

문제: 낱말 겹침 검색과 임베딩 검색이 정답의 근거 문서를 찾는지 비교하고, 3교시에 쓸 검색 설정 하나를 점수로 정한다.

| 시간 | 활동 |
|---|---|
| 0~5분 | `rag_bot`과 `student_bot`을 나란히 읽고 바뀐 곳 찾기 |
| 5~12분 | (examples/) `uv run ex05`로 두 검색 비교, `SETS`에 `"train"`을 더해 다시 실행 |
| 12~18분 | `ex04`를 `BOT = "rag_bot"`(기본값 `TOP_K = 3`, `MIN_SCORE = 0.0`)으로 `mine`·`public` 한 번씩 실행, 기록표 두 줄 |
| 18~26분 | `TOP_K`나 `MIN_SCORE` 하나만 바꿔 `ex05`와 `ex04`(`mine`·`public`) 다시 실행, 기록표 두 줄 |
| 26~30분 | 3교시에 쓸 검색 설정 하나를 정해 `rag_bot`에 남기고, 기록표에서 그 설정의 두 줄 '바꾼 상수' 칸 끝에 '3교시 사용'을 덧붙이기 |

실행하기 전에 예상을 먼저 적고, 실행한 뒤 관찰을 적는다.

| 확인할 것 | 실행 전 예상 | 관찰 |
|---|---|---|
| 기본값에서 두 검색이 근거를 놓친 문항 수(`mine`·`public`) | | |
| `train`에서 `student_bot`만 놓친 문항 | | |
| 내가 바꾼 설정에서 기본값보다 근거를 더 놓친 문항(`student_bot`은 그대로) | | |
| 정답 문항과 답변 불가 문항의 최고 유사도가 갈리는지 | | |
| 기본값 `rag_bot`의 `mine`·`public` 점수와 1교시 `student_bot` 줄의 차이 | | |

단계별 힌트

1. 상수 블록, 검색 함수, `answer()`를 차례로 비교한다. 요청 본문과 시스템 지시도 같은지 본다.
2. `ex05`의 `놓침`은 정답의 근거 문서가 검색 결과에 없다는 뜻이다. 그 문항은 모델을 바꿔도 맞히기 어렵다.
3. 참고 자료가 문서 5개뿐이라 `TOP_K` 3이면 낱말 겹침 검색도 평가 문항의 근거를 대부분 보낸다. 차이는 `train`이나 직접 바꿔 쓴 질문에서 드러난다.
4. `MIN_SCORE`를 올리면 답변 불가 문항에 보내는 문서가 줄지만, 정답 문항의 문서도 함께 빠질 수 있다. 두 범주의 유사도를 나란히 적어 본다.
5. `rag_bot`을 잴 때 `ex04`의 '기록할 값'에는 `qwen3.5:2b`와 `bge-m3` 두 모델 줄이 나온다. 둘 다 옮기고, '바꾼 상수' 칸에 `TOP_K`·`MIN_SCORE`와 `ex05` 요약(예: 근거 포함 n/m. `public`의 m은 16이고, `mine`의 m은 1교시에 더한 답할 수 있는 문항 수만큼 늘어난다)을 적는다.
6. `EMBED_MODEL`은 수업 중에 바꾸지 않는다. 다른 임베딩 모델은 과제를 할 때 수업 밖에서 받은 뒤 바꾸고, 바꾸면 `ex05`·`ex06`·학습을 다시 실행한다.

2교시 끝에 정한 `TOP_K`·`MIN_SCORE`는 3교시 `ex06`이 `outputs/sft/settings.json`에 남기고, `wku-base`·`wku-lora`도 이 값으로 잰다. 정하지 못했으면 기본값으로 되돌린다.

완료 기준

- 기록표에 `rag_bot`의 기본값과 바꾼 설정 줄이 `mine`·`public` 두 세트로 있다.
- `ex05` 요약(근거를 모두 찾은 문항 수)과 `train`에서 `student_bot`만 놓친 문항을 적었다.
- 3교시에 쓸 검색 설정을 `rag_bot`에 남겼다.

명령과 6주차 예제와의 대응표는 [2교시 안내](examples/period2/README.md)에 있다.

## 3교시 — 학습 예시와 LoRA 학습·등록

문제: `rag_bot`이 보낼 대화로 학습 예시를 만들어 0.5B 모델을 학습·등록하고, 학습 전후를 같은 문항으로 잰다.

| 시간 | 활동 |
|---|---|
| 0~4분 | (examples/) 학습 문항(`src/lab_shared/data/train_questions.json`·`train_answers.json`)을 훑고 `uv run ex06`으로 학습 예시를 만든다. `제외` 줄 기록 |
| 4~6분 | `ollama ps`에 나온 모델을 모두 `ollama stop <이름>`으로 내리고 `cd ../finetune` |
| 6~13분 | (finetune/) `uv run ft01`. 도는 동안 `ft01`의 상수를 7주차 `ex03`과 비교하고, 끝나면 토큰 수·`train_runtime`·GPU 최대 할당 기록 |
| 13~19분 | `uv run ft02` → GGUF 변환 → `ollama create wku-lora -f Modelfile.lora` → `ollama list` 확인 |
| 19~27분 | (examples/) `ex04`(`BOT = "rag_bot"`)에서 `rag_bot`의 `MODEL`을 `"wku-lora"`로 바꿔 `mine`·`public`, `"wku-base"`로 바꿔 `mine`·`public` 실행 |
| 27~30분 | 기록표 정리, 다음에 바꿀 것 하나 적기 |

실행하기 전에 예상을 먼저 적고, 실행한 뒤 관찰을 적는다.

| 확인할 것 | 실행 전 예상 | 관찰 |
|---|---|---|
| 내가 바꾼 검색 설정에서 `ex06`이 뺀 학습 문항과 이유 | | |
| 내 PC의 `ft01` 토큰 수 범위·`train_runtime`과 [따라하기 기준 PC 값](walkthrough.md#기준-pc-실측)의 차이 | | |
| `wku-base`와 `wku-lora`의 형식 오류 수 | | |
| `wku-lora`가 틀린 문항의 `id`와 실패 종류 | | |

단계별 힌트

1. `ex06`이 검색에 `bge-m3`를 써서 Ollama에 모델이 올라가 있다. `ft01`은 Ollama가 올린 모델이 있으면 멈추므로 먼저 내린다. `ft01`이 도는 동안 다른 터미널에서 `ex04`·`ex05`를 실행하지 않는다.
2. 토큰 수는 `ft01` 시작 부분(`모델:` 줄 다음)의 `학습 예시 n건, 토큰 수 최소 … 최대 …` 줄에서, 학습 시간은 끝부분의 `{'train_runtime': …}` 값(초)에서, GPU 메모리는 끝부분의 `GPU 최대 할당 메모리` 줄에서 읽는다.
3. step 시간이 점점 늘면 VRAM이 넘친 것이다. 다른 프로그램의 GPU 사용을 줄이고 `DTYPE`·`GRADIENT_CHECKPOINTING`을 확인한다.
4. 어댑터나 병합 폴더가 이미 있다는 안내가 나오면 `finetune/src/shared`의 `ADAPTER_DIR`·`MERGED_DIR`을 새 이름으로 바꾼다. 변환 명령의 입력 폴더도 새 `MERGED_DIR`로 바꾼다. 그대로 두면 이전 병합 모델을 다시 변환해 등록한다.
5. 학습 전후는 `BOT = "rag_bot"`과 같은 `QUESTION_SET`으로 잰다. 바꾸는 것은 `rag_bot`의 `MODEL` 하나다. `BOT`이 `"student_bot"`이면 `MODEL`을 바꿔도 점수가 달라지지 않는다.
6. `ex06`이 평가 문항과 같은 학습 문항을 알리면 학습 문항 쪽 문장을 바꾼다. 내 문항을 바꾸면 1·2교시 `mine` 줄과 문항이 달라진다.
7. 공개 점수만 오르고 내 문항 점수가 그대로면, 학습 데이터가 평가 문항과 같은 사실을 외우게 했는지 살펴본다.

`wku-lora`가 틀린 문항의 `id`는 위 표에 적고, `ex04` 출력은 [1교시 안내](examples/period1/README.md#터미널-출력을-파일로-남기기)대로 파일로 남긴다. 4교시 1단계에서 그중 한 문항의 `질문` 줄을 `ex07`에 넣는다.

완료 기준

- 기록표에 `wku-lora`와 `wku-base`의 줄이 각각 `mine`·`public`으로 있다.
- `ex06`이 뺀 학습 문항과 이유, `ft01`의 토큰 수 범위와 `train_runtime`을 적었다.
- 평가 문항(공개 20문항, 내 문항)을 학습 데이터에 넣지 않았다.

명령 전체와 막히는 곳은 [따라하기](walkthrough.md)와 [3교시 안내](examples/period3/README.md)에 있다.

## 4교시 — 추론 버그 잡기

문제: 3교시에 자기 모델이 틀린 문항 하나를 `ex07`로 재현해 원인을 좁히고, 버그 세 개가 `ex07`의 [6]·[5]와 `ex04` 실패 종류 표에 어떻게 나타나는지 예상과 비교한다.

| 시간 | 활동 |
|---|---|
| 0~7분 | (examples/) 1. `ex04`에서 실패한 문항의 `질문` 줄을 `ex07`(`BOT = "rag_bot"`, `SHOW_PROMPT = False`)에 넣기 |
| 7~12분 | 2. `BOT = "student_bot"`으로 같은 질문을 넣어 두 출력 비교 |
| 12~27분 | 3. `ex07`의 `BOT`을 `"rag_bot"`으로 되돌리고 넣기 전 `git diff -- src/rag_bot/__init__.py`와 질문 A 기준값 기록, 버그 1~3마다 예상 → 넣기 → `ex07`·`ex04` 관찰 → 되돌리기 |
| 27~30분 | 4. 위 표 정리 |

`rag_bot`의 `MODEL`은 3교시에 등록한 자기 모델(예: `"wku-lora"`)로 둔다. 버그 심기에는 질문 A(원광대학교를 상징하는 새는 무엇인가요?) 하나만 넣는다. 시간이 모자라면 `ex04`는 버그 하나에서만 실행하고, 하지 못한 버그는 과제 기간에 골라서 한다(선택). 버그 1은 수업에서 끝까지 한다.

단계별 힌트

1. 실패한 문항은 `ex04` 출력에서 점수 줄과 `응답` 줄 사이에 `질문` 줄이 있다. `질문` 낱말 뒤의 문장만 복사한다. 출력이 남아 있지 않으면 3교시와 같은 설정으로 `ex04`를 한 번 더 실행한다.
2. `ex07`의 `BOT`과 `rag_bot`의 `MODEL`은 `ex04`에서 잴 때와 같게 둔다. 봇 파일이나 `ex07`의 상수를 고치면 `/bye`로 끝내고 다시 실행한다.
3. [5]의 status가 `ok`인데 점수가 낮았으면 형식은 맞고 답의 내용이 틀린 것이다. [6]에 문제 줄이 없으면 반환값을 정답과 비교하고, 검색된 문서(`ex05`)와 `SYSTEM_PROMPT`를 본다.
4. 두 봇은 검색 방법과 모델이 함께 다르다. 차이가 검색에서 왔는지 모델에서 왔는지 [3]과 [2]를 나눠 적는다. 참고 줄은 `ex07`이 문제로 판정하지 않은 값이고, 답에 주는 영향은 참고 줄 끝의 안내대로 재 봐야 안다.
5. 버그는 한 번에 하나만 넣는다. 버그 2의 값은 질문 A 기준값의 eval_count를 2로 나눈 정수다. 버그 3은 `MODEL`의 지금 이름에서 한 글자만 틀리게 한다.
6. 예상은 질문 A 기준값의 capabilities와 [증상별 확인할 값과 고칠 곳](examples/debugging.md#증상별-확인할-값과-고칠-곳) 표를 보고 정한다. 같은 버그라도 `MODEL`이 가리키는 모델에 따라 결과가 다를 수 있다.
7. 기준값에서도 [6]에 줄이 나올 수 있다. 버그를 넣은 뒤에는 기준값에 없던 줄을 찾는다. `ex07`을 다시 켠 첫 질문에서 모델을 다시 올리면 버그와 상관없이 '모델 새로 적재'가 나올 수 있다.
8. `ex04`는 `BOT = "rag_bot"`, `QUESTION_SET = "mine"`으로 실행하고 전체 평균을 3교시 기록표의 자기 모델 `mine` 줄과 비교한다. [5]의 status는 1교시 실패 종류 표에서 `invalid_response`가 형식 오류, `timeout`이 시간 초과, `error`가 실행 오류다.
9. 되돌린 뒤 `git diff -- src/rag_bot/__init__.py` 출력이 넣기 전 기록과 같은지 본다. 다르면 버그를 넣은 줄을 다시 본다.

완료 기준

- 1단계 문항의 [5] status, [6]의 증상(없으면 '없음'), 확인한 값, 고칠 곳을 적었다.
- 기준 봇과 자기 모델의 차이를 하나 이상 적었다.
- 수업에서 넣은 버그의 예상과 관찰을 적었고(버그 1은 반드시), `git diff` 출력이 넣기 전 기록과 같다.

명령, 상수, 과제 폴더에서 `ex07`을 쓰는 방법은 [4교시 안내](examples/period4/README.md)에, 증상 표와 나머지 버그는 [추론 버그 잡기](examples/debugging.md)에 있다.
