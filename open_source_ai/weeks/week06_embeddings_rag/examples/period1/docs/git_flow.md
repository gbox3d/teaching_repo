# GitHub 협업 흐름: Issue에서 Merge까지

다른 사람의 저장소에 변경을 제안하는 순서는 Fork, Issue, Branch, Pull Request, Review, Merge다. 먼저 Issue로 무엇을 왜 바꾸려는지 적어 합의를 얻는다.

자신의 fork에서 `feature/readme`처럼 목적이 드러나는 브랜치를 만들고 작은 단위로 커밋한다. 커밋 메시지 제목은 명령형으로 짧게 쓰고, 본문에는 왜 바꾸었는지를 적는다.

Pull Request(PR)에는 변경 이유, 확인 방법, 관련 Issue 번호를 적는다. 리뷰어는 사람이 아니라 코드에 대해 말하며, 수정 요청이 오면 같은 브랜치에 커밋을 추가해 push하면 PR이 자동으로 갱신된다.

작업이 끝나지 않았어도 의견을 받고 싶으면 Draft PR로 열어 둔다. 하나의 PR은 하나의 목적만 담아야 리뷰가 빨라진다. 같은 줄을 서로 다르게 고치면 충돌이 생기며, 충돌 표시를 직접 정리한 뒤 커밋해 해결한다.
