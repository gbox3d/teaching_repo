# 1교시 · 설명 20분
## 오픈소스 거버넌스 — 역할·규칙·건강 지표

---

## 0–3분 · 코드보다 먼저 정해지는 것

```text
거버넌스 = 누가(역할) · 무엇을(결정 범위) · 어떻게(절차) 결정하고 바꾸는가
```

- 혼자일 때는 "내가 정한다"로 충분했다.
- 세 명이 되면 merge 권한, 리뷰 순서, 충돌 시 결정권이 필요하다.
- 규칙이 문서에 없으면 규칙은 목소리 큰 사람에게 있다.

**규칙은 코드처럼 저장소에 커밋되어야 한다.**

**질문:** 팀원 둘이 서로 다른 모델을 고집하면 누가 어떻게 정하는가?

---

## 3–6분 · 네 가지 역할

```text
사용자 ──▶ 기여자 ──▶ 커미터 ──▶ 메인테이너
 (쓴다)   (Issue·PR)  (merge 권한)  (방향·릴리스·규칙)
```

| 역할 | 하는 일 | 권한 |
|---|---|---|
| 사용자 | 실행, 버그 보고 | 없음 |
| 기여자 | Issue, PR, 리뷰 코멘트 | fork 안에서만 |
| 커미터 | 리뷰 승인, merge | 브랜치 쓰기 |
| 메인테이너 | 로드맵, 릴리스, 규칙 개정 | 저장소 설정 |

우리 팀은 셋 다 커미터이고, **메인테이너 역할은 돌아가며 맡는다**(릴리스 담당).

## 6–9분 · 의사결정 모델

| 모델 | 누가 결정하는가 | 예 | 강점·약점 |
|---|---|---|---|
| BDFL | 창시자 한 명 | 초기 소규모 프로젝트 | 빠름 · 버스 팩터 1 |
| 위원회 | 선출·지명된 운영진 | 대형 커뮤니티 프로젝트 | 안정 · 느림 |
| 재단 | 법인 아래 기술 위원회 | 여러 기업이 함께 쓰는 프로젝트 | 중립 · 절차 무거움 |

- 모델 이름보다 **"결정이 어디에 기록되는가"**를 본다: Issue 토론, RFC 문서, 회의록.
- 팀 프로젝트는 "합의 안 되면 Issue에 근거를 적고 다수결, 동률이면 이번 마일스톤 담당이 정한다" 정도면 충분하다.

## 9–12분 · 규칙 문서 세트

| 파일 | 답하는 질문 |
|---|---|
| `CODE_OF_CONDUCT.md` | 어떻게 대하는가 — Contributor Covenant 채택 |
| `CONTRIBUTING.md` | 어떻게 참여하는가 — 브랜치·PR·리뷰·응답 시간 |
| `.github/ISSUE_TEMPLATE/*.md` | 무엇을 적어야 보고가 되는가 |
| `.github/PULL_REQUEST_TEMPLATE.md` | 변경을 어떻게 설명하는가 |
| `LICENSE` | 어떤 조건으로 쓰고 나누는가 |

GitHub는 이 파일들을 **Insights → Community Standards**에서 한 화면으로 보여 준다.

**질문:** 전문을 복사해 붙인 CoC와 "채택한다"고 선언한 CoC는 무엇이 다른가?

## 12–15분 · 프로젝트 건강 지표

| 지표 | 어디서 읽는가 | 무엇을 말하는가 |
|---|---|---|
| 첫 응답 시간 | 최근 Issue 3개의 첫 코멘트 시각 | 메인테이너가 살아 있는가 |
| 열린/닫힌 Issue 비율 | Issues 탭의 Open·Closed 수 | 처리 속도 |
| 릴리스 간격 | Releases 탭 날짜 | 예측 가능한 배포 |
| 버스 팩터 | Insights → Contributors 상위 비율 | 몇 명이 빠지면 멈추는가 |

- 수치 하나로 "좋다·나쁘다"를 말하지 않는다. **두 프로젝트를 같은 잣대로 비교**한다.
- 버스 팩터는 "상위 3인 커밋 비율"로 대략 잡는다.

**질문:** 첫 응답은 빠른데 릴리스 간격이 긴 프로젝트는 무엇을 뜻하는가?

## 15–17분 · 시연 — 저장소 두 개를 같은 표로

1. `huggingface/transformers` → Insights → Community Standards → 체크 항목 확인
2. `.github/` 폴더 → 이슈 템플릿 종류 수 → Releases 날짜 5개

4. 수치 항목은 스크립트로 보강

**브라우저에서 읽은 근거 URL이 먼저, 스크립트는 보조**다.

# 2교시 · 설명 20분
## 문제 정의와 기술 선정 근거

---

## 0–3분 · 아이디어가 아니라 문제

```text
[사용자]가 [상황]에서 [문제]를 겪는다.
지금은 [기존 해법]으로 해결하지만 [한계]가 있다.
```

- "수업 도우미 챗봇을 만들겠다"는 아이디어다. 문제가 아니다.
- "실습 중 uv 오류 메시지를 받은 수강생이 검색으로 해결하지만 수업 맥락(uv·Ollama·Windows)이 빠진 답을 받는다"는 문제다.

**문제 문장이 흔들리면 모델·데이터 선택도 흔들린다.**

---

## 3–6분 · 사용자 한 명, 상황 하나

| 항목 | 예 |
|---|---|
| 사용자 | 이 과목을 듣는 수강생 |
| 상황 | 실습 30분 안에 오류를 해결해야 한다 |
| 현재 해법 | 웹 검색, 옆 사람에게 질문 |
| 한계 | 수업 환경과 다른 답, 질문할 사람 부족 |
| 성공 신호 | 오류 메시지를 넣으면 수업 문서 출처와 함께 첫 조치가 나온다 |

- "모든 개발자"는 사용자가 아니다. **얼굴이 떠오르는 한 명**을 고른다.
- 성공 신호는 12주차 베타에서 실제로 측정할 수 있어야 한다.

**질문:** 여러분 팀의 사용자는 지금 그 문제를 무엇으로 해결하고 있는가?

---

## 6–9분 · Must / Should / Could

| 등급 | 뜻 | 예 |
|---|---|---|
| Must | 없으면 베타가 아니다 (3개) | 오류 메시지 입력 → 출처 있는 답, `/health`, 실행 절차 README |
| Should | 있으면 확실히 좋다 | 대화 이력, 수업 문서 자동 갱신 |
| Could | 시간이 남으면 | 웹 UI 테마, 음성 입력 |

- Must는 **12주차 3차 과제 베타에 반드시 들어가는 것**만 3개.
- Should 이상은 Issue로 만들되 마일스톤 M3 이후에 둔다.
- 범위 과다는 가장 흔한 실패 원인이다. Must가 5개면 이미 많다.

---

## 9–12분 · 모델 선정 기준 네 가지

| 기준 | 확인 방법 | 기록 |
|---|---|---|
| 라이선스 | 모델 카드의 SPDX ID 또는 약관 이름 | 상업적 이용·재배포 조건 |
| VRAM | 파라미터 × 비트 ÷ 8 + KV 캐시 | 12 GB 안에 들어가는가 |
| 재현성 | Ollama 태그, HF revision 고정 | 정확한 ID |
| 한국어 품질 | 같은 프롬프트 5개로 비교 | 4주차 `model_report.md` 재사용 |

```powershell
uv run python vram_estimate.py --candidate "qwen3:8b,8.2B,4" --candidate "qwen3:0.6b,0.6B,4"
```

**추정치와 실측치를 나란히 적는다.** 추정만 있으면 근거가 아니다.

---

## 12–15분 · 데이터 선정 기준

| 기준 | 질문 |
|---|---|
| 확보 가능성 | 자체 작성, 공개 데이터셋, 사용자 생성 중 무엇인가 |
| 라이선스 | CC-BY·CC0처럼 재배포가 허용되는가, 연구 전용인가 |
| 개인정보 | 이메일·전화·이름 패턴이 들어올 수 있는가 |
| 양 | LoRA는 자체 작성 40~60건으로도 시작할 수 있다 |
| 평가셋 분리 | 학습에 쓰지 않을 10~20문항을 처음부터 떼어 둔다 |

- 5주차 `SOURCES.md`, 7주차 `evalset.json`이 그대로 데이터 후보 근거가 된다.
- "데이터는 나중에 구한다"는 계획이 아니라 **위험**이다.

**질문:** 여러분 팀의 첫 50건은 누가 언제 쓰는가?

---

## 15–17분 · 위험과 완화

| 위험 | 신호 | 완화 |
|---|---|---|
| 데이터 없음 | 10주차까지 학습 파일 0건 | 팀원 3명이 각 20건 자체 작성 |
| VRAM 부족 | 로드 시 OOM | 소형 모델·양자화·`num_ctx` 축소 |
| 범위 과다 | Must가 5개 이상 | Must 3개로 잘라 Should로 강등 |
| 팀원 이탈·공백 | 한 사람 브랜치에만 커밋 | Issue를 작게, 리뷰어 교차 지정 |

위험은 "없다"고 쓰지 않는다. **없다고 쓴 팀이 12주차에 가장 많이 막힌다.**

## 3–6분 · 마일스톤 3개

```text
M1 · 11주 · 첫 실험 기록      experiments/run-001.md, DATA_CARD.md, 평가셋 10문항
```

## 9–12분 · PR 규칙과 리뷰어

| 규칙 | 우리 팀 기본값 |
|---|---|
| 브랜치 이름 | `feat/<issue번호>-<짧은-설명>` |
| PR 크기 | 변경 300줄 이하, Issue 1개당 PR 1개 |
| 리뷰어 | 작성자가 아닌 팀원 1명 필수 |
| 자기 merge | 금지 (리뷰 승인 후 merge) |
| 응답 기대 시간 | 리뷰 요청 후 48시간 |

- 규칙은 `CONTRIBUTING.md`에 적고, 1교시에 고른 규칙 3개를 반영한다.
- 13주차에 branch protection으로 **규칙을 저장소 설정에 강제**한다.

## 12–15분 · 개인 기여 증거

```text
팀 저장소 → Insights → Contributors : 누가 언제 얼마나
Issues (assignee:@me) · Pull requests (author:@me) · Reviews (reviewed-by:@me)
```

- 팀 과제라도 **채점은 개인의 commit·Issue·PR·Review**를 본다.
- 한 사람 계정으로 몰아서 push하면 나머지 팀원의 증거가 사라진다.
- 공유 PC에서는 각자 자기 계정으로 로그인하고, 끝나면 로그아웃한다.

## 15–17분 · 3분 제안 발표 구성

| 시간 | 내용 | 채점표 항목 |
