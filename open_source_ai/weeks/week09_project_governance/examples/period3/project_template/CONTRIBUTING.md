# 기여 안내

이 문서는 팀원과 외부 기여자가 같은 절차로 참여하게 하는 규칙이다. 규칙을 바꿀 때는 이 파일을 고치는 PR로 바꾼다.

## 참여 흐름

```text
Issue 등록 → 브랜치 생성 → 작은 commit → PR(템플릿) → 리뷰 1명 승인 → merge → Issue 닫힘
```

1. 모든 작업은 **Issue에서 시작**한다. Issue가 없으면 먼저 만든다(`.github/ISSUE_TEMPLATE/` 사용).
2. 브랜치 이름은 `feat/<issue번호>-<짧은-설명>`, 버그는 `fix/<issue번호>-<짧은-설명>`.
3. commit 메시지 제목은 명령형 영문 또는 한국어 한 줄(50자 이내), 본문에는 **왜** 바꿨는지 적는다.
4. PR은 Issue 1개당 1개, 변경 300줄 이하를 목표로 한다. 크면 나눈다.
5. PR 본문의 템플릿 항목(목적·변경·확인 방법·관련 Issue)을 모두 채운다.
6. 작성자가 아닌 팀원 1명이 리뷰·승인해야 merge한다. **자기 PR을 자기가 merge하지 않는다.**
7. merge 방식은 squash를 기본으로 한다. 릴리스 담당이 다르게 정하면 이 문서를 고친다.

## 리뷰 규칙

- 리뷰 요청 후 **48시간** 안에 첫 응답을 남긴다. 못 하면 Issue 코멘트로 알린다.
- 코멘트는 코드에 대해 쓴다. 사람에 대해 쓰지 않는다. 제안은 "이렇게 하면 ~ 때문에 좋겠다"처럼 이유를 붙인다.
- 리뷰어는 최소 다음을 확인한다: 실행되는가, Issue의 완료 조건을 만족하는가, 비밀·개인정보가 없는가, `SOURCES.md` 갱신이 필요한 외부 자원이 들어오지 않았는가.

## 의사결정

- 기술 선택이 갈리면 Issue에 각자 근거(실측 수치·라이선스·일정 영향)를 적고 다수결로 정한다.
- 동률이면 현재 마일스톤 담당이 정하고 결정 이유를 Issue에 남긴다.
- 결정 기록이 없는 변경은 되돌릴 수 있다.

## 실행·검증

```powershell
uv sync
uv run team-project doctor
```

13주차부터는 `uv run pytest`와 `uv run ruff check`가 통과해야 merge한다.

## 하지 않는 것

- `.env`, 토큰, 개인정보, 모델 가중치 파일을 커밋하지 않는다.
- 출처와 라이선스가 없는 코드·데이터·모델을 들여오지 않는다. 들여오면 `SOURCES.md`에 같이 적는다.
- `main`에 직접 push하지 않는다.
