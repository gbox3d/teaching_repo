# 기말평가 루브릭 — 프로젝트 검증 100점

기말평가는 별도 필기시험이 아니라, 제출된 릴리스를 평가자(강의자 또는 조교)가 깨끗한 PC에서 [examples/reviewer_checklist.md](examples/reviewer_checklist.md) 절차로 검증하는 것이다. 15주차 2교시의 교차 재현 검증 기록은 참고 자료이며 점수를 대신하지 않는다. 배점은 100점 상대 배점이며, 학교 적용 시 실제 비율·마감은 학교 운영 문서가 정한다.

## 평가 절차

1. 제출 정보의 저장소 URL·태그·commit id를 확인하고 `git clone` → `git checkout <태그>`.
2. `uv sync --frozen` → README 재현 절차대로 Must 기능 실행 → `uv run pytest -q`.
3. 오류 경로 확인: Ollama 서버를 끈 상태와 잘못된 입력에서 사람이 읽을 수 있는 메시지가 나오는가.
4. 코드·테스트·CI·리뷰 이력을 읽는다(`tests/`, `.github/workflows/`, PR 목록).
5. 문서·평가 결과·한계·CHANGELOG가 실제 실행 결과 및 태그와 일치하는지 대조한다.
6. 채점 기록 양식에 근거와 함께 적는다.

## 배점 표

| 항목 | 배점 | 완전 충족 기준 |
|---|---:|---|
| 기능 동작 | 30 | 제안서의 Must 기능이 README 절차대로 실행되고, 정상 경로와 오류 경로(Ollama 미기동·잘못된 입력·컨텍스트 밖 질문 등) 모두 사람이 읽을 수 있는 결과를 낸다. 출처·모델 표시가 실제 출력에 있다 |
| 코드 품질 | 25 | 설정과 코드가 분리되어 있고(`.env.example`·환경변수 기본값), 모델 호출이 격리되어 테스트 가능하다. `uv run pytest -q`와 `uv run ruff check`가 통과하고 CI가 초록불이다. 리뷰 코멘트가 코드 변경으로 이어진 흔적이 있다 |
| 재현성 | 25 | clone → `uv sync --frozen` → 실행 → 테스트가 평가자의 개입 없이 통과한다. `uv.lock`이 `pyproject.toml`과 맞고, 모델 ID·용량·캐시 위치·GPU 없는 대체 경로가 README에 있으며 그대로 동작한다 |
| 완성도 | 20 | README·평가 수치·한계·실패 사례가 실제 저장소 상태와 일치한다. 알려진 결함이 Issue 또는 한계 항목에 있다. 릴리스 태그·CHANGELOG·commit id가 정합하다. 실행 화면 또는 시연 영상이 기준본과 같다 |
| 합계 | 100 | |

## 수준별 판단

### 완전 충족

평가자가 README만으로 재현했고, 오류 경로에서도 프로그램이 죽지 않고 원인을 알려 준다. 테스트·CI·문서·태그가 서로 모순되지 않는다.

### 부분 충족

핵심 기능은 동작하지만 오류 경로 일부가 스택 트레이스로 끝나거나, 재현 중 문서에 없는 명령이 필요했거나, 테스트는 통과하지만 CI가 없거나, 문서의 수치가 실제 출력과 다르다. 시도 흔적만이 아니라 실행 가능한 부분 결과가 있어야 한다.

### 미충족

`uv sync --frozen`이 릴리스 결함으로 실패하거나, Must 기능이 실행되지 않거나, 태그가 없거나, 본인(팀) 구현임을 확인할 수 없다.

## 감점 적용 원칙

- 환경 문제(평가 PC의 모델 미캐시·네트워크·포트 충돌)는 감점하지 않고 기록한다. README가 그 상황을 안내하고 있으면 재현성 항목에서 오히려 근거로 인정한다.
- 같은 원인으로 여러 증상이 생기면 가장 관련 있는 항목에서 한 번만 감점하고 나머지에는 기록만 남긴다.
- 항목별 최대 배점을 넘겨 감점하지 않는다.
- 모델 품질(정확도·속도)의 한계는 그 자체로 감점하지 않는다. 한계가 문서에 정직하게 있는지로 완성도를 판단한다.
- 실제 비밀·개인정보 노출은 4차 종합과제 루브릭의 보안 항목에서 처리하고, 이 루브릭에서는 기록만 남긴다.
- 발표 장애와 검증 결과는 별개다. 발표에서 실패했어도 저장소가 재현되면 이 루브릭에서는 감점하지 않는다.
