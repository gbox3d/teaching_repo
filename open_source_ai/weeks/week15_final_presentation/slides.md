# 1교시 · 설명 20분
## 발표 규칙과 평가자의 시선

---

## 0–3분 · 발표는 주장이 아니라 증거다

- 이어받는 것: 14주차 `v0.1.0` 릴리스, 교차 재현 Issue, 시연 리허설
- 이번 주 세 증거: 발표 기록 → 검증 기록 → 회고·제출 점검
- 발표는 완성도를 자랑하는 자리가 아니다
- **재현 가능한 주장을 3분 안에 실제로 실행해 보이는 자리다**

**질문:** 발표에서 "잘 됩니다"라는 말 대신 무엇을 보여 주면 평가자가 믿는가?

---

## 3–6분 · 발표 규칙

| 항목 | 규칙 |
|---|---|
| 시간 | 팀당 시연 3분 + 질의 2분, 타이머 준수 |
| 기준본 | 릴리스 태그가 가리키는 commit, `git describe --tags`로 시작 |
| 코드 | 발표 중·다른 팀 발표 중 수정 금지 |
| 장애 | fallback(사전 `outputs/`·녹화)으로 마치고 원인 기록 |
| 화면 | 토큰·`.env`·개인 경로·실명 노출 금지 |

**태그 밖에서 실행한 시연은 릴리스의 증거가 아니다.**

---

## 6–10분 · 평가자가 보는 네 가지

| 보는 것 | 통과 신호 | 실패 신호 |
|---|---|---|
| 문제 | 30초 안에 사용자·상황이 한 문장 | 기술 이름 나열로 시작 |
| 시연 | 기능 1개가 실제로 실행되고 출처·모델이 보임 | 캡처만 넘김 |
| 한계 | 수치 1개 + 실패 사례 1개를 같은 무게로 | "다 됩니다" |
| 재현 | README 절차 3줄, 열린 Issue | 재현 언급 없음 |

**질문:** 네 가지 중 우리 팀이 지금 가장 약한 것은 무엇인가?

---

## 10–13분 · 3분 시연 구성

| 시간 | 화면 | 증거 |
|---:|---|---|
| 0:00–0:30 | README 첫 화면, `git describe --tags` | 저장소 URL, 태그 |
| 0:30–1:45 | 핵심 기능 1개 실제 실행 + 오류 처리 1개 | 실행 출력, `outputs/` |
| 1:45–2:20 | 평가 수치 1개, 실패 사례 1개 | `eval-*.json`, `FAILURE_ANALYSIS.md` |
| 2:20–3:00 | 재현 절차 3줄, 열린 Issue | README, Issues |

서버 켜기·모델 로드·저장소 열기는 발표 **전에** 끝낸다. 실행 구간이 가장 길어야 한다.

---

## 13–16분 · 질문 카드와 답하는 순서

카드 예시(`examples/question_cards.md`):

- 처음 보는 PC에서 README만 보면 어디서 먼저 막히는가?
- 오픈 웨이트 모델을 썼는데 "오픈소스 AI"라 부를 수 있는가?
- Ollama가 꺼져 있으면 `/chat`은 무엇을 돌려주는가? 지금 보여 달라.

답하는 순서: **질문 재진술 → 현재 사실(파일·수치) → 선택 이유 → 한계·다음 조치**

**질문:** 모르는 질문을 받았을 때 가장 나쁜 답과 가장 좋은 답은 무엇인가?

---

## 16–18분 · 순서·장비·장애

- 발표 순서와 기록 담당을 먼저 정한다
- 발표 PC: `git status` clean, `git describe --tags`, `ollama list`
- 터미널 글꼴 확대, 시연 명령은 한 파일에 순서대로
- 장애 대체: Ollama 재시작 1회 → 사전 `outputs/` → 녹화 재생
- 청중은 `presentation_log.md`에 팀마다 한 행, **점수는 적지 않는다**

---

## 18–20분 · 실습 인계

[1교시 실습 — 최종 발표 라운드](lab.md#1교시-실습--최종-발표-라운드)

완료 조건:

1. 기준본(태그) 확인 출력이 화면에 나왔다.
2. 시연에 실제 실행과 한계 진술이 모두 있었다.
3. 받은 질문·답하지 못한 질문을 `presentation_log.md`에 적었다.

팀이 4팀을 넘으면 학교 시간표에 따라 확장한다. 실습 30분 뒤 휴식 10분, 휴식 후 2교시.

# 2교시 · 설명 20분
## 재현성 검증 절차와 기말평가 항목

---

## 0–3분 · 왜 남이 재현해야 하는가

- 이어받는 것: 1교시 기록표의 검증 대상 팀 URL·태그
- 내 PC에서 되는 것은 증거가 아니다. **처음 보는 사람이 README만으로 되는 것이 증거다**
- 기말평가는 필기시험이 아니라 평가자가 릴리스를 체크리스트로 검증하는 것
- 오늘 다른 팀 저장소에 같은 절차를 먼저 적용한다

**질문:** 14주차 교차 재현에서 우리 팀이 받은 Issue는 지금 닫혔는가?

---

## 3–7분 · 평가자 체크리스트 6단계

```powershell
git clone <URL> .\review\team-b
git -C .\review\team-b checkout v0.1.0
Set-Location .\review\team-b
uv sync --frozen
uv run python -m app ...      # README 절차대로 기능 1개
uv run pytest -q
```

이어서 문서(README·LICENSE·CONTRIBUTING·CHANGELOG·SOURCES) → 라이선스·출처 대조 → 비밀·개인정보 검사. `reviewer_checklist.md`는 이 여섯 단계를 0~9행으로 펼친다.

**단계 순서를 바꾸지 않는다. 건너뛴 단계는 "해당 없음"과 이유를 적는다.**

---

## 7–10분 · 실패를 구분한다

| 유형 | 예 | 처리 |
|---|---|---|
| 환경 문제 | 모델 미캐시, 포트 충돌, 네트워크 | 재시도 1회, "환경"으로 기록 |
| 릴리스 결함 | `uv.lock` 불일치, README 누락 단계, 테스트 실패, 태그 없음 | Issue로 보고 |
| 설계 한계 | 모델 품질·속도 | 한계 항목 명시 여부만 확인 |

`uv sync --frozen` 실패 메시지 첫 줄이 분류 근거다.

**질문:** 대상 팀 모델이 내 PC에 없다. 이것은 어느 유형인가? README에 무엇이 있어야 통과인가?

---

## 10–13분 · 검증 도구 시연

```powershell
.\cross_review.ps1 -RepoUrl <URL> -Team team-b -Tag v0.1.0
uv run python verify_release.py --repo .\review\team-b --team team-b
```

- `verify_release.py`: 필수 파일·`.gitignore`·태그·README 절·비밀 패턴 → `outputs/verify-*.md`
- `cross_review.ps1`: clone → checkout → sync → pytest → verify를 한 로그로
- 결과는 PASS / WARN / FAIL. **WARN은 도구가 판단을 미룬 것, 사람이 읽는다**
- README 절차대로 기능을 실행하는 단계는 자동화하지 않는다

---

## 13–16분 · 기말평가 항목

| 항목 | 배점 | 평가자가 확인하는 것 |
|---|---:|---|
| 기능 동작 | 30 | Must 기능이 README 절차로 실행, 정상·오류 경로 |
| 코드 품질 | 25 | 구조·pytest·ruff·CI·리뷰 반영 |
| 재현성 | 25 | clone → sync → 실행 → 테스트가 개입 없이 통과 |
| 완성도 | 20 | 문서·수치·한계가 실제와 일치, 태그·CHANGELOG |

100점 상대 배점이다. 실제 비율은 학교 운영 문서가 정한다. 자세한 기준은 `final_review_rubric.md`.

**질문:** 오늘 검증에서 대상 팀이 가장 많이 잃을 항목은 어디인가?

---

## 16–18분 · 리뷰 기록의 규칙

- 사실만: 명령, 출력 첫 줄, 파일명, commit id
- 사람이 아니라 저장소에 대해 쓴다
- 대상 저장소에 push하지 않는다. Issue만 남긴다
- Issue 양식: 제목 `[재현] <단계> <증상>`, 환경, 절차, 기대, 실제, 분류
- **대상 팀이 그대로 따라 할 수 있어야 좋은 재현 보고다**

---

## 18–20분 · 실습 인계

[2교시 실습 — 교차 재현 검증](lab.md#2교시-실습--교차-재현-검증)

완료 조건:

1. 0~9단계 모두에 통과/실패/해당 없음과 근거가 있다.
2. 실패마다 환경 문제 / 릴리스 결함 / 설계 한계 분류가 있다.
3. 릴리스 결함 Issue를 1건 등록했다(없으면 근거를 적었다).

실습 30분 뒤 휴식 10분, 휴식 후 3교시.

# 3교시 · 설명 20분
## 회고와 오픈소스 이후

---

## 0–3분 · 회고는 평가가 아니다

- 이어받는 것: 2교시 검증 기록, 우리 팀이 받은 Issue
- 회고의 목적은 점수가 아니라 **다음 프로젝트에서 바뀔 행동 하나**
- 근거 없는 문장("열심히 했다")은 회고가 아니다
- 오늘 산출물: 동료 피드백 1건, 개인 회고, 제출 정보 확정

---

## 3–7분 · 회고 방법 세 칸

| 칸 | 나쁜 예 | 좋은 예 |
|---|---|---|
| 잘된 것 | 협업이 잘 됐다 | PR 12건 중 11건이 리뷰 1회 이상 뒤 merge(Issue #8~#20) |
| 어려웠던 것 | 시간이 부족했다 | LoRA run-002가 VRAM 초과로 3회 실패, 원인은 batch 8 |
| 다음에 다르게 | 더 일찍 시작 | 실험 기록 양식을 첫 학습 전에 커밋 |

**모든 칸에 commit·Issue·수치 중 하나를 붙인다.** 못 붙이면 지운다.

**질문:** 우리 팀 저장소에서 "잘된 것"의 근거로 쓸 수 있는 파일은 무엇인가?

---

## 7–10분 · 동료 피드백 원칙

- 점수를 주지 않는다. 사실과 제안을 나눈다
- 구체적으로: 파일·명령·수치가 들어간 문장만
- 실행 가능하게: 이번 주 안에 할 수 있는 제안 1개
- 저장소·발표에 대해 쓴다. 사람에 대해 쓰지 않는다
- 양식: 좋았던 점 1 · 재현 실패 1 · 제안 1 · 질문 1
- 전달: 대상 팀 Issue 또는 Discussion, URL 기록

---

## 10–13분 · 오픈소스 이후

| 책임 | 무엇을 | 언제 |
|---|---|---|
| 기여 지속 | 받은 Issue 응답, 패치 릴리스(`v0.1.1`) | 학기 뒤 첫 달 |
| 포트폴리오 | README 첫 화면, 릴리스 페이지, 기여 그래프 | 지원 전 |
| 라이선스 유지 | 의존성·모델 라이선스 재확인, `SOURCES.md` 갱신 | 반년마다 |

**라이선스는 릴리스 순간이 아니라 유지하는 동안의 책임이다.** 한 번 공개한 라이선스로 받은 사용자의 권리는 되돌릴 수 없다.

**질문:** 사용한 모델의 라이선스가 다음 버전에서 바뀌면 우리 저장소는 무엇을 해야 하는가?

---

## 13–16분 · 4차 과제 제출 점검

`examples/submission_checklist.md`의 여덟 묶음:

- 기준본: 태그 → commit id, URL이 로그아웃 상태에서 열림
- 실행·재현: 깨끗한 폴더 clone → `uv sync --frozen` → 절차 → pytest
- 문서 세트 · 출처·라이선스(`SOURCES.md`, SPDX)
- 협업 근거: 팀원별 commit·Issue·PR·Review URL
- 평가·한계 · AI 도구 활용 내역(채택·거절·검증)
- 보안: `.env` 미추적, 이력에 비밀 없음, `pip-audit`

자기 저장소에 `verify_release.py --check-ollama`를 돌려 FAIL을 먼저 없앤다.

---

## 16–18분 · 학기 이후에 할 일 3개

1. 교차 재현 Issue 하나를 닫고 **패치 릴리스** `v0.1.1`을 낸다.
2. 수업 밖 오픈소스 프로젝트에 **작은 Issue 또는 PR** 하나를 보낸다. 문서 오타·재현 실패 보고도 기여다.
3. 한 학기 뒤 모델·데이터·의존성 **라이선스를 다시 확인**하고 `SOURCES.md`를 갱신한다.

다음 주차 폴더는 없다. 저장소는 닫지 않는다.

**질문:** 셋 중 이번 달 안에 실제로 할 수 있는 것은 무엇인가? 담당은 누구인가?

---

## 18–20분 · 실습 인계

[3교시 실습 — 회고와 최종 제출 점검](lab.md#3교시-실습--회고와-최종-제출-점검)

완료 조건:

1. 피드백 4칸에 구체적 근거가 있고 대상 팀에 전달한 URL이 있다.
2. 회고 1~3절의 모든 항목에 근거가 붙어 있다.
3. `submission.md`의 commit id가 태그가 가리키는 commit과 같다.

실습 30분 뒤 휴식 10분. 학기 마지막 블록이다.

## 이번 주 정리

```text
발표: 기준본(태그) → 실제 실행 → 한계 → 재현 절차          (3분 + 2분)
검증: clone → sync --frozen → 실행 → 테스트 → 문서·라이선스 → 비밀
회고: 잘된 것 · 어려웠던 것 · 다음에 다르게  + 근거 하나씩
이후: 패치 릴리스 · 외부 기여 · 라이선스 재확인
```

**다른 사람이 재현·검증·기여할 수 있을 때 비로소 오픈소스 릴리스다.**
