# 3차 종합과제 — PEFT/LoRA 실험 기록과 AI 서비스 베타

## 목적

9~12주차(3장 모델 적응과 서비스 구현)에서 팀이 한 일을 **다른 사람이 재현하고 실행할 수 있는 형태**로 팀 저장소에 남긴다. LoRA 학습이 "돌아갔다"가 아니라 같은 설정으로 다시 돌릴 수 있어야 하고, 평가 수치는 어떤 데이터·지표로 나왔는지 추적되어야 하며, 서비스는 모델 서버가 꺼졌을 때도 원인을 말해야 한다. 이 과제의 결과물은 13~15주차 테스트·CI·릴리스의 출발점이 된다.

## 대상 챕터 범위

| 주차 | 내용 | 이 과제에서 확인하는 것 |
|---|---|---|
| 9주차 | 프로젝트 제안·거버넌스 | 제안서의 Must 범위와 마일스톤이 실제 산출물과 연결되는가 |
| 10주차 | PEFT/LoRA | 실험 기록 양식, 어댑터 저장, 전후 비교 |
| 11주차 | 데이터셋 구성·모델 평가 | 데이터 카드, PII 점검, 기준선 대비 정량·정성 평가, 실패 분석 |
| 12주차 | AI 서비스화와 배포 | `/health`·`/chat`, UI, 오류 처리, 설정 외부화, 실행 절차 |

## 필수 산출물

1. **실험 기록 2회 이상** — `experiments/run-001.md`, `experiments/run-002.md`(10주차 양식). 각 기록에 LoRA 설정(r·alpha·target modules), 데이터 버전(파일명·건수·commit), seed, 실행 시간, VRAM, step별 loss 요약, 샘플 출력 3개 이상, 실패·중단 사례. 두 기록은 최소 한 가지 변수(r, 데이터, epoch 등)가 달라야 하고 무엇을 왜 바꿨는지 적는다.
2. **데이터 카드** — `DATA_CARD.md`(11주차 양식). 출처·라이선스·정제 전후 건수·중복 제거·PII 점검 결과·분할 비율·알려진 편향.
3. **평가 결과와 실패 분석** — `outputs/eval-*.json`(또는 `evidence/`로 복사한 사본)과 기준선 대비 비교표, `FAILURE_ANALYSIS.md`(사례 3개: 증상·원인 가설·개선안). 평가셋은 학습에 쓰지 않았음을 데이터 카드에 명시한다.
4. **AI 서비스 베타** — 팀 저장소 안의 uv 프로젝트로:
   - FastAPI 앱 서버: `GET /health`(모델 서버 연결·모델 존재 확인), `POST /chat`(pydantic 스키마 검증), 스트리밍은 선택
   - 오류 처리: 모델 서버 연결 실패·모델 없음·시간 초과·잘못된 요청을 **서로 다른 상태 코드**와 사람이 읽을 `detail`로 응답
   - UI 1종: Gradio 또는 정적 HTML+fetch. 대기·오류 상태가 화면에 보일 것
   - `.env.example`(모든 설정 항목과 설명), `.gitignore`(`.env`·`outputs`·`.venv`)
   - 실행 절차: README 「실행」 절에 전제 → 명령 → 확인 → 실패 시 볼 것. Docker 경로는 선택, uv 경로는 필수
   - 증거: 정상 1건과 실패 경로 3건 이상의 점검 결과 JSON(12주차 `smoke_test.py` 형식 또는 동등한 것)
5. **출처·라이선스 갱신** — `SOURCES.md`에 기본 모델·데이터·어댑터의 이름·revision·라이선스·용도·변경 내용. 어댑터를 공개한다면 기본 모델 라이선스와의 관계를 한 줄로 적는다.
6. **개인 기여 증거** — 아래 「개인 기여 증거」 절.

## 제출 형식

- 팀 저장소 URL + **최종 commit id**(40자 또는 7자 이상 축약) + README의 재현 절차 위치(제목 또는 줄 번호)
- 채점은 제출한 commit id 시점의 저장소로 한다. 그 뒤의 commit은 반영하지 않는다.
- 저장소는 채점자가 접근할 수 있어야 한다(공개 또는 강의자 계정 초대). 비공개 저장소라면 초대 완료를 제출물에 적는다.
- 모델 가중치·어댑터 파일은 저장소에 넣지 않는다. 필요하면 재현 명령(학습 스크립트·seed)으로 대체하거나 별도 배포 위치와 해시를 적는다.

## 개인 기여 증거

팀 과제라도 개인별로 다음을 확인한다. README 「기여」 절 또는 `CONTRIBUTORS.md`에 표로 정리한다.

| 항목 | 최소 | 근거로 적을 것 |
|---|---|---|
| commit | 의미 있는 commit 5개 이상 | `git log --author=<이름> --oneline` 결과 요약 |
| Issue | 담당 Issue 2개 이상(열고 닫음) | Issue 번호와 상태 |
| Pull Request | 본인이 연 PR 1개 이상(리뷰를 거쳐 merge) | PR 번호 |
| Review | 다른 팀원 PR에 리뷰 코멘트 1개 이상 | PR 번호와 코멘트 요지 |
| 담당 산출물 | 실험 기록·데이터 카드·서비스·UI·문서 중 1개 이상 | 파일 경로 |

"함께 했다"는 기록으로 인정하지 않는다. 짝 프로그래밍을 했다면 commit 본문의 `Co-authored-by`로 남긴다.

## 제출 전 검사

- [ ] 깨끗한 폴더에 clone → `Copy-Item .env.example .env` → `uv sync` → README의 실행 명령만으로 앱 서버가 뜬다.
- [ ] `/health`가 정상 상태에서 `ok`이고, 모델 서버를 못 찾게 했을 때 `degraded`와 원인 `detail`을 돌려준다.
- [ ] `/chat`이 정상 200, 잘못된 요청 422, 모델 서버 실패 5xx(원인별로 다른 코드)를 돌려주는 점검 JSON이 저장소에 있다.
- [ ] UI에서 정상 답과 오류 문구를 각각 한 번씩 확인했다.
- [ ] `experiments/run-001.md`·`run-002.md`의 설정·seed·데이터 버전만 보고 같은 학습을 다시 시작할 수 있다.
- [ ] `DATA_CARD.md`에 정제 전후 건수와 PII 점검 결과가 있고, 평가셋이 학습에 쓰이지 않았음이 적혀 있다.
- [ ] `FAILURE_ANALYSIS.md`에 사례 3개가 증상·원인 가설·개선안 구조로 있다.
- [ ] `SOURCES.md`의 모델·데이터·어댑터 항목에 라이선스가 모두 적혀 있고, 상업적 이용·재배포 조건이 팀의 공개 계획과 충돌하지 않는다.
- [ ] `git log -p -- .env`가 비어 있고, 저장소 어디에도 토큰·비밀번호·실제 개인정보가 없다.
- [ ] 기여 표의 commit·Issue·PR·Review 번호가 실제로 존재한다.
- [ ] 제출한 commit id가 위 검사를 끝낸 시점의 것이다.

## 금지 사항

- 실제 토큰·비밀번호·개인정보를 저장소에 넣는 것. `.env`를 커밋한 이력이 있으면 토큰을 회전하고 그 사실을 적는다.
- 재현 불가능한 캡처만으로 결과를 주장하는 것. 캡처는 보조 자료이며 JSON·로그·commit이 증거다.
- 실험 기록의 수치를 사후에 고치거나 seed·데이터 버전을 빠뜨리는 것.
- 라이선스가 불명확한 모델·데이터를 쓰는 것. 라이선스가 없는 자원은 사용 불가로 본다.
- 다른 사람의 코드나 AI 도구가 생성한 코드를 출처 표기 없이 넣는 것. AI 도구 사용은 허용하되 README에 무엇을 어떻게 썼고 무엇을 직접 검증·수정했는지 적는다.
- 팀원의 계정으로 대신 commit·리뷰하는 것.

배점·마감은 학교 운영 문서가 정한다. 평가 항목과 수준별 판단은 [3차 종합과제 루브릭](assignment_rubric.md)을 따른다.
